# Follow-through, overshoot and secondary-motion tools in After Effects (expressions, scripts/plugins, baking, Lottie)

Research notes, current as of 2026-10-09. Method note: aescripts.com, schoolofmotion.com, helpx.adobe.com, motionscript.com, mtmograph.com, mamoworld.com, toolfarm.com, lesterbanks.com, community.adobe.com, creativecow.net, lottiefiles.com and most vendor sites were blocked by this session's egress proxy, so product facts for commercial tools come from search-engine summaries of those pages (URL cited) rather than from the pages themselves, while expression source code, the Adobe expression reference (docsforadobe mirror), Lottie's own docs and Duik's docs were read directly on GitHub. Prices are only given where a dated source stated them; treat all prices as "last seen" values.

Seekability vocabulary used below: **PURE(t)** = the output at time t depends only on t plus static inputs (keyframes, sliders), so play/seek/export agree and any frame can be evaluated in isolation; **HISTORY** = the output depends on earlier outputs (a true simulation), so it must be stepped from the start or baked to keyframes; **KEYFRAMES** = the tool writes ordinary keyframes, so it is trivially seekable.

## Key question 1 — Expressions: inertial bounce/overshoot, wiggle/temporalWiggle, delay chains, smooth(), loopOut("offset"), velocity-driven squash/rotation, slider control, and which are pure functions of time

### Takeaway
Every classic AE "overlap" expression is a closed-form function of time: it reads keyframe times, keyframe velocity (`velocityAtTime`) or another property's value at an offset time (`valueAtTime(time - delay)`), then adds a damped sine, a projectile segment, a noise function or a box filter. None of them stores state between frames because AE gives expressions no place to store it; the only "history-dependent" expression behaviours are the ones that re-sample their own past (e.g., Duik's overlap/soft-body simulations), which AE's own documentation flags as quadratic-cost and which are therefore the things users bake.

### Cited Findings

**The Adobe expression primitives these techniques are built on (docsforadobe mirror of the Adobe reference)**
- `valueAtTime(t)` "Returns the value of a property at the specified time, in seconds"; `velocityAtTime(t)` "Returns the temporal velocity value at the specified time"; `speedAtTime(t)` "Returns the spatial speed value at the specified time". — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `wiggle(freq, amp, octaves=1, amp_mult=0.5, t=time)` "Randomly shakes (wiggles) the value of the property"; `freq` in wiggles per second, `amp` in the property's units, `octaves` = noise octaves added together, `amp_mult` = per-octave amplitude multiplier, `t` = base start time so you can wiggle the value sampled at a different time. — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `temporalWiggle(freq, amp, octaves, amp_mult, t)` "Samples the property at a wiggled time" and "For this function to be meaningful, the property it samples must be animated" (it perturbs the sampling time, not the value). — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `smooth(width=.2, samples=5, t=time)` smooths values over time "using a box filter"; `width` = seconds averaged, `samples` = evenly spaced samples ("Higher is smoother but slower. Odd numbers include the current value"). — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `loopOut(type="cycle", numKeyframes=0)` loops the segment measured from the last keyframe back toward the In point; types: `"cycle"`, `"pingpong"`, `"offset"` ("Repeats the segment, offsetting each cycle by the property's start-to-end value difference times the loop count"), `"continue"` ("keeps animating from the velocity at the first or last keyframe"; takes no keyframe argument). `loopOutDuration` takes seconds instead of a key count. — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `nearestKey(t)` returns the Key nearest a time; `key(index)` returns a Key by index; `numKeys` is the keyframe count (and "Separating dimensions changes the keyframe count"); `velocity` returns the temporal velocity at the current time (for spatial properties the tangent vector); `speed` is a 1-D positive spatial speed. — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- AE performance behaviour relevant to statelessness: "After Effects now attempts to detect an expression that does not change throughout a comp and calculates the expression only once", and "Any expression using posterizeTime() now calculates only once for the entire comp, not on every frame." — [docsforadobe changelog](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/introduction/changelog.md)
- Duik's documentation states the evaluation model plainly: "Expressions in After Effects are all evaluated (computed) when rendering each frame of the composition", and because AE has no reliable way to store data in expressions, an expression that depends on the same property's earlier values must "re-compute everything for each frame of the composition", total work `(f² + f) / 2` for `f` frames. — [Duik performance docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/advanced/performance.md)

**The inertial bounce / overshoot expression (Dan Ebberts lineage; Harry Frank "graymachine" popularisation)**
- Canonical text as republished by Animoplex ("Original Version: graymachine.com/top-5-effects-expressions"): — [Animoplex gist](https://gist.github.com/animoplex/aafd6a157282351c8dfeea385d969ef2)
  ```javascript
  amp = 5.0; freq = 2.0; decay = 4.0;
  n = 0;
  if (numKeys > 0) {
    n = nearestKey(time).index;
    if (key(n).time > time) { n--; }
  }
  if (n == 0) { t = 0; } else { t = time - key(n).time; }
  if (n > 0 && t < 1) {
    v = velocityAtTime(key(n).time - thisComp.frameDuration/10);
    value + v*(amp/100)*Math.sin(freq*t*2*Math.PI)/Math.exp(decay*t);
  } else {
    value;
  }
  ```
  Its own comment: "Amp is intensity, freq is bounces per second, and decay is the speed of decay, slow to fast", and "Use this on any property with two keyframes… based on velocity of the value change. Perfect for a scale from 0 to 100 or a speedy rotation". — [Animoplex gist](https://gist.github.com/animoplex/aafd6a157282351c8dfeea385d969ef2)
- Another widely copied version uses `amp = 0.04; freq = 3.0; decay = 10.0`, comments "decay: a friction/mass setting, higher value means a shorter decay", applies only for about the first second after the keyframe, and credits graymachine.com. — [swizzlevixen/ae-expressions](https://github.com/swizzlevixen/ae-expressions/blob/master/intertial-bounce.js)
- The velocity is sampled a tenth of a frame *before* the keyframe (`velocityAtTime(key(n).time - thisComp.frameDuration/10)`) so it reads the arrival velocity rather than the zero velocity after the key. — [Animoplex gist](https://gist.github.com/animoplex/aafd6a157282351c8dfeea385d969ef2); same construct in [after-effects-mcp expressionGenerators.ts](https://github.com/ishu86/after-effects-mcp) ("Velocity arriving at key n: sampled a tenth of a frame before it")
- Ebberts' "overshoot" variant (the motionscript formulation) divides the damped sine by the angular frequency so the wobble launches at exactly the keyframe's velocity: `value + v*(Math.sin(freq*t*2*Math.PI)/Math.exp(decay*t))/(freq*2*Math.PI)` with defaults `freq = 3, decay = 5` in one script that packages it. — [glide host.jsx](https://github.com/EJ-AIpreneur/glide)
- Ebberts' gravity "bounce" variant (settles like a dropped ball) is a loop over bounce segments: velocity after each contact `v = -velocityAtTime(key(n).time - .001)*e` scaled by elasticity `e`, each segment duration `segDur = 2*vl/g` from gravity `g`, displacement `value + vu*delta*(vl - g*delta/2)`, loop `while (tNext < t && nb <= nMax)` with `nMax` = number of bounces. — [Elast-o-matic.jsx (IVG Design, MIT, v1.1.3 2026-07-28)](https://github.com/ivg-design/AE/blob/main/packages/ae-scripts/src/keyframes/Elast-o-matic.jsx)
- Ebberts, 2011: on long timelines the decay term "can grow so large that JavaScript returns Infinity", breaking the division; his fix was to limit the calculation to a few seconds after the key, since the decay has finished by then. — [Creative COW thread 1859347](https://creativecow.net/?p=1859347)
- Ebberts, 2018: to combine the bounce with a time offset, compute on a shifted time variable and use `valueAtTime` for the base value. — [Adobe Community thread 9784480](https://community.adobe.com/t5/after-effects/offset-in-time-and-inertial-bounce-expressions-together/m-p/9784480)
- Ebberts' two-keyframe shortcut samples velocity 0.001 s before the keyframe. — [Creative COW thread 1853883](https://creativecow.net/?p=1853883)
- Attribution is disputed between Ebberts and Harry Frank; search surfaced both claims and could only confirm Ebberts' authorship of the underlying technique. — [School of Motion bounce expression article](https://schoolofmotion.com/blog/after-effects-bounce-expression)
- Visual signature: in the Graph Editor's post-expression graph "We get this sinusoidal wave with a decay in the amplitude", and "The expression uses the velocity at the last keyframe as its energy source". — [Tuts+ inertial bounce tutorial](https://photography.tutsplus.com/tutorials/how-to-animate-inertial-bounce-expressions-in-after-effects--cms-41469)
- The inertial expression overshoots in the direction of travel then settles; a bounce that reverses direction (a drop) needs a different expression — the reason the Ukramedia preset ships "inertial bounce" and "bounce back" separately. — [Adobe Community thread 13578026](https://community.adobe.com/t5/after-effects-discussions/inertial-bounce-multiple-times-on-the-same-property/m-p/13578026/highlight/true); [lesterbanks on Ukramedia's Bounce & Drop preset](https://lesterbanks.com/?p=45802)
- Slider-control packaging: a 2014 CC-BY-SA script adds three Slider Control effects named `BC_amp_<prop>` (0.025), `BC_freq_<prop>` (2) and `BC_decay_<prop>` (3) to the layer and writes `value + v*amp*Math.sin(freq*t*2*Math.PI)/Math.exp(decay*t)` reading them. — [setBounceExpression.jsx](https://github.com/ae-scripting/scripting-snippets/blob/master/setBounceExpression.jsx)
- A shipped Lottie file shows the same formula driven by sliders labelled "Overshoot", "Bounce", "Friction" with `amp = Overshoot/2.5, freq = Bounce/20, decay = Friction/20`, i.e. user-facing 0–100 sliders rescaled inside the expression. — [OctoDash toggle-switch.json](https://github.com/UnchartedBull/OctoDash/blob/master/src/assets/animations/toggle-switch.json)
- A function-library version: `bounceKeys(amp = 0.12, freq = 2.5, decay = 8, keyMin = 1, keyMax = numKeys)` where amp is "The amount of swing past each value", with the note "For better bouncing, use our dedicated library eSpring". — [motiondeveloper/aefunctions](https://github.com/motiondeveloper/aefunctions/blob/master/src/index.ts)
- Spring-interpolation alternative: eSpring is a "Hold-frame based spring animations" library, `eSpring({mass:1, stiffness:100, damping:10, initialVelocity:0, property:thisProperty}, time)`; "You add one keyframe per value, and the spring configuration sets the animation's duration", and it "can animate correctly out of in-progress animations". — [motiondeveloper/espring](https://github.com/motiondeveloper/espring)
- Typical user-tuned ranges seen across sources: amp 0.025–0.12 (velocity-fraction form) or 5 (percent form); freq 2–3 Hz; decay 3–10. — [Animoplex gist](https://gist.github.com/animoplex/aafd6a157282351c8dfeea385d969ef2); [swizzlevixen](https://github.com/swizzlevixen/ae-expressions/blob/master/intertial-bounce.js); [setBounceExpression.jsx](https://github.com/ae-scripting/scripting-snippets/blob/master/setBounceExpression.jsx); [aefunctions](https://github.com/motiondeveloper/aefunctions/blob/master/src/index.ts)

**Delay / follow chains (`valueAtTime(time - delay)`)**
- Pattern: `var delay = index * 0.1; thisComp.layer("Leader").position.valueAtTime(time - delay)` — layers lower in the stack lag more. — [adobe-hut expression notes](https://github.com/dvschultz/adobe-hut)
- "valueAtTime() in Ae gets the value of a property as evaluated at any given time"; tutorials by Felt Tips (staggered delay), Lee Daniels (cascade of layers following a master), Owen Chikazawa (offset in time and position with a controller slider on a separate control layer), Evan Abrams/ECAbrams (simple trail with custom delay; project file) and K Motion (three example setups). — [lesterbanks 52207](https://lesterbanks.com/?p=52207); [lesterbanks 55194](https://lesterbanks.com/?p=55194); [lesterbanks 31357](https://lesterbanks.com/?p=31357); [ECAbrams project file](https://ecabrams.gumroad.com/l/Vfagk); [AEJuice delay-expression article](https://aejuice.com/blog/delay-expression-in-after-effects)
- Springier chains: a Creative COW reply recommends building follow-the-leader from Ebberts' expressions, adding an offset, and "layering overshoot expressions on top of the delay", pointing to MotionScript's elastic-connection expression. — [Creative COW thread 1876656](https://creativecow.net/?p=1876656)
- Cost: "Long chains of layer references add up. It takes After Effects a lot of time to resolve a value by looking up the layer above, then the layer above that"; loops using `valueAtTime()` over earlier comp time get slower the longer the comp. — [Creative COW: tips to optimize your expressions](https://creativecow.net/forums/thread/tips-to-optimize-your-expressions-which-expressi/)
- With motion blur on, expressions are re-evaluated for every motion-blur sample; a user who tried to cache a result in a Point Control and read it with `valueAtTime(0)` found it still evaluated per sample. — [Adobe Community thread 12585183](https://community.adobe.com/t5/after-effects-discussions/sourcerectattime-expression-causing-major-performance-issues-with-motionblur/m-p/12585183)

**wiggle / temporalWiggle for secondary motion**
- "temporalWiggle has the same parameters as the normal wiggle; since you are wiggling time – in seconds – you will find you need much smaller values for the second number… The example uses temporalWiggle(4,0.2), which wiggles time by two-tenths of a second"; and "When the wiggle expression is applied to a property with more than one dimension – such as Position or Scale – all properties are wiggled independently"; wiggle "randomizes itself, depending on the 'index' of the layer". — [ProVideo Coalition, Wiggle](https://www.provideocoalition.com/dmoe9_wiggle/)
- iExpressions' Wiggle family adds the variants users keep asking for: Directional (angle), Looping ("ends at its starting position on the last frame"), One Side, Separate (per-axis freq/amp), Temporal, Wave; fading is done by linking amplitude to a keyframed slider. — [iExpressions docs mirror](https://raw.githubusercontent.com/Amal-David/docingest/main/server/storage/docs/docs.mamoworld.com/documentation_2026-09-18T13:25:45.115Z.md)
- Duik's Wiggle automation differs from native `wiggle()` by animatable frequency, built-in loop duration (defaults to comp duration), per-axis/per-channel amplitude, "Link dimensions" for scale, and a random seed that keeps motion stable when layers are reordered or copied. — [Duik Wiggle docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/guide/automation/wiggle.md)

**Velocity-driven squash/stretch and rotation-from-velocity**
- The reference exposes `velocity` (tangent vector for spatial properties), `speed`, `speedAtTime` and `velocityAtTime` which is what these expressions read. — [docsforadobe property reference](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)

### Inferences
- **Seekability:** the inertial bounce, overshoot, gravity bounce, delay chain, wiggle, temporalWiggle, smooth and loopOut families are all PURE(t): each frame is computed from `time`, the keyframe list and static sliders, with `velocityAtTime`/`valueAtTime` being lookups into the keyframe curve, not into earlier *outputs*. The `t < 1` guard and Ebberts' "few seconds" cap exist only to avoid `exp(decay*t)` overflowing, not because the math is stateful.
- **Cost model, not state, is what makes users bake:** a delay chain of depth N evaluates N upstream expressions per frame; `smooth()` costs `samples ×` the upstream cost; `temporalWiggle` costs one extra upstream evaluation; motion blur multiplies all of this per blur sample. A native engine that memoises property evaluation per (property, time) removes the reason people bake these.
- **The gravity bounce is piecewise closed-form:** the `while (tNext < t)` loop walks bounce segments up to `nMax`, so cost is O(bounces) and it is still PURE(t); a native "Bounce" settle type should expose Elasticity, Gravity and Max bounces exactly like the expression.
- **Native feature implied:** a per-keyframe (or per-property) "Settle" modifier with types Overshoot (damped sine launched at arrival velocity; Amplitude/Frequency/Decay), Bounce (elasticity/gravity/count) and Spring (mass/stiffness/damping, keyframes as targets as in eSpring/iExpressions spring systems), plus a "Follow" modifier (source property + delay seconds/frames + per-index stagger) and a "Wiggle" modifier with seed, loop length, per-axis amplitude and dimension linking. All are expressible as pure functions of time.
- **Spring interpolation with chained targets is still PURE(t)** if each segment's initial conditions (value and velocity at the previous target's switch time) are computed analytically from the previous segment; eSpring's claim that it "can animate correctly out of in-progress animations" implies exactly this construction (unverified).
- The `index`-based delay (`delay * (index-1)`) is the AE idiom a "stagger by layer order" control should replace; users today must keep layer order and delay in sync by hand.

## Key question 2 — Scripts and plugins that package these behaviours (existence, controls, invocation, price, praise/complaints, seekability)

### Takeaway
The AE ecosystem splits cleanly into (a) expression-writers that keep the result live and tunable (iExpressions, Ease and Wizz, Mt. Mograph Motion's Excite/Jump/Delay, Overlap, AutoSway, EZ Inertia, Elast-o-matic, Duik Kleaner) — all PURE(t) unless they simulate history — and (b) keyframe-writers that give editable Graph-Editor output at the cost of re-running the tool after every change (Squash & Stretch, Easy Bounce, Newton, Flow's bezier presets, Dojo Shifter staggers). Several tools the brief named could not be verified to exist (Dojo Bounce, Bounce Pro, Boombox, a Mister Horse "Squash & Stretch").

## Key question 3 — Baking: Convert Expression to Keyframes, Smoother, keyframe-reduction scripts, and why users bake

### Takeaway
AE's native bake writes one keyframe on every frame and disables (but keeps) the expression; everything else in this space exists to (a) reduce that key count (Smart Baker, Easy Bake, Duik's smart/precise modes), (b) make it reversible (Unbake), or (c) do it in bulk for Lottie hand-off and render performance.

### Cited Findings
- Native behaviour: "After Effects can bake the expressions to keyframes for you, with the Animation ▶ Keyframe Assistant ▶ Convert Expression to Keyframes menu entry. This creates one keyframe per frame, then deactivates the expression." — [Duik performance docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/advanced/performance.md)
- Motivation and trade-off from an expression-performance thread: Convert Expression to Keyframes "calculates the expression once and saves the results, so nothing is recalculated at render time. The trade-off is that the bounce no longer updates if you change its settings." — [Creative COW: tips to optimize your expressions](https://creativecow.net/forums/thread/tips-to-optimize-your-expressions-which-expressi/)
- The key-count complaint: AE "bakes the values every single frame – resulting in a vast quantity of keyframes, even when the layer in question didn't move"; Jake & Dan's free Smart Baker "detects straight linear interpolation and motionless gaps when baking, so it skips keys that add nothing". — [lesterbanks: Smart Baker](https://lesterbanks.com/2011/05/smart-baker-for-after-effects/)
- Ebberts' trick to bake *plain keyframed* animation (e.g., before smoothing): add an expression that simply reads `value`, then run Convert Expression to Keyframes. — [Adobe Community: expression to keyframes and smooth via script](https://community.adobe.com/questions-529/can-i-do-expression-to-keyframes-and-smooth-via-script-31156)
- Easy Bake (Khanyu & Zack Lovatt, aescripts): "converts expressions to keyframes faster, simpler and with more control", "will prune away any redundant keys", bakes "your whole project and all the nested precomps", and offers "Surgically Undo" per property; forum reports of a hang in CC 2015.3 and an invisible baked layer. — [lesterbanks on Easy Bake](https://lesterbanks.com/?p=41621); [aescripts Easy Bake discussion](https://aescripts.com/forums/discussion/1265/easy-bake); [Toolfarm Easy Bake](https://www.toolfarm.com/?p=69020)
- Bake Expressions (AEJuice): "restore all expressions in 1 click" via Unbake; batch "your entire project, selected comps, active comp, selected layers, or properties". — [AEJuice Bake Expressions](https://aejuice.com/product/bake-expressions)
- Duik's bake tool offers "two better ways": Smart mode "creates an animation as close as possible to the result of the expression, using just a few Bézier keyframes", Precise mode "creates an animation with as much keyframes as needed for a perfect match" (still fewer than AE's native). — [Duik performance docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/advanced/performance.md)
- AutoSway's Bake writes the sway to keyframes on the control layer "which reduces the calculation time required for Expressions", with Unbake to return to the live state. — [Toolfarm AutoSway](https://www.toolfarm.com/?p=31131)
- Newton has no separate bake step because the simulation is only ever delivered as keyframes. — [aescripts Newton](https://aescripts.com/newton/?aff=50)
- Lottie's docs give the export reason: "you can pre-bake expressions into keyframes before export by using Convert expression to keyframes feature of After Effects, or any baking plugin"; bodymovin adds a "Convert expressions to keyframes" export option and a `// lottie:bake` comment to bake a single expression while leaving the AE project unmodified. — [airbnb/lottie web.md](https://github.com/airbnb/lottie/blob/master/web.md); [lottie-web wiki: Expressions](https://github.com/airbnb/lottie-web/wiki/Expressions)
- Baked wiggle will not match the original: the bodymovin developer says "it's difficult to simulate wiggle and it would never work exactly the same since I don't have AE's random seed". — [Webflow forum thread](https://forum.webflow.com/t/lottie-ae-wiggle-effect-bodymovin-oh-my/100067)
- Motion blur multiplies expression cost per blur sample, which is one of the practical triggers for baking. — [Adobe Community thread 12585183](https://community.adobe.com/t5/after-effects-discussions/sourcerectattime-expression-causing-major-performance-issues-with-motionblur/m-p/12585183)
- Expression-performance guidance from a long-running tips thread: avoid `valueAtTime()` loops over earlier comp time, avoid deep layer-reference chains, use conditionals to skip expensive branches, and bake when "the times get ridiculous". — [Creative COW: tips to optimize your expressions](https://creativecow.net/forums/thread/tips-to-optimize-your-expressions-which-expressi/)
- A 2026 open-source AE-class editor documents its own bake as "Like Convert Expression to Keyframes, but it preserves keyframes outside the baked range and never deletes a hand-written expression, it just disables it" and lists "After Effects has a Smoother and roving keyframes" as the baseline it rolls into one smoothing pass. — [rebound tool-meta.js](https://github.com/meszmate/rebound)

### Inferences
- Users bake for exactly four reasons, all stated in sources: render/scrub performance (per-frame and per-blur-sample evaluation), Lottie/bodymovin export (native players run no expressions), editability in the Graph Editor (keyframe tools only see keys), and portability/hand-off to people without the plugin.
- The recurring pain is the one-key-per-frame output; the market answer is curve fitting (Duik "smart", Easy Bake pruning, Smart Baker linear/static detection). A native engine whose procedural modifiers are PURE(t) can export by sampling and curve-fitting on demand, and can keep the modifier live internally, which removes the Unbake problem entirely.
- "Convert Expression to Keyframes" semantics worth copying exactly: keyframes replace the property's keys over the layer's in→out range, the expression is disabled not deleted, so re-enabling it restores the live behaviour.

### Gaps
- Adobe's own help page for Convert Expression to Keyframes and for The Smoother (tolerance parameter, spatial/temporal modes) could not be fetched; the native description above comes from Duik's docs and forum summaries. No source was found that documents Smoother's tolerance units.
- No source on whether AE's bake samples at comp frame rate or layer time when time-remapped/stretched.
- Easy Bake current price/version and Bake Expressions price not found.

## Key question 4 — How educators teach overlapping action / follow-through in AE (offset children, delay chains, squash on impact, settle after arrival, typical values)

### Takeaway
The teaching consensus is: animate the root, let children lag by a few frames (by offsetting their keyframes, by `valueAtTime(time - delay)`, or by a tool like Duik/Overlap), add a velocity-launched settle (overshoot) at arrival and a squash on impact, and tune three numbers — delay frames, overshoot amplitude, decay. Only community-written pages give numeric ranges (e.g., 4–8 frames of continued motion for secondary elements), and the educator sites themselves were not fetchable in this session.

### Cited Findings
- School of Motion has a free "Animation 101: Follow-Through in After Effects" lesson (Joey Korenman) covering "follow-through, or overlapping action", using the free Duik plugin and a method "that doesn't rely on artwork split into separate layers", and a second lesson "How to Create Automatic Follow Through in After Effects" that uses "a very simple expression to get automatic follow though on a lot of your animations". — [SoM follow-through article](https://www.schoolofmotion.com/blog/animation-tricks-follow-through-after-effects); [SoM automatic follow-through lesson](https://www.schoolofmotion.com/training/viewer/automatic-follow-through-after-effects)
- School of Motion also publishes a bounce-expression explainer (the Ebberts inertial expression) and an animated-trails-with-expressions article. — [SoM bounce expression](https://schoolofmotion.com/blog/after-effects-bounce-expression); [SoM animated trails](https://www.schoolofmotion.com/blog/animated-trails-expressions-after-effects)
- lesterbanks catalogues "various methods for overshooting animation" (2014) and later "easily create bounce and overshoot using Motion 3" (2020). — [lesterbanks 2014](https://lesterbanks.com/2014/01/various-methods-overshooting-animation-effects/); [lesterbanks 2020](https://lesterbanks.com/2020/11/easily-create-bounce-and-overshoot-using-motion-3/)
- Mt. Mograph's tutorial frames the manual method as adding a keyframe past the end value or shaping Bezier handles, and names the Ebberts expression as the procedural route. — [Mt. Mograph blog](https://mtmograph.com/blogs/tools/the-bounce-and-overshoot-animation-trick-every-motion-designer-should-know)
- Conceptual distinction used in tutorials: "Follow through is when the main body stops and appendages keep moving from momentum before they settle. Overlapping action is the separate idea that parts move at different rates throughout the motion". — [playbooks.com animation-principles page (community-written)](https://playbooks.com/skills/dylantarre/animation-principles/follow-through-overlapping)
- Numeric rules of thumb (community-written, low authority): root first, "primary extensions with a slight delay, secondary extensions with more delay, and tertiary elements like hair or cloth with the most drag"; secondary elements continue "4-8 frames past the primary stop"; "ease-out curves with a slight overshoot and a possible small reverse overshoot"; implement with keyframe offsets or `valueAtTime(time - n*frameDuration)`. — [playbooks.com animation-principles page](https://playbooks.com/skills/dylantarre/animation-principles/follow-through-overlapping)
- Duik's Kleaner encodes the same recipe as presets: anticipation before the move, overlap/drag for spatial properties, follow-through oscillation or bounce after the last key, soft-body lag for pins; its advice is to time with linear keyframes "and let the Kleaner handle the rest". — [Duik Kleaner docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/guide/automation/kleaner.md)
- Duik's own guidance on when *not* to automate: "animating hanging hairs or the antenna of a car is quick and easy with a few keyframes", reserving simulation for cases that need it. — [Duik performance docs](https://github.com/RxLaboratory/Duik/blob/master/src-docs/docs/advanced/performance.md)
- Squash on impact as a packaged behaviour: Easy Bounce "adds squash"; Squash & Stretch ships 60+ keyframe behaviours. — [aescripts Easy Bounce](https://aescripts.com/forums/discussion/2326/easy-bounce); [aescripts Squash & Stretch](https://aescripts.com/after-effects/animation/assistant/squash-and-stretch)
- ECAbrams (Evan Abrams) teaches the valueAtTime delay/trail pattern with a downloadable project (CC 2014+). — [ECAbrams Gumroad](https://ecabrams.gumroad.com/l/Vfagk)

### Inferences
- The educators' three-number mental model (delay in frames, overshoot amount, decay/duration) maps one-to-one onto the slider sets every tool exposes; a native UI should label them in those terms (frames, % overshoot, settle time) rather than amp/freq/decay.
- "Offset child layers" and "delay chains" are the same operation (sample the parent's motion at `t - d`); a native "Follow" with per-child delay plus optional spring makes layer-order hacks unnecessary.
- Because Kleaner snaps follow-through contacts to whole frames and uses an asymmetric (Gaussian) ease, a native settle should allow frame-snapped contacts and asymmetric ease as options; both are deliberate animation choices, not physics.

- School of Motion, Jake in Motion (Jake Bartlett), Ben Marriott, Ukramedia (beyond the preset), ECAbrams (beyond the project listing), Motion Design School, Animade and Ordinary Folk pages were blocked or not surfaced; no quotes of their specific parameter recommendations could be captured. No Ben Marriott follow-through tutorial was found at all.
- No authoritative educator source for "overshoot percentage" or "frames of delay" numbers; the only numbers found are from a community page.

## Key question 5 — Lottie/bodymovin constraints: what survives export, what designers bake, and Lottie-native replacements

### Takeaway
Expressions survive only in lottie-web (a JavaScript subset, no `wiggle`/`velocityAtTime`/`linear`), and are unsupported on Android, iOS and Windows; effects are almost entirely unsupported outside the web SVG renderer. So motion designers bake bounce/overshoot/wiggle/delay to keyframes before export, and LottieFiles now offers a native Spring Curve, graph editor and physics simulator to produce the same looks as keyframes.

### Cited Findings
- Official support table: Expressions — Android ⛔, iOS (Core Animation) ⛔, iOS (Main Thread) ⛔, Windows ⛔, Web SVG/Canvas/HTML 👍; Time remap supported everywhere except Windows; Auto Orient web only; effects Fill/Stroke/Tint/Tritone web only, Gaussian blur and Drop Shadow Android 4.1+ (and iOS for drop shadow); Luma mattes unsupported on native. — [airbnb/lottie supported-features.md](https://github.com/airbnb/lottie/blob/master/supported-features.md)
- Web renderer detail: expressions "are similar to javascript but not quite the same… I use Esprima and Escodegen. A subset of expressions is supported"; native functions "linear, velocityAtTime and wiggle are not supported"; this "causes issues when exporting Duik's forward kinematics" (lottie-web issue 1661); workaround "pre-bake expressions into keyframes before export… or any baking plugin". — [airbnb/lottie web.md](https://github.com/airbnb/lottie/blob/master/web.md)

### Inferences
- For a Lottie-targeting user the decisive constraint is the native players: even the subset lottie-web runs is useless for iOS/Android, so the only portable form of overlap/overshoot/wiggle is keyframes. A native app that keeps modifiers PURE(t) can export by sampling to keyframes with curve-fitting — exactly what Duik's "smart" bake and LottieFiles' physics simulator do.
- LottieFiles' Spring Curve + Physics Simulator is the clearest signal of what "built-in" looks like for this audience: spring as an *easing type* on a keyframe pair, and physics as a keyframe generator, both producing plain keyframes in the JSON.
- Because bodymovin wraps expressions in try/catch returning `value`, a web Lottie silently degrades to the keyframed value when an expression fails; baking is the only way to guarantee identical output across players.
