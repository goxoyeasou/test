# Beyond manual keyframes: springs, procedural motion, recording/fitting, easing libraries, animation-principle presets, AI assistance, and keyframe smoothing

Scope note for the report writer: these notes cover the alternatives to hand-tuned bezier keyframes and how each can coexist with a deterministic, seekable keyframe timeline (play/seek/export must agree). For every method I flag whether it is (a) a pure function of time (directly seekable), (b) a stateful simulation that must be baked/cached, or (c) a transform over existing keys. Research constraints: many primary docs (Figma help/blog, Rive docs, Cavalry docs, Adobe HelpX, GSAP docs, Blender manual, easings.net, W3C, motion.dev, remotion.dev) were blocked by the network proxy, so for those products I relied on their open-source runtime/source code on GitHub (which is often a better primary source for formulas) and on search-result excerpts; the gaps sections say where this left holes. Current as of October 2026.

## Key question 1: Spring and physics interpolation (Apple, Motion/Framer, React Spring, Rive, Figma, Principle) — closed forms, seek, duration-based springs, interruption

### Takeaway
Every major shipping spring is a damped harmonic oscillator; Apple (SwiftUI/UIKit/Core Animation), Motion/Framer Motion, Flutter's engine and Remotion evaluate it in closed form so the value at any time t is a pure function (seekable, export-safe), while React Spring and Anime.js integrate numerically (stateful, must be re-simulated from the start to seek). "Duration-based" springs are achieved by three different tricks (Apple: make the duration the oscillation period and call it "perceptual duration"; Motion: solve for the stiffness whose decay envelope drops below 0.001 at T; Remotion: measure the natural settle time and rescale time), and interruption is handled by restarting the closed form with the current position and velocity as initial conditions.

### Cited Findings

**The model, in Apple's words (WWDC23 "Animate with springs")**
- SwiftUI's spring takes "just 2 parameters: duration and bounce"; bounce runs "from -1.0 to 1.0" (bouncy springs have bounce values up to 100%, flattened springs between 0 and -100%); and "the duration parameter is a perceptual duration that is chosen to be predictable and not move around, even as the other parameters of a spring change." — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/)
- The physical mapping shown in the session is `mass = 1`, `stiffness = (2π ÷ duration)^2`, with damping derived from bounce (the session's slide as captured reads `damping = 1 − 4π·bounce ÷ duration` for bounce ≥ 0 and `4π ÷ (duration + 4π·bounce)` for bounce < 0). — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Apple's API reference example gives `Spring(duration: 0.5, bounce: 0.3)` → `(mass, stiffness, damping) = (1.0, 157.9, 17.6)`. — [Apple SwiftUI Spring docs](https://developer.apple.com/documentation/swiftui/spring)
- Three regimes are named: bounce > 0 "underdamped / bouncy" (overshoots and oscillates), bounce = 0 "critically damped / smooth", bounce < 0 "overdamped / flattened". The session describes the curves verbally: bounce 100% is "exactly the behavior of a cosine wave… the duration corresponds exactly to the period of the curve"; underdamped is "a damped cosine or sine wave" (cosine × exponential decay); critically damped is "the basic equation of a line… multiplied by the same exponential"; overdamped uses "two exponential functions added together instead of a line." — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Seek/determinism: the `Spring` type is evaluated directly as a function of time: `mySpring.value(target: 1, time: time)` and `mySpring.velocity(target: 1, time: time)`; custom animations call `spring.value(target:initialVelocity:time:)`. Apple says this is useful "for simulations, or to get values for charts." — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/); API: `value(target:initialVelocity:time:)` "Calculates the value of the spring at a given time given a target amount of change", `velocity(…)`, `settlingDuration(target:initialVelocity:epsilon:)` "The estimated duration required for the spring system to be considered at rest", plus a stateful `update(value:velocity:target:deltaTime:)` and `force(…)` for integrators. — [Apple SwiftUI Spring docs](https://developer.apple.com/documentation/swiftui/spring)
- Apple also exposes `init(response:dampingRatio:)` ("response: the stiffness of the spring, defined as an approximate duration in seconds"; "dampingRatio: the amount of drag applied, as a fraction of the amount needed to produce critical damping") and `init(settlingDuration:dampingRatio:epsilon:)`. — [Apple SwiftUI Spring docs](https://developer.apple.com/documentation/swiftui/spring)
- Settling vs perceptual duration: "technically it keeps moving forever, just with smaller and smaller movement"; "That amount of time until a spring animation is finished enough to remove is called the settling duration," which "can be a bit unpredictable," so SwiftUI's completion handler "uses a perceptual duration instead of a settling duration." Core Animation got `CASpringAnimation(perceptualDuration: 0.6, bounce: 0.2)`. — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/)
- Interruption / velocity carry-over: "a spring animation uses the velocity it had when it was retargeted as the initial velocity towards its new destination and this same velocity preservation makes these kind of interruptions feel smooth and natural." SwiftUI "will now automatically track velocities any time a gesture is changing properties," whereas an ease-in-out curve "has no way to represent an initial velocity." With zero initial velocity the cosine term "has to start off pointing downwards to cancel out with the decay and give us our flat start." — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/)

**Motion (formerly Framer Motion / Motion One) — closed-form generator, source-verified**
- Defaults: `duration: 800 // ms`, `bounce: 0.3`, `visualDuration: 0.3 // seconds`, `stiffness: 100`, `damping: 10`, `mass: 1.0`; rest thresholds `restSpeed` 2 (0.01 "granular") and `restDelta` 0.5 (0.005 granular), with "granular" chosen when `Math.abs(s.delta) < 5`. A spring is "time-defined" when no stiffness/damping/mass is given and duration or bounce is. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts)
- Core quantities: `dampingRatio = damping / (2 * Math.sqrt(stiffness * mass))`, `undampedAngularFreq = millisecondsToSeconds(Math.sqrt(stiffness / mass))`, `decay = dampingRatio * undampedAngularFreq`. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts)
- Closed forms in the code (Δ = initial delta to target, v = initial velocity):
  - ζ < 1: `target - env * (A * sin + delta * cos)` with `env = exp(-decay * t)`, `sin = sin(angularFreq * t)`, `cos = cos(angularFreq * t)` (angularFreq is the damped frequency).
  - ζ = 1: `target - exp(-undampedAngularFreq * t) * (delta + (velocity + undampedAngularFreq * delta) * t)`.
  - ζ > 1: `target - S * decayAt(slow, t) - F * decayAt(fast, t)` with `slow = decay - dampedAngularFreq`, `fast = decay + dampedAngularFreq`.
  Velocity has matching closed forms (`env * (sinC * sin + cosC * cos)` etc.), and the generator exposes `velocity: (t) => …`. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts)
- Overdamped numerics: the older `sinh/cosh` form overflowed, so inputs were capped at 300, and that cap made slow overdamped springs "visibly snap to the target mid-animation" (issue #1207: at stiffness 4, damping 35, mass 0.5, range 0→1000 the value jumps from ≈625 to ≈989 between 8594 ms and 8700 ms). The fix is the two-exponential form: with D = initial delta, V = v₀ + ζω₀D, ω_d = ω₀√(ζ²−1): `λ_slow = −ω₀/(ζ+√(ζ²−1))` (avoids cancellation), `λ_fast = −ω₀(ζ+√(ζ²−1))`, `c_slow = (V + ω_d·D)/(2ω_d)`, `c_fast = D − c_slow`, `x(t) = target − (c_slow·e^{λ_slow t} + c_fast·e^{λ_fast t})`, `v(t) = −(c_slow·λ_slow·e^{λ_slow t} + c_fast·λ_fast·e^{λ_fast t})`. — [Motion plan 031](https://github.com/motiondivision/motion/blob/main/plans/031-overdamped-spring-exponential-form.md)
- Done condition: when not resolved from a duration, done when `Math.abs(currentVelocity) <= restSpeed && Math.abs(target - current) <= restDelta`; when resolved from duration, `state.done = t >= duration`. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts)
- Duration-based springs (`findSpring`): damping ratio `ζ = clamp(minDamping, maxDamping, 1 − bounce)`; for ζ < 1 `ω = ln(ζ / (safeMin · √(1 − ζ²))) / (ζT)` with `safeMin = 0.001`; for ζ = 1 `ω = 9.2334134764516 / T`; then `stiffness = ω²·mass`, `damping = ζ·2·√(mass·stiffness)`. I.e. Motion's "duration" is the time at which the oscillation envelope `(ζ/√(1−ζ²))·e^{−ζωT}` (or `e^{−u}(u+1)` when critically damped) falls below 0.001; the previous implementation did the same with 12 Newton–Raphson iterations. — [Motion plan 033](https://github.com/motiondivision/motion/blob/main/plans/033-findspring-closed-form.md)
- `visualDuration` is a different notion: the code starts from `root = (2π) / (visualDuration * 1.2)` (the rest of the branch was truncated in my fetch), explicit stiffness/damping/mass override it, and the plan gives the example `spring({ keyframes: [0, 1], visualDuration: 0.5, bounce: 0 })` settling at 900 ms vs 1100 ms for default physics — i.e. the input is a "how long it looks" target, not the settle time. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts); [Motion plan 030](https://github.com/motiondivision/motion/blob/main/plans/030-spring-visual-duration-without-bounce.md); Motion's docs describe visual duration as "a time, set in seconds, that the animation will take to visually appear to reach its target" with the bounce playing out after that point. — [motion.dev spring docs (via search excerpt)](https://motion.dev/dom/spring)
- Velocity carry-over in Motion: physics-defined springs inherit velocity (`velocity: inheritVelocity(options.velocity || 0)`, `isTimeDefined ? 0 : -millisecondsToSeconds(velocity)`), but "Time-defined springs ignore inherited velocity" (velocity forced to 0), because the duration/bounce → stiffness solve assumes v₀ = 0. — [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts); [Motion plan 033](https://github.com/motiondivision/motion/blob/main/plans/033-findspring-closed-form.md)
- Baking a spring to a fixed-duration curve: `calcGeneratorDuration` samples the generator with `timeStep = 50` ms until `state.done` or `maxGeneratorDuration = 20_000` ms (returns `Infinity` at the cap); `toString()` then returns `"<ms> linear(...)"`, i.e. a pre-sampled CSS `linear()` easing of fixed length for WAAPI/CSS playback. — [motion-dom calc-duration.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/utils/calc-duration.ts); [motion-dom spring.ts](https://github.com/motiondivision/motion/blob/main/packages/motion-dom/src/animation/generators/spring.ts)
- Motion's docs warn that a spring with `damping: 0` "will run forever," so a sampling loop needs a stop condition. — [motion.dev (search excerpt)](https://motion.dev/dom/spring)

**React Spring — numeric integration (stateful)**
- `SpringValue.advance()` integrates with fixed 1 ms semi-implicit Euler steps: `const step = 1 // 1ms; const numSteps = Math.ceil(dt / step)`, then per step `springForce = -tension * 0.000001 * (position - to)`, `dampingForce = -friction * 0.001 * velocity`, `acceleration = (springForce + dampingForce) / mass`, `velocity += acceleration * step`, `position += velocity * step`. Precision default `from == to ? 0.005 : min(1, |to - from| * 0.001)`; `restVelocity = config.restVelocity || precision / 10`; `clamp` sets `bounceFactor = 0` and on crossing the target `velocity = -velocity * bounceFactor; position = to`. `duration` + `easing` configs are closed-form (`position = from + easing(p) * (to - from)`), and `decay` is closed-form exponential (`e = exp(-(1 - decay) * elapsed)`, `position = from + (v0 / (1 - decay)) * (1 - e)`). — [react-spring SpringValue.ts](https://github.com/pmndrs/react-spring/blob/main/packages/core/src/SpringValue.ts)
- Facebook's Rebound (the ancestor of tension/friction APIs): "low friction and high tension will create an animation that moves rapidly and oscillates many times before coming to a rest." — [Facebook Engineering, Rebound](https://engineering.fb.com/2013/12/10/android/under-the-hood-building-and-open-sourcing-the-rebound-animation-library-for-android/)
- Anime.js's spring solver likewise "simulates the spring in small time steps, checks whether motion has dropped below a rest threshold (0.0005), and requires the spring to stay at rest for 200ms before stopping," capping at 60 s. — [Anime.js spring docs (mirror)](https://www.mintlify.com/juliangarnier/anime/easings/spring)

**Flutter / iOS parity**
- Flutter's engine ships a `spring_animation.h` "based off of a damped harmonic oscillator" that "models the closed form of the second order differential equation" and "match[es] the algorithm used by iOS's CASpringAnimation." — [Flutter engine spring_animation.h](https://flutter.googlesource.com/mirrors/engine/+/HEAD/third_party/spring_animation/spring_animation.h)

**Remotion — spring as a pure function of frame (video renderer)**
- Remotion's `spring({frame, fps, config, durationInFrames, durationRestThreshold, delay, …})` is evaluated per frame; the docs say the spring "is first stretched to the duration that you pass using durationInFrames, if you pass a duration," then reversal and delay are applied; `durationRestThreshold` "only has an effect if durationInFrames is also specified" and e.g. 0.001 "means that after 30 frames, the spring has reached 99.9% of its distance to the end value"; `delay: 25` means "frames 0-24 will return the initial value." — [Remotion spring docs (search excerpt)](https://www.remotion.dev/docs/spring)
- `measureSpring()` computes the settle length; "theoretically, a spring animation never ends… Instead, a threshold defines when the animation is considered done"; the default threshold is 0.005 (0.01 = within 1% of target). — [Remotion measure-spring docs (search excerpt)](https://v3.remotion.dev/docs/measure-spring)

**Rive — "elastic" interpolation as a keyframe interpolation mode**
- Rive's keyframe interpolation types are Linear (default), Cubic (two draggable handles), Hold, and Elastic, which "goes past the target value, oscillates, and then settles on it" with two controls: Amplitude (overshoot size) and Period (how fast the oscillation dies down); set in the Interpolation panel or Graph Editor. — [Rive interpolation docs](https://rive.app/docs/editor/animate-mode/interpolation-easing); [community copy](https://rive.app/community/doc/interpolation-easing/docP9A6iGEsI)
- Runtime source: `ElasticEase(amplitude, period)` precomputes `m_s = period/4` when amplitude < 1, else `period/(2π) · asin(1/amplitude)`; `easeOut(f)` returns a decaying sine offset by 1 with decay `2^(−10·t)`; `easeIn(f)` uses `t = f − 1` and returns `−(amp · 2^(10t) · sin(−t − m_s …))`; `easeInOut` maps f to t ∈ [−1, 1] and uses the easeIn form ×½ for t < 0 and the easeOut form ×½ + 1 otherwise. Rive's twist: `computeActualAmplitude(t)` linearly blends the amplitude from 1 toward the set amplitude inside `|t| < |m_s|` when amplitude < 1 (comment: "s… the effective starting period used to align the decaying sine with the keyframe"). — [rive-runtime elastic_ease.cpp](https://github.com/rive-app/rive-runtime/blob/main/src/animation/elastic_ease.cpp)
- `ElasticInterpolator::transform(factor)` switches on easing type (in/out/inOut) and `transformValue` is `valueFrom + (valueTo − valueFrom) * transform(factor)`; defaults are amplitude 1.0, period 0.5 (period 0 falls back to 0.5). This is a pure function of normalized segment time. — [rive-runtime elastic_interpolator.cpp](https://github.com/rive-app/rive-runtime/blob/main/src/animation/elastic_interpolator.cpp)

### Inferences
- Consistency check on Apple's mapping: the WWDC slide text as captured ("damping = 1 − 4π·bounce ÷ duration") cannot be right as written (it goes negative for ordinary inputs), but Apple's documented example (duration 0.5, bounce 0.3 → stiffness 157.9, damping 17.6) is reproduced exactly by `ω₀ = 2π/duration`, `ζ = 1 − bounce`, `stiffness = ω₀²` (=157.91) and `damping = 2ζω₀ = 4π(1 − bounce)/duration` (=17.59). So for bounce ≥ 0 the robust reading is **ζ = 1 − bounce** with the period fixed by duration; Motion's `findSpring` uses the same `ζ = 1 − bounce` convention. (Treat the bounce < 0 branch as unverified; see Gaps.)
- Why closed forms give deterministic seek: with initial delta Δ, initial velocity v₀ and parameters (ζ, ω₀), x(t) is an explicit expression in t (Motion's `resolveSpring(t)`, Apple's `value(target:initialVelocity:time:)`, Remotion's `spring({frame})`). Any frame can be evaluated independently, in any order, on any thread, which is exactly the "pure function of time" property your core needs. Numeric integrators (React Spring, Anime.js) are deterministic only if you replay from t=0 with the same step size; random access requires re-simulating, which is why they are a poor fit for seek/export unless baked.
- Two different meanings of "duration" exist and your UI should pick one explicitly: (1) Apple's perceptual duration (= 2π/ω₀, so the first overshoot peak lands near duration/2 and motion looks "done" at ~duration even though it mathematically settles later); (2) Motion's/Remotion's settle-based duration (solve or rescale so the envelope is below a threshold at T). The settle-based one guarantees the value is within ε of the target at T, which is the stronger guarantee for a timeline where the next keyframe begins at T.
- Making a spring hit the target exactly at T on a timeline: options that keep it a pure function are (a) Motion's `findSpring` solve (envelope ≤ 0.001 at T), (b) Remotion's time-rescale `x(t·t_settle/T)` after measuring t_settle for a threshold, (c) evaluate x(t) for t < T and clamp to target for t ≥ T (cheapest; a discontinuity of at most ε), or (d) blend `x(t)` toward the target with a short ease over the last few percent of T. All are seekable. Any of them can also be baked to dense keys at the composition frame rate for export to formats without springs.
- Interruption on a deterministic timeline: the UI event "retarget at time t_i" can be stored as a new spring segment whose initial conditions are `(x_prev(t_i), v_prev(t_i))` from the previous closed form (Apple's "velocity it had when it was retargeted"). The whole sequence remains a pure function of time as long as the retarget times/targets are stored as data; nothing needs wall-clock state. Note Motion's caveat: if the user specified the spring by duration/bounce, carrying velocity breaks the duration solve (Motion zeroes it); you would need to re-solve stiffness with v₀ ≠ 0 (root find) or accept a slightly different settle time.
- As an interpolation mode between keys: Rive shows the pattern — treat "elastic/spring" like "cubic bezier": the segment from key A (t₀, v₀) to key B (t₁, v₁) is evaluated with `v₀ + (v₁ − v₀)·f(u)`, u = (t − t₀)/(t₁ − t₀). A physically parameterised spring can be exposed the same way if you store (ζ or bounce, and either perceptual or settle duration) per segment and derive ω₀ from the segment length. The segment's end derivative is then ≈0 (unless you also carry velocity into the next segment), which is fine for UI motion but you should expose "continue velocity into next key" as an option.
- As a layer on top of keys: Cavalry's experimental "Spring" behaviour (see KQ2) is the other integration pattern — the spring tracks the keyframed value as a moving target (a second-order filter). That is inherently a simulation (the output at t depends on the whole input history), so it must be baked/cached per frame for seek; it can still be deterministic if the integrator step is fixed to the composition frame rate and always starts from the comp start.

- Figma's actual spring solver, settling threshold, and the numeric preset values for Gentle/Quick/Bouncy/Slow were not obtainable: figma.com, help.figma.com and forum.figma.com were blocked; only search excerpts were available.
- Principle: no primary documentation on Principle's spring/driver model surfaced in search; I could not confirm its parameter names (tension/friction vs. others).

## Key question 2: Procedural motion (After Effects expressions, Cavalry behaviours, Rive state machines/blend states, Jitter/Fable presets) — determinism and seekability

### Takeaway
After Effects expressions are the reference model for "procedural but seekable": every expression is a function evaluated at the current time with explicit time-sampling helpers (`valueAtTime`, `wiggle(…, t)`, `loopOut`, `smooth`), so they compose with keyframes as a layer on top; Cavalry generalises this into stackable Behaviour nodes (Oscillator, Stagger, Noise, Spring…) and Keyframe Layers that add/overwrite keyframed curves with a Strength, while Rive's state machines and blend states are input-driven runtime constructs (not functions of timeline time) and belong to interactive playback rather than a seekable timeline.

### Cited Findings

**After Effects expressions (property methods)**
- `wiggle(freq, amp, octaves=1, amp_mult=0.5, t=time)` "Randomly shakes (wiggles) the value of the property." `freq` is "Frequency, in wiggles per second"; `amp` "Amplitude, in units of the property to which it is applied"; `octaves` "Number of octaves of noise to add together"; `amp_mult` "Amount that amp is multiplied by for each octave"; `t` sets the base start time "if you want the output to be a wiggle of the property value sampled at a different time." — [AE expression reference (docsforadobe mirror), property.md](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `temporalWiggle(freq, amp, octaves, amp_mult, t)` "Samples the property at a wiggled time" and "the property it samples must be animated, because the function alters only the time of sampling, not the value." — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `smooth(width=0.2, samples=5, t=time)` "Smooths the property values over time, converting large, brief deviations…"; `width` is "The range of time (in seconds) over which the filter is averaged"; `samples` should be odd "so that the value at the current time is included in the average." — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `loopIn/loopOut(type="cycle", numKeyframes=0)`: `"cycle"` "Repeats the specified segment"; `"pingpong"` alternates forward/backward; `"offset"` repeats "offsetting each cycle by the property's start-to-end value difference, multiplied by the loop count"; `"continue"` "Does not repeat the segment" but keeps animating "based on the velocity at the first or last keyframe." `loopOutDuration(type, duration)` loops a segment measured in composition seconds backward from the last keyframe. — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- `valueAtTime(t)` "Returns the value of a property at the specified time, in seconds"; `velocityAtTime(t)` "Returns the temporal velocity value at the specified time"; `speedAtTime(t)` "Returns the spatial speed value." The page does not state how `wiggle`'s randomness is seeded. — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)

**Cavalry — Behaviours, Stagger, Oscillator, Spring, Keyframe Layers**

- Oscillator "deforms and affects Shapes with trigonometric wave patterns," offers sine/cosine/tangent and square/triangle/sawtooth styles, and has a Stagger setting: "When used with a Duplicator this will stagger the movement in time across duplicates." ### Inferences
- Determinism recipe (what AE and Cavalry imply, and what your core should enforce): a procedural operator is seekable iff it is written as `f(t, params, keyframes)` with no hidden per-frame state. AE's API makes this explicit: `wiggle`'s `t` parameter, `valueAtTime(t)`, `loopOut` (re-maps t into the keyframed range), `smooth` (samples the property at a set of times around t). Noise-based operators (wiggle, Cavalry Noise/Oscillator) are seekable when the noise is a hash/gradient noise of (t, seed) rather than an accumulated random walk. Operators that are *filters over history* (AE `smooth` is fine because it samples a finite window around t; a spring-follow like Cavalry's Spring behaviour is not, because it integrates from the start) need either a finite window definition or baking/caching from comp start.
- Composition order used by these tools: keyframes → expression/behaviour layer (modifies the keyframed value: additive, multiplicative, or time-remapping) → output. Cavalry's Keyframe Layers show a useful additional pattern: several keyframe stacks blended by Strength with Normal(add)/Overwrite modes, which is a clean way to let a "procedural layer" or an "AI-generated layer" sit beside hand keys without destroying them.
- Rive-style state machines/blend states are not timeline concepts: their output depends on live inputs and elapsed real time since a transition, so they are not a pure function of timeline time. For a motion-graphics timeline the equivalent is a *blend between two keyframed curves driven by a keyframed or expression-driven weight*, which is seekable (and is what Cavalry's Keyframe Layer Strength does).
- Jitter/Fable "presets" (and Figma Motion's "presets", KQ6) are in practice parameterised keyframe templates (enter/exit/emphasis with a duration and an easing) instantiated onto the timeline; they are therefore already keyframes and trivially seekable. AI-generated "effects" in Jitter are described as editable parameterised effects (see KQ6), which maps to the behaviour-node model.

## Key question 3: Recording motion and fitting keyframes (Motion Sketch, Schneider's algorithm, RDP, least-squares cubic fitting, Blender Clean/Decimate, Maya Simplify, AE Smoother) — error metrics and thresholds

### Takeaway
Recording produces one sample per frame; the shipping reduction tools then either (a) fit piecewise cubic beziers to the samples with a max-error tolerance (Schneider 1990, used by nearly every "fit-curve" library), (b) greedily remove keys whose removal least perturbs the curve (Blender Decimate, RDP-style), or (c) merge keys within a time/value tolerance (Maya Simplify, Blender Clean). The thresholds that ship are small and unit-specific: AE Smoother tolerance in pixels for position, Maya 0.05 s time / 0.01 value tolerance, Blender decimate ratio 0.333 or error margin 0.0, Motion Sketch smoothing 1.

### Cited Findings

**After Effects: Motion Sketch → Smoother**
- Motion Sketch's Smoothing parameter "is enabled by default and set to 1 in the Motion Sketch panel"; raising it before sketching reduces keyframe density. — [Frame.io blog, Motion Sketch](https://blog.frame.io/2023/05/17/quickly-create-complex-motion-paths-in-after-effects/); a user who set Smoothing to zero ended up with a keyframe on every frame. — [Adobe community thread](https://community.adobe.com/t5/after-effects-discussions/motion-sketch-problem/m-p/15177244)
- The Smoother replaces selected keyframes with a sparser set; "The meaning of the Tolerance value changes depending on what type of keyframes you are editing – for example, when you're editing Position keyframes, it will define the number of pixels new Position keyframes are allowed to vary from the original path. Larger Tolerance values result in fewer keyframes and therefore generally smoother animation." It is applied as Spatial (position path in the comp panel) or Temporal (value-over-time). — [ProVideo Coalition, Creating Motion Graphics with AE hidden gems ch. 5](https://www.provideocoalition.com/creating_motion_graphics_with_after_effects_hidden_gems_chapter_5_-_animati/); a tutorial used "a tolerance of about 10… to the spatial path" to remove unnecessary keyframes. — [LinkedIn Learning / Lynda, Working with the Smoother](https://www.lynda.com/After-Effects-tutorials/Working-Smoother/78545/79322-4.html?src=c.r.su)

**Schneider's algorithm (Graphics Gems, 1990) — piecewise cubic bezier fitting with max-error tolerance**
- Entry: tangents at the ends are estimated from neighbouring points (`ComputeLeftTangent`, `ComputeRightTangent`) and `FitCubic(d, 0, nPts-1, tHat1, tHat2, error)` is called with a squared-error tolerance. — [GraphicsGems FitCurves.c](https://github.com/erich666/GraphicsGems/blob/master/gems/FitCurves.c)
- `FitCubic`: two-point case places inner control points at one-third of the chord along the end tangents; otherwise `ChordLengthParameterize` assigns each sample a parameter u ∈ [0,1] by cumulative chord length; `GenerateBezier` solves a 2×2 least-squares system (Cramer's rule) for the tangent scales `alpha_l`, `alpha_r`, falling back to the Wu/Barsky heuristic `segLength/3` when the determinant is ~0 or an alpha < `1e-6·segLength`; `ComputeMaxError` returns the largest squared point-to-curve distance and the index of that point (`splitPoint`). — [GraphicsGems FitCurves.c](https://github.com/erich666/GraphicsGems/blob/master/gems/FitCurves.c)
- Acceptance/iteration: if maxError < error, emit; else if maxError < `iterationError` (the current code sets `iterationError = error * 4.0`, with a comment "fixed issue 23"), run up to `maxIterations = 4` rounds of `Reparameterize` (one Newton–Raphson step per point: `u' = u − f(u)/f'(u)`, f(u) = (Q(u) − P)·Q'(u)) and refit; otherwise split at the max-error point with a center tangent (`ComputeCenterTangent`, negated for the right half) and recurse. — [GraphicsGems FitCurves.c](https://github.com/erich666/GraphicsGems/blob/master/gems/FitCurves.c)
- Ports: `fit-curve` (JS) "Fit one or more cubic Bezier curves to a polyline," taking points and an error tolerance ("The smaller the number - the much closer spline should be"); Python (NumPy) and Dart ports exist. — [fit-curve on npm](https://www.npmjs.com/package/fit-curve); [volkerp/fitCurves](https://github.com/volkerp/fitCurves)

**Ramer–Douglas–Peucker and Visvalingam–Whyatt (polyline simplification)**
- RDP is top-down: measure each intermediate vertex's distance from the chord joining the segment's endpoints, split at the farthest vertex if it exceeds epsilon, recurse; O(n log n) is achievable with dynamic convex hulls; epsilon can be made non-parametric by using the digitisation error as the stop condition. — [Wikipedia, RDP](https://en.wikipedia.org/wiki/Ramer%E2%80%93Douglas%E2%80%93Peucker_algorithm); in ArcGIS terms the tolerance is "the largest perpendicular offset allowed between an original vertex and the simplified line." — [ArcGIS Pro Simplify Line](https://pro.arcgis.com/en/pro-app/3.0/tool-reference/cartography/simplify-line.htm)
- Visvalingam–Whyatt is bottom-up: repeatedly remove the vertex whose triangle with its neighbours has the smallest effective area until the smallest area exceeds a threshold; output is described as "less angular" than RDP's; the thresholds have different units (distance vs area). — [cartagen docs, Visvalingam–Whyatt](https://cartagen.readthedocs.io/en/latest/reference/cartagen.simplify_visvalingam_whyatt.html); [ArcGIS Pro](https://pro.arcgis.com/en/pro-app/3.0/tool-reference/cartography/simplify-line.htm)

**Blender F-curve Decimate and Clean (source-verified)**
- Decimate "removes keyframes that affect the curve shape the least"; mode RATIO ("uses a percentage to set how many keyframes to remove") or ERROR ("uses an allowed deviation from the original path"); `factor` default 0.333333, `remove_error_margin` default 0.0 ("how much the new decimated curve is allowed to deviate from the original"). The 4.2 API describes `factor` as the ratio of remaining keys while 4.4/4.5 describe it as the ratio to remove — the descriptions conflict. — [Blender bpy.ops.graph 4.2](https://docs.blender.org/api/4.2/bpy.ops.graph.html); [Blender bpy.ops.graph 4.5](https://docs.blender.org/api/4.5/bpy.ops.graph.html)
- Implementation: `prepare_for_decimate` converts linear keys to bezier ("Convert to a linear bezt curve to be able to use the decimation algorithm"; handles set to one-third of the distance to each neighbour) and flags unsupported interpolation types to be skipped; `decimate_fcurve_segment` computes `target_fcurve_verts = ceil(bezt_segment_len - selected_len * remove_ratio)` and calls `BKE_curve_decimate_bezt_array(..., resolution 12, error_sq_max, ...)` ("The actual resolution displayed in the viewport is dynamic so we just pick a value that preserves the curve shape"); keys tagged for removal are dropped and survivors reinserted with `insert_bezt_fcurve`. — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc)
- Clean Keyframes: rebuilds the curve keeping only keys whose values differ from the previous kept key or the next key by more than the threshold (`IS_EQT` on time; "only add if values are a considerable distance apart"); with `cleardefault` a curve reduced to a single default-value key is deleted. — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc)

**Maya Simplify Curve**
- Time Tolerance "is the amount (in seconds) that the timing for the keys is averaged when the selected curve is simplified," default 0.05; Value Tolerance "the amount (in your current working units) that the values of the keys are averaged," default 0.01; "the higher the Time Tolerance, the sparser your keys and the less your resulting curve resembles the original curve"; Simplify Method is Classic (keys not on every frame) or Dense Data ("meant for dense sets such as motion capture"). Autodesk: "you may have to experiment with the Value Tolerance and Time Tolerance values." — [Maya 2023 Simplify Curve options](https://help.autodesk.com/cloudhelp/2023/ENU/Maya-Animation/files/GUID-455F76C5-F761-4007-AFFE-E0F80BEFB627.htm); command flags `-timeTolerance` 0.05 s, `-valueTolerance` 0.01, `floatTolerance` 0.05 for float-driven curves. — [Maya simplify command](https://help.autodesk.com/cloudhelp/2016/ENU/Maya-Tech-Docs/Commands/simplify.html)

### Inferences
- Error metric that matches your product: for spatial paths (recorded pointer motion) use Schneider's max perpendicular distance in pixels (that is what AE's spatial Smoother tolerance is, in pixels); for value-vs-time curves use max |value error| in property units plus a time tolerance (Maya's pair), because a bezier value curve must be a function of time (x monotonic), which is a stronger constraint than a 2-D path. Schneider's algorithm needs a small modification for value-vs-time curves: parameterise by time instead of chord length and constrain handle x so the segment stays monotonic in time (CSS cubic-bezier's x₁,x₂ ∈ [0,1] constraint is the same idea).
- Practical defaults implied by the tools: AE users reach for a tolerance around 10 px on sketched paths; Maya's 0.05 s / 0.01 unit; Blender's error margin is expressed in curve units with 0 meaning "lossless"; Motion Sketch's default smoothing of 1 means the raw capture is already lightly filtered before fitting. A sensible UI exposes one slider ("fidelity"), mapped to Schneider's error tolerance in screen pixels for paths and to a percentage of the property's recorded range for value curves, with a live keyframe count.
- Pipeline that gives the best keys: (1) low-pass the recorded samples first (Gaussian/Butterworth, KQ7) to remove jitter, otherwise the fitter spends segments on noise; (2) detect velocity extrema/zero crossings and force split points there (these become the "key poses"; RDP's farthest-point split tends to pick them anyway); (3) Schneider-fit each span with tangents continuous across splits; (4) optionally snap key times to frames. Blender's choice to convert linear keys to bezier with 1/3 handles before decimating shows that the decimation and the refit are separable steps.
- Seekability: fitted keys are ordinary keys, so the result is a pure function of time; keep the raw recording as a hidden "source" so the user can re-fit at a different tolerance without re-recording (non-destructive bake).

- Adobe's authoritative description of Smoother tolerance units for temporal (non-position) properties and of Motion Sketch's smoothing algorithm was not retrievable (helpx blocked); the cited values come from Meyer/PVC and tutorials.
- Blender's `BKE_curve_decimate_bezt_array` cost function (how "affects the curve shape the least" is measured) is in a different file I did not fetch; the manual was blocked.
- Maya's "Dense Data" method is not described algorithmically in the docs I could access.

## Key question 4: Easing preset libraries and "designed" easing (Material, Apple, Flow, easings.net, Penner, expressive curves) — bezier handles vs functions

### Takeaway
The standard libraries fall into two groups: curves expressible as a single CSS-style cubic bezier (all Penner polynomial/sine/expo/circ families and the "back" overshoot family, with y-handles outside [0,1]), and curves that are not single beziers (elastic, bounce, Material's multi-segment emphasized path, GSAP CustomEase paths), which must be stored as functions, as multi-segment paths, or as sampled `linear()`-style tables.

### Cited Findings

**GSAP CustomEase — arbitrary path as easing function**
- `CustomEase.create('myEase', 'M0,0 C0.5,0 0.5,1 1,1')` takes an SVG path; the code `_normalize`s it so x runs 0→1, subdivides each cubic into points (`threshold = 1 / (precision * 200000)`), keeps x monotonic (drops points whose x doesn't move forward, patches zero gaps to avoid division by zero), builds a lookup table sized `l = (1 / closest + 1) | 0` from the smallest x gap (fast mode samples at equal x; accurate mode "ensur[es] that EVERY anchor is hit perfectly"), and evaluates with `point.y + ((p - point.x) / point.cx) * point.cy` after an O(1) table jump. — [GSAP CustomEase.js](https://github.com/greensock/GSAP/blob/master/src/CustomEase.js)

### Inferences
- Storage model: one `cubic-bezier(x₁,y₁,x₂,y₂)` per key pair covers every Penner polynomial/sine/expo/circ curve and the "back" family (overshoot/anticipation are simply y-handles beyond [0,1]); that is why Flow, Figma ("ease in back/out back") and Material can ship as handle presets. Elastic, bounce, wiggle, multi-bounce and Material's emphasized "path" are not single beziers; the three shipping representations are (a) a closed-form function (easings.net `maths`), (b) a multi-segment bezier path (GSAP CustomEase/CustomBounce/CustomWiggle, Material emphasized), or (c) a sampled table (`linear()` in CSS; Motion's `toString()` output). For a timeline, (b) is the most editable: a multi-segment path between two keys can be shown and tweaked in the same graph editor as handles, and it stays an exact pure function of time.
- A "designed easing" library in your app can therefore be a list of named entries each holding either four bezier numbers or an SVG-like path in the unit square; apply = write handles onto the selected key pairs (Flow's "apply to each pair of keys"), or attach as a reusable reference so library edits propagate (a "shared easing" like Figma's copy/paste values but linkable).
- Material's emphasized tokens are a useful reminder that "standard" curves are asymmetric (fast accelerate, long decelerate: 0.2,0,0,1) — most "smoothing" complaints about hand keys are symmetric ease-in-out handles; an auto-ease default of standard/emphasized-decelerate reads as more natural than 0.42,0,0.58,1.

## Key question 5: Animation principles as computable presets (ease, anticipation, overshoot, follow-through, secondary motion, stagger/offset) and one-click smoothing

### Takeaway
Every classic principle has a shipping computable form: anticipation/overshoot = back-easing (handles beyond the unit square) or a spring/elastic segment; follow-through/secondary motion = a second-order filter or spring applied to the keyframed value (Cavalry Spring behaviour) or AE's `loopOut("continue")`/inertia expressions; staggering = a start-time offset distribution over an index (GSAP stagger `each/amount/from/grid/ease`, Cavalry Stagger with a Graph); and GSAP's CustomBounce/CustomWiggle show how bounce and wiggle can be generated as multi-segment bezier paths so they remain editable keyframe-style curves.

### Cited Findings
- GSAP stagger: a number form, or an object with `each`, `amount` (total time to spread the start times across), `from` ("start, center, end, edges, random, index"), `grid` (explicit `[rows, cols]` or `"auto"`, computed from `getBoundingClientRect()`), `axis`, and `ease` — "the ease distributes the start times of the animations, so 'power2' would start out with bigger gaps." With a grid, "the stagger is based on each element's total distance to the 'from' value on both axes." — [GSAP Staggers](https://gsap.com/resources/getting-started/Staggers/)
- Cavalry Stagger generates "sequential values between a minimum and maximum" distributed by a Graph, per duplicate ID, and can offset animation timing; Oscillator's Stagger option "stagger[s] the movement in time across duplicates." — [Cavalry docs: Stagger](https://docs.cavalry.scenegroup.co/nodes/behaviours/stagger); [Cavalry docs: Oscillator](https://cavalry.studio/docs/nodes/behaviours/oscillator/)
- Cavalry Spring behaviour "Add[s] dynamic secondary motion to a Shape's position keyframes" (Damping, Mass, Speed Limit) — i.e. follow-through/secondary motion as a layer on top of keys. — [Cavalry docs: Spring](https://cavalry.studio/docs/nodes/behaviours/spring/)
- AE `loopOut("continue")` "keeps animating based on the velocity at the first or last keyframe" (follow-through past the last key); `velocityAtTime(t)` gives the derivative needed for inertia-style expressions. — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- GSAP CustomWiggle: `wiggles` (default 10), `type` in easeOut/easeInOut/uniform/anticipate/random, `amplitudeEase`, `timingEase`; it builds an SVG path where each half-cycle flips sign and follows an amplitude envelope `y = ((y > 0) ? -1 : 1) * yEase(i * inc)`; for `anticipate`, "the anticipate ease is actually applied on the x-axis (timing) and uses easeOut for amplitude" and the first peak is negated so the motion starts by pulling backward; the path is handed to `createCustomEase`. — [GSAP CustomWiggle.js](https://github.com/greensock/GSAP/blob/master/src/CustomWiggle.js)
- GSAP CustomBounce: `strength` (default 0.7, capped 0.999; `decay`), `endAtStart` (prepends an anticipation segment and flips the path), `squash` (percent; also creates a companion `squashID` ease for scale), with each bounce shrinking by `w *= decayX * ((decayX + 1) / 2); h *= decay * decay;` and `decay *= 0.95`, emitted as cubic segments `prevX,1, cp1,y, x,y, cp2,y, nextX,1` then normalised to x ∈ [0,1]. — [GSAP CustomBounce.js](https://github.com/greensock/GSAP/blob/master/src/CustomBounce.js)
- Penner back/elastic/bounce closed forms (overshoot constant 1.70158; elastic `2^(−10x)·sin((10x − 0.75)·2π/3) + 1`; bounce pieces with 7.5625 and 2.75) are listed under KQ4. — [easings.net source](https://github.com/ai/easings.net/blob/master/src/easings.yml)
- Rive's Elastic interpolation (Amplitude, Period) is the keyframe-mode version of overshoot/settle. — [Rive interpolation docs](https://rive.app/docs/editor/animate-mode/interpolation-easing)
- Flow applies a chosen curve "to each pair of keys" — the one-click "re-ease everything" interaction. — [Motion Array, Flow review](https://motionarray.com/learn/after-effects/flow-after-effects-extension-review/)

### Inferences
- One-click presets that stay pure functions of time, and how to implement each:
  - Ease in/out: write bezier handles on each key pair (Flow). Per-segment, deterministic.
  - Anticipation: either back-easing handles (y₁ < 0) on the outgoing segment, or insert a short pre-key moving slightly opposite (keeps the bezier model). Overshoot: y₂ > 1 handles, or an elastic/spring segment (Rive).
  - Follow-through / secondary motion: a spring that *follows* the keyframed value is a simulation (history-dependent). Two seekable alternatives: (1) per-segment: at each key with a velocity discontinuity, add a decaying-sine residual `A·e^{−λ(t−t_k)}·sin(ω(t−t_k))` scaled by the velocity jump (closed form, sum of finitely many terms per time — pure function); (2) bake the filter to dense keys / a cached sample track at the comp frame rate.
  - Stagger: an index→delay map `delay(i) = ease(i/(n−1)) · amount` (GSAP) or a Graph-distributed value (Cavalry); evaluation of layer i at time t is just `f(t − delay(i))`, i.e. a time offset — pure function. Grid/distance-based "from" is the same with `i` replaced by normalised distance.
  - Wiggle/bounce: generate a multi-segment bezier path (GSAP approach) so the result is visible and editable as keys; or keep it as a closed-form function with a seed (Penner elastic/bounce; hash-noise wiggle with t as input).
- "Smoothing" in the one-click sense (make hand keys feel natural) is mostly (a) replacing linear/symmetric handles with asymmetric standard/emphasized curves, (b) adding small overshoot on arrival for emphasis, and (c) staggering siblings — all three are handle rewrites and time offsets, so they can be offered non-destructively as a layer (Cavalry Keyframe Layer with Strength) with a "bake to keys" command.

- Cavalry's Delay/Noise behaviour pages were not found in search results, so their attribute lists are unconfirmed.

## Key question 6: AI and ML assistance for motion graphics (as of October 2026) — what has shipped vs research

### Takeaway
What has actually shipped is almost entirely LLM-driven *generation of editable animation parameters* (Jitter's prompt-to-effect, Figma Motion's agent, Rive's AI Agent, Adobe's After Effects AI Assistant for expressions) rather than learned inbetweening or learned easing; the research line (Keyframer, LogoMotion, MoVer) is likewise "LLM writes CSS/SVG animation code + verification," while learned motion in-betweening and generative video inbetweening (AnyMoLe, Generative Inbetweening) target 3D characters and pixels, not motion-graphics property curves. I found no shipped product that learns easing from reference video; the closest is the UIST 2023 Wakey-Wakey prototype that transfers GIF motion onto text.

### Inferences
- Integration pattern that all shipped products converge on: the model emits *parameters* (keyframes, presets, effect parameters, expression code), never frames. Jitter ("tweaking animation parameters manually"), Figma Motion ("timeline and reusable structure"), Rive (scripts in the Assets panel) and Adobe (expressions) all keep the output editable and, crucially, deterministic/seekable because it is ordinary timeline data. For your app this means an AI feature should target your keyframe/behaviour schema (or an expression language) and be verifiable (MoVer's idea of checking generated motion against stated constraints is directly reusable as unit tests for generated keys).
- Nothing shipped as of Oct 2026 does learned *inbetweening of property curves* for motion graphics; "AI inbetweening" in marketing refers to video-frame generation (Runway/Generative Inbetweening), which is neither seekable in your sense nor editable. The practical AI help for "smoother keyframes" today is: generate the initial key set and easing from a prompt, then let the deterministic tools (springs, presets, fitting) do the smoothing.
- Learning easing from reference video remains research-grade (Wakey-Wakey's trajectory transfer is the closest); a pragmatic non-ML equivalent is "record from video": track a point, get dense samples, and fit keys (KQ3) — same pipeline as pointer recording.

## Key question 7: Smoothing existing keyframes (AE Smoother, Blender Smooth Keys / Gaussian / Butterworth, Maya Simplify, Savitzky–Golay) — preserving key times while smoothing values

### Takeaway
Shipping smoothers operate on values only and leave key times untouched: Blender's classic Smooth Keys is a fixed 5-tap weighted average (3:5:2:1:1 / 1:1:2:5:3) that skips endpoints, its Gaussian smooth samples the curve per frame, convolves with a normalised half-kernel (default sigma 0.33, width 6) and blends by a factor, and its Butterworth smooth is a forward-backward IIR low-pass (default 3 Hz cutoff, order 4) with endpoint blending; AE's `smooth()` expression is a windowed average over time (0.2 s, 5 samples); AE's Smoother and Maya's Simplify instead *reduce* keys within a tolerance (which changes key times) — so the correct tool depends on whether the key set or the curve shape is the thing to preserve.

### Cited Findings
- Blender Smooth Keys (classic): "calculate the new smoothed F-Curve's with weighted averages… done with two passes to avoid progressive corruption errors"; "previous: w/a ratio = 3:5:2:1:1" → `y1 = (3*p2 + 5*p1 + 2*c1 + n1 + n2) / 12`, "next: w/a ratio = 1:1:2:5:3" → `y3 = (p2 + p1 + 2*c1 + 5*n1 + 3*n2) / 12`, `y2 = (y1 + y3)/2`; handles "weighted between their original values and the averaged values" as `h = h*0.7 + y*0.3`; "Don't touch end points (otherwise, curves slowly explode…)". — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc)
- Blender Gaussian smooth: kernel `sigma_sq = 2σ²`, `normalized_index = i/(kernel_size−1)`, `kernel[i] = exp(−normalized_index²/sigma_sq)`, half-kernel stored, centre counted once and others doubled, normalised to sum 1; the pass runs only for `i` in `[kernel_size, sample_count − kernel_size)` (edges keep original values), keys map to sample indices with `round()` ("(int) would create stepping on x-values that are just below a full frame"), sub-frame keys interpolate between filtered samples, and the result is `interpf(filter_result, original, factor)`. Operator defaults: `sigma` 0.33 ("lower values make it sharper"), `filter_width` 6 ("how far to each side the operator will average the key values"). — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc); [Blender bpy.ops.graph 4.2](https://docs.blender.org/api/4.2/bpy.ops.graph.html)
- Blender Butterworth smooth: coefficients from `a = tan(π·cutoff/s)` and `r = sin(π(2i+1)/(4·order))` per biquad stage; the forward pass offsets input so "the first sample starts at 0. This avoids oscillations at the start and end of the curve"; "Run the filter backwards as well to remove phase offset"; near segment ends `butterworth_calculate_blend_value` blends back to the raw samples over `blend_in_out` frames with matched slopes. Defaults: `cutoff_frequency` 3.0 Hz ("lower values give a smoother curve"), `filter_order` 4 ("higher values produce a harder frequency cutoff"), `samples_per_frame` 1; the manual notes an implicit maximum "at half the sample rate" and that it "preserves the peaks of the animation" but "can introduce a ripple effect when the key values change rapidly." — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc); [Blender bpy.ops.graph 4.2](https://docs.blender.org/api/4.2/bpy.ops.graph.html); [Blender manual PR: Butterworth filter](https://projects.blender.org/blender/blender-manual/pulls/104511/files)
- AE `smooth(width=0.2, samples=5, t)`: averages the property over a time window; samples "odd… so that the value at the current time is included." — [AE expression reference mirror](https://github.com/docsforadobe/after-effects-expression-reference/blob/master/docs/objects/property.md)
- AE Smoother: replaces keys within a Tolerance (pixels for Position), spatial or temporal; fewer keys ⇒ generally smoother. — [ProVideo Coalition](https://www.provideocoalition.com/creating_motion_graphics_with_after_effects_hidden_gems_chapter_5_-_animati/)
- Maya Simplify: Time Tolerance 0.05 s and Value Tolerance 0.01 average key timing and values; Classic vs Dense Data methods. — [Maya 2023 Simplify Curve options](https://help.autodesk.com/cloudhelp/2023/ENU/Maya-Animation/files/GUID-455F76C5-F761-4007-AFFE-E0F80BEFB627.htm)
- Blender Clean Keyframes removes keys whose values are within a threshold of neighbours (value-based, keeps times of surviving keys). — [Blender keyframes_general.cc](https://github.com/blender/blender/blob/main/source/blender/editors/animation/keyframes_general.cc)

### Inferences
- Preserving key times while smoothing values — the Blender pattern is the right one for a keyframe timeline: (1) sample the curve at the comp frame rate over the selected span, (2) filter the samples (Gaussian for a gentle, phase-free blur; forward-backward Butterworth when you need to keep peaks and specify a cutoff in Hz; a 5-tap weighted average when keys are sparse), (3) write back only `value` at each existing key (`round()` the key time to the nearest sample; sub-frame keys interpolate), (4) blend with the original by a Strength factor, (5) re-derive handles from the filtered samples (slope at each key) or blend handles 70/30 as Blender does, and (6) leave endpoints fixed so adjacent segments don't drift. Everything here is a transform on key data, so the result stays a pure function of time.
- Savitzky–Golay (local least-squares polynomial fit per window, evaluated by convolution) is the natural "keep peaks, smooth jitter" filter for recorded curves and is what Blender's Gaussian/Butterworth are approximating; I could not fetch a citable source (Wikipedia/SciPy blocked), so treat this as general knowledge rather than a sourced finding.
- Tolerance-based reducers (AE Smoother, Maya Simplify, Blender Decimate) *do* move or delete keys; offer them as a separate "simplify" command and keep "smooth values" (times fixed) distinct in the UI, because users of hand-timed keys want the former only after recording and the latter on hand keys.

### Gaps
- The Blender manual's user-facing descriptions (and recommended sigma/width values) were blocked; defaults come from the API reference and code.
- No source could be fetched for Savitzky–Golay or for Maya's smoothing (as opposed to simplifying) tools.
- Adobe's official Smoother documentation was blocked; tolerance semantics for non-spatial properties are only described second-hand.
