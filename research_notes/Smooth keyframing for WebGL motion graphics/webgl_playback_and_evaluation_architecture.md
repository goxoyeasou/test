## Key question 1 — Time representation: fixed vs variable step, rational vs float time, mapping rAF timestamps to composition frames without drift, 60/120/144 Hz displays, and the "every other frame doubles" judder

### Takeaway
No mainstream web runtime uses exact rational time; they use float seconds or float frames driven by the `requestAnimationFrame` timestamp, and the ones that feel smooth (a) derive time from an absolute timestamp minus a start offset rather than accumulating deltas, (b) clamp or "smooth" pathological deltas, and (c) snap their internal tick to a frame grid with a small tolerance. Judder when the composition rate does not divide the display rate is a presentation-cadence problem, not an evaluation problem: either present each composition frame for an integer number of refreshes (accepting a 2:3-style cadence) or evaluate at display time ("sub-frame" interpolation) for preview while keeping export frame-exact.

### Cited Findings

**What `requestAnimationFrame` actually gives you**
- MDN: "The frequency of calls to the callback function will generally match the display refresh rate. The most common refresh rate is 60hz ... 75hz, 120hz, and 144hz are also widely used." The timestamp argument is "A DOMHighResTimeStamp indicating the end time of the previous frame's rendering", "based on the number of milliseconds since time origin ... with a minimal precision of 1 millisecond"; it is "similar to calling performance.now() at the start of the callback function, but it is never the same value"; "When multiple callbacks queued by requestAnimationFrame() begin to fire in a single frame, each receives the same timestamp"; and "requestAnimationFrame() calls are paused in most browsers when running in background tabs or hidden iframes". MDN's explicit advice: "Be sure always to use the first argument" to compute progress, otherwise "the animation will run faster on high refresh-rate screens." — [MDN requestAnimationFrame (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/window/requestanimationframe/index.md)
- `performance.now()` resolution is coarsened "To offer protection against timing attacks and fingerprinting": "Resolution in isolated contexts: 5 microseconds", "Resolution in non-isolated contexts: 100 microseconds". — [MDN performance.now (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/performance/now/index.md)
- Web Animations spec: a document timeline's current time "is calculated as a fixed offset from the |now| timestamp provided" each time "update animations and send events" runs, and the document timeline's `currentTime` "will not change within a task". The timing model "takes an input time and produces an output iteration progress"; "the output is based solely on the input time and is independent of previous inputs, the model can be described as stateless", with the caveat that "the model can only truly be described as stateless in the absence of dynamic changes to its timing properties". — [Web Animations Level 1, csswg-drafts source](https://raw.githubusercontent.com/w3c/csswg-drafts/main/web-animations-1/Overview.bs)
- Chromium engineer Nat Duca (2015) argued against passing a vsync-aligned time as the rAF timestamp because objects placed using "vsync+jitter" rather than "vsync+0" "will have unnecessary micro-jitter in their placement" (snippet; page not fetched). — [public-web-perf thread](https://lists.w3.org/Archives/Public/public-web-perf/2015Apr/0016.html)
- Chromium's frame pipeline: "BeginImplFrame starts a compositor frame (with each vsync) that will wait up until a deadline for a BeginMainFrame plus activation to complete before it times out and draws any asynchronous animation and scroll/pinch updates"; BeginMainFrame (where "HandleInputEvents, Animate, StyleUpdate and LayoutUpdate" run) is only sent "if there is main thread damage"; commit blocks the main thread while the layer tree is copied; work missing the activation deadline "is a possible source of a dropped frame"; with too many queued swaps the GPU thread may "just block until the next vblank"; and presentation time is estimated because the exact time is not available on every platform. — [Chromium "Life of a frame" (GitHub mirror)](https://github.com/chromium/chromium/blob/main/docs/life_of_a_frame.md)

**120 Hz and higher displays**
- Safari/WebKit: a WebKit bug thread states Safari limits web content to roughly 60 fps by default on ProMotion devices, and 120 Hz rAF is available only by turning off the "Prefer Page Rendering Updates Near 60fps" feature flag; a 2022 comment in that thread notes that "both Firefox and Chrome can run requestAnimationFrame at 120fps" (snippets; bugs.webkit.org not fetchable here). A separate, still-open (May 2026) WebKit bug asks for a way to enable 120 Hz in WKWebView-based hybrid apps, which the flag does not affect. — [WebKit bug 236780](https://bugs.webkit.org/show_bug.cgi?id=236780); [WebKit bug 294338](https://bugs.webkit.org/show_bug.cgi?id=294338); [German how-to on the Safari flag](https://www.iphone-ticker.de/promotion-im-web-freischalten-so-nutzt-safari-die-volle-bildrate-271471/)
- Android Frame Pacing (Swappy) docs describe the exact judder mechanism: "If a game running at 30 FPS attempts to render on a device that natively supports 60 FPS, the game render loop doesn't realize that a repeated frame remains on the screen for an extra 16 milliseconds. This disconnect usually creates substantial inconsistency in frame times, such as: 49 milliseconds, 16 milliseconds, 33 milliseconds." "Short frames followed by long frames are perceived by the player as stuttering." Display queue is "typically of size 2"; when full "the game is blocked ... (buffer-stuffing)". The fix is presentation timestamps "so that frames are not presented early" plus fences "to inject waits ... rather than allowing back pressure to build up". It lists stable rates per panel: 60 Hz → 60/30/20; 60+90 Hz → 90/60/45/30; 60+90+120 Hz → 120/90/60/45/40/30, and notes "a game that cannot produce 60 frames per second can drop to 45 FPS instead of 30 FPS to remain smooth" on a 90 Hz panel. — [Android Frame Pacing](https://developer.android.com/games/sdk/frame-pacing)
- Blur Busters forum: a 60 fps stream on a 120 Hz panel is clean only when each frame is held exactly two refreshes; "if 60fps isn't locked to every other refresh in fixed-refresh mode, there's going to be some jitter. That one is very visible"; "A 24fps film on a 120Hz display gets a new frame every 5 refreshes, while a 60Hz display gets one every 2.5 refreshes" (snippets). — [Blur Busters thread](https://forums.blurbusters.com/viewtopic.php?p=80448)
- JUCE forum measurement on a 120 Hz Windows 11 machine: timing-based frame limiting to 60 fps produced a mode of 1 skipped interval, "51 dropped frames" and wide variation in elapsed times, which the author linked to visible judder (snippet; forum not fetchable). — [JUCE forum: Animation frame rate limits](https://forum.juce.com/t/fr-animation-frame-rate-limits/62104)

**How real runtimes derive time from rAF (source code)**
- **GSAP ticker** (`gsap-core.js`): uses rAF when present (`_raf = typeof(requestAnimationFrame) !== "undefined" && requestAnimationFrame`) with a `setTimeout` fallback; default internal gap is 240 fps (`_gap = 1000 / 240`); `fps(n)` sets `_gap = 1000 / (fps || 240)`; a tick is dispatched only when `overlap = time - _nextTime` is `> 0` (or manual), then `_nextTime += overlap + (overlap >= _gap ? 4 : _gap - overlap)`; **lagSmoothing** defaults are `_lagThreshold = 500` ms and `_adjustedLag = 33` ms — when `elapsed > _lagThreshold || elapsed < 0` the ticker shifts its origin: `_startTime += elapsed - _adjustedLag`, so a 500 ms+ stall is treated as a 33 ms frame instead of a jump; `lagSmoothing(0)` disables it (`_lagThreshold = threshold || Infinity`). `deltaRatio(fps)` returns `_delta / (1000 / (fps || 60))`. The ticker auto-sleeps (`autoSleep` 120 ticks) when no root children are active. — [GSAP source](https://raw.githubusercontent.com/greensock/GSAP/master/src/gsap-core.js)
- **Anime.js v4 engine/clock**: tick via `requestAnimationFrame` in browsers and `setImmediate` otherwise; `engine.useDefaultMainLoop = true` (set false and call `engine.update()` to drive it yourself); `engine.pauseOnDocumentHidden = true` (pauses on `visibilitychange`); per-tickable fps throttling is done in `Clock.requestTick`: `elapsed = time - _lastTickTime`, tolerance `min(frameDuration * .25, 4)` ms, skip if `elapsed + tolerance < frameDuration`, otherwise `_lastTickTime = elapsed >= frameDuration ? time - (elapsed % frameDuration) : time` — the comment says "Tolerance prevents dropping frames that arrive a bit early due to RAF jitter" and the remainder keeps the tick "aligned to the frame grid". Defaults: `maxFps = 240`, `precision: 4` (decimal places), `tickThreshold: 200`, `K = 1e3`. — [engine.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/engine/engine.js); [clock.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/core/clock.js); [globals.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/core/globals.js); [consts.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/core/consts.js)
- **PixiJS Ticker**: `targetFPMS = 0.06` (60 fps); `deltaTime = deltaMS * targetFPMS` is a dimensionless scalar; raw `elapsedMS` is saved before capping ("Save uncapped elapsedMS for measurement"); `_maxElapsedMS = 100` (i.e. `minFPS` 10) caps the step used for animation; `maxFPS` gates frames with `if (delta < _minElapsedMS) return; _lastFrame = currentTime - (delta % _minElapsedMS)`; negative deltas are zeroed because they "can be the result of a race condition between when an animation frame is requested". — [PixiJS Ticker.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/src/ticker/Ticker.ts)
- **Phaser TimeStep**: `minFps` default 5 ("Defaults to 200ms between frames"), `targetFps` 60; if `delta > _min` it substitutes the last sane delta ("Probably super bad start time or browser tab context loss"); `smoothStep` averages a 10-sample ring buffer (`deltaHistory` default 10); after focus/resume a cooldown of `panicMax` = 120 frames caps `delta` to the target; `Math.max(0, time - lastTime)` "because Chrome will sometimes give negative deltas"; with `fpsLimit` it accumulates and keeps the remainder (`this.delta %= this._limitRate`); `frame++` "is unaffected by delta smoothing". — [Phaser TimeStep.js](https://raw.githubusercontent.com/phaserjs/phaser/master/src/core/TimeStep.js)
- **Three.js Timer** (successor to `Clock`): `update(timestamp)` takes the rAF timestamp (falls back to `performance.now()`); results are cached so repeated `getDelta()` calls in one step agree; `connect(document)` listens to `visibilitychange` and `reset()`s on return so the next delta does not span the hidden period; the class comment says the goal is "to avoid the conceptual flaws that became apparent in `Clock` over time". — [Three.js Timer.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/core/Timer.js)
- **lottie-web**: time is float *frames*; `frameMult = animationData.fr / 1000`, `frameModifier = frameMult * playSpeed * playDirection`, and `advanceTime(value)` does `nextValue = currentRawFrame + value * frameModifier`; the displayed frame is `isSubframeEnabled ? currentRawFrame : ~~currentRawFrame` (bitwise truncation). README: `setSubframe(false)` "will respect the original AE fps"; `true` "will update on every requestAnimationFrame with intermediate values" (default true). — [AnimationItem.js](https://raw.githubusercontent.com/airbnb/lottie-web/master/player/js/animation/AnimationItem.js); [lottie-web README](https://raw.githubusercontent.com/airbnb/lottie-web/master/README.md)
- **dotlottie-web** exposes the same choice as `useFrameInterpolation`: off keeps the original AE frame rate, on refreshes on each rAF with intermediate values (snippet; the README section I fetched did not contain it, so treat wording as approximate). — [dotlottie-web README](https://github.com/LottieFiles/dotlottie-web/blob/HEAD/packages/web/README.md)
- **Rive web runtime**: `draw(time)` computes `elapsedTime = (time - this.lastRenderTime) / 1000`, with **no cap** on elapsed time in the loop; on `visibilitychange` it cancels the loop and sets `lastRenderTime = 0` so "the first resumed frame starts with elapsedTime === 0"; `drawFrame()` prefers `document.timeline.currentTime` as the time source when available; it redraws only when `artboard.didChange()` / deferred work / `_needsRedraw` / canvas size changed; it reschedules only while `animator.isPlaying`. — [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts)
- **Theatre.js core**: sequence `position` is float **seconds**, clamped to `length` (no wrap in `Sequence.ts`; looping is via `iterationCount` in the playback controller); `subUnitsPerUnit` defines a snapping grid (`gridLength = 1 / subUnitsPerUnit`, `closestGridPosition` rounds to it) and feeds `TimeBasedPositionFormatter(_fps)`; `play({iterationCount, range, rate, direction}, ticker)` is driven by an externally supplied `ticker`. Exported project JSON stores `subUnitsPerUnit: 30` and keyframe positions as plain decimals such as `3.433` (snippet from docs). — [Theatre Sequence.ts](https://raw.githubusercontent.com/theatre-js/theatre/main/packages/core/src/sequences/Sequence.ts); [Theatre.js sequences docs](https://www.theatrejs.com/docs/0.5/manual/sequences)
- **Motion Canvas**: `PlaybackManager` keeps an integer-like `frame` counter (`frame += speed`, `speed = 1`), `fps = 30` default, and `duration` in frames; the `Renderer.renderFrame(settings, time)` converts with `secondsToFrames(time)`. — [PlaybackManager.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/PlaybackManager.ts); [Renderer.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/Renderer.ts)
- **Remotion** is frame-integer based: components are "a function that transforms a frame number into an image"; "Frame 30 might be rendered before frame 10, or frame 50 might be rendered twice" during parallel rendering. — [Remotion: Flickering](https://www.remotion.dev/docs/flickering)

**Game-loop theory**
- Gaffer on Games "Fix Your Timestep": a fixed dt loop "works well only if the display refresh rate matches dt"; variable dt makes "the behavior of your physics simulation depend on the delta time you pass in"; semi-fixed steps are "never larger than this value because if it is we subdivide the timestep"; "it's called the spiral of death because being behind causes your update to simulate more steps to catch up" — the remedy is to "clamp at a maximum # of steps per-frame"; semi-fixed results are "not *exactly the same*" across runs because of floating point, so exact reproducibility "requires a fully fixed dt"; the accumulator means "the renderer produces time and the simulation consumes it in discrete dt sized steps"; and "the final touch" renders `alpha = accumulator / dt` as "a blending factor between the previous and current physics state" (lerp for vectors, slerp for quaternions). — [Fix Your Timestep (source on GitHub)](https://raw.githubusercontent.com/gafferongames/gafferongames/master/content/post/fix_your_timestep.md)

### Inferences
- The two robust patterns in shipping code are **timeline time = rAF timestamp − origin** (Web Animations, GSAP's `_startTime`, Rive's use of `document.timeline.currentTime`) and **frame-grid-aligned ticking with a tolerance** (Anime.js: skip only if `elapsed + min(25%, 4 ms) < frameDuration`, then re-anchor to `time - elapsed % frameDuration`; Phaser `delta %= limitRate`). Both avoid the drift that pure delta accumulation produces. For a composition with a rational time core, the natural mapping is `compFrame = floor((rafTimestamp - playStartTimestamp) * fps / 1000 + ε)` computed from the absolute timestamp each frame, then evaluated at the exact rational time `compFrame / fps` — never `frame += 1` per callback, because callbacks are skipped in background tabs, under load, and on 120/144 Hz panels.
- Every runtime that survives background tabs clamps or re-origins large deltas (GSAP 500 ms → 33 ms; Pixi 100 ms cap; Phaser substitutes last sane delta; Three.js/Anime.js/Rive reset on visibility change). For a timeline editor the equivalent is "pause-on-hidden, re-anchor origin on resume" rather than a cap, so that play position stays frame-exact.
- The "every other frame doubles" judder cannot be fixed inside JS evaluation; it is decided by which refresh each frame is presented on. On a 60 Hz panel a 24 fps composition will alternate 2 and 3 refreshes per frame (2.5 average), like 3:2 pulldown; on 120 Hz it is a clean 5. Options for preview: (1) accept the cadence but make it **regular** (schedule frame changes on the rAF whose timestamp crosses the frame boundary, never skip-and-double unpredictably); (2) do what lottie-web/dotlottie do with sub-frame interpolation — evaluate at the display's time, which is smoothest but shows images that will not exist in the export; (3) when `fps` divides the refresh rate (30 on 60/120, 24 on 120/144, 60 on 120), lock to the integer multiple as Android frame pacing does. A "frame-exact preview" toggle that switches between (1) and (2) mirrors `setSubframe`/`useFrameInterpolation`.
- Chromium's pipeline implies at least one and often two vsyncs of latency between the rAF callback and pixels on screen, and the swap can stall if the GPU queue is full; a worker-rendered WebGL2 canvas inherits the same compositor cadence. Rive's "only redraw when the artboard changed and only reschedule while playing" loop is the right default for an editor that is idle most of the time.

## Key question 2 — Evaluation performance: hundreds of bezier curves per frame in JS, LUT vs Newton vs closed-form, typed arrays, WebAssembly, incremental re-evaluation, GPU evaluation

### Takeaway
The CSS-style cubic-bezier x→t solve is a solved micro-problem: an 11-entry Float32 LUT + up to 4 Newton iterations (bezier-easing ≤ v2) or a closed-form cubic root (bezier-easing v3, which needed a follow-up fix for near-double roots) is a few arithmetic operations per curve, so hundreds of curves per frame are not the bottleneck in JS; what the big runtimes optimize is (a) pre-sampling generators/springs to compute durations once, (b) doing nothing when nothing changed (dirty tracking / redraw-on-change), and (c) keeping the render path, not the curve math, on the GPU. GPU keyframe evaluation on the web has no documented production example; the documented engine pattern is "bake curves to LUTs on the CPU, sample on the GPU".

### Cited Findings
- **bezier-easing ≤ 2.1.0** (the Chrome/Firefox CSS timing-function algorithm): `NEWTON_ITERATIONS = 4`, `NEWTON_MIN_SLOPE = 0.001`, `SUBDIVISION_PRECISION = 0.0000001`, `SUBDIVISION_MAX_ITERATIONS = 10`, `kSplineTableSize = 11`, `kSampleStepSize = 1/(11-1)`; samples are stored in `new Float32Array(kSplineTableSize)` when available; `getTForX` finds the LUT interval, then uses Newton-Raphson if `initialSlope >= NEWTON_MIN_SLOPE`, returns the guess if slope is exactly 0, else falls back to binary subdivision; `if (mX1 === mY1 && mX2 === mY2) return LinearEasing`. — [bezier-easing v2.1.0 source](https://raw.githubusercontent.com/gre/bezier-easing/v2.1.0/src/index.js)
- **bezier-easing v3.x** replaced the LUT/Newton/subdivision search with "a closed-form algebraic cubic solve" (by Dmitry Baranovskiy, PR #63) described as "exact and faster"; v3.1.0 "Faster cubic solving through simplified math in `x2t`"; **v3.2.0 (Oct 2026) fixed "wrong roots near double roots and overflow for tiny x" and clamps x to [0,1]** — i.e. the closed-form path had numerical edge cases that the iterative version did not. The current solver picks "Cardano's formula or a trigonometric form depending on the discriminant", and bypasses the solver for inputs outside (0,1). The README says the library "uses fast heuristics (involving dichotomic search, newton-raphson, sampling)" and is "heavily based on implementations available in Firefox and Chrome"; no benchmark numbers are published ("the benchmark's precision shouldn't be fully trusted"). — [bezier-easing releases](https://github.com/gre/bezier-easing/releases); [bezier-easing master source](https://raw.githubusercontent.com/gre/bezier-easing/master/src/index.js); [bezier-easing README](https://github.com/gre/bezier-easing)
- **GSAP** evaluates each tween per tick as a pure function of its total time: clamp `tTime` to `[0, tDur]`, `time = _roundPrecise(tTime % cycleDuration)`, `if (isYoyo) time = dur - time`, `this.ratio = ratio = this._ease(time / dur)`, then each property tween applies `pt.r(ratio, pt.d)`; "lazy" rendering (`_lazy`, `_lazyLookup`, `_lazyRender()`) defers reading start values until the first render so that overwrites and jumps to the end of a populated timeline still read correct starting values. — [GSAP source (second half)](https://raw.githubusercontent.com/greensock/GSAP/master/src/gsap-core.js)
- **Motion (Framer Motion) generators** are pre-sampled to find durations: `calcGeneratorDuration` steps `generator.next(duration)` by `timeStep = 50` ms until `state.done` or `maxGeneratorDuration = 20_000` ms (returns `Infinity` at the cap); velocity is analytic for springs and otherwise a finite difference over `velocitySampleDuration = 5` ms. — [calc-duration.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/utils/calc-duration.ts); [velocity.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/utils/velocity.ts)
- **Rive** does not redraw unless something changed: the loop draws only when `artboard.didChange()`, deferred work is pending, `_needsRedraw`, or the canvas size changed; the state-machine `advanceAndApply` is the per-frame evaluation entry point, and scrubbed linear animations are sorted to run first. — [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts)
- **Rive's renderer** is C++ (compiled to WASM for the web) with "RenderContextImpl backends for Metal, Vulkan, D3D11, D3D12, and OpenGL/WebGL"; on the web `@rive-app/webgl2` "draws through a multisample anti-aliasing (MSAA) path" and the faster path "relies on ... WEBGL_shader_pixel_local_storage, a draft WebGL extension" that Rive "is helping to standardize" (snippets; rive.app not fetchable). — [Rive renderer open-source announcement](https://rive.app/blog/rive-renderer-now-open-source-and-available-on-all-platforms); [Rive canvas vs webgl docs](https://rive.app/docs/runtimes/web/canvas-vs-webgl)
- **Figma** moved its C++ engine to WebAssembly ("load time improved by more than 3x") and in its WebGPU post says WebGPU "allows optimizations WebGL can't, such as compute shaders that can shift work from the CPU to the GPU" and helps avoid "WebGL's bug-prone global state" (snippets; figma.com not fetchable). — [Figma: WebAssembly cut load time by 3x](https://www.figma.com/blog/webassembly-cut-figmas-load-time-by-3x/); [Figma rendering: Powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)
- **GPU-side curve evaluation in game engines**: Unity users bake an `AnimationCurve` to "256 samples in an array" for jobs/shaders and "lerp nearest available samples"; Stride's `ComputeAnimationCurve` keeps evaluation on the CPU and marks its raw sampler as "intended to be used for baking purposes only" (snippets). — [Unity forum](https://discussions.unity.com/t/need-way-to-evaluate-animationcurve-in-the-job/702132); [Stride ComputeAnimationCurve](https://doc.stride3d.net/latest/en/api/Stride.Animations.ComputeAnimationCurve-1.html)
- **dotlottie-web** ships a ~500 KB compressed WASM engine (ThorVG-based) and lists OffscreenCanvas as optional for "rendering on worker threads for improved responsiveness". — [dotlottie-web README](https://github.com/LottieFiles/dotlottie-web/blob/HEAD/packages/web/README.md)
- **WebGL best practices** relevant to evaluation→render handoff: "Certain WebGL entry points - including `getError` and `getParameter` - cause synchronous stalls on the calling thread"; "Even basic requests can take as long as 1ms"; `readPixels`/`getBufferSubData` "are typically synchronous"; use a fence + `clientWaitSync` polling pattern for async readback; in WebGL2 "prefer `texStorage` + `texSubImage`"; `invalidateFramebuffer` to discard depth/stencil/MSAA attachments you will not reuse. — [MDN WebGL best practices (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/webgl_api/webgl_best_practices/index.md)

### Inferences
- Per-curve cost with the bezier-easing ≤2 algorithm is one LUT scan (≤10 compares) plus ≤4 Newton steps (each ~10 flops) — order of 100 flops; with the v3 closed form it is a handful of transcendental calls. Either way a few hundred curves per frame cost microseconds in JS, far below the 8.3 ms (120 Hz) or 16.7 ms (60 Hz) budget; measure before reaching for WebAssembly. WASM pays off for large *vector path* work (Rive, dotlottie/ThorVG, Figma), not for keyframe interpolation.
- The v3.2.0 fix in bezier-easing is a concrete warning: a closed-form cubic solve needs discriminant-branch care (double roots, tiny x, clamping) or it will produce visibly wrong eases at exactly the "nice" handle positions designers use (e.g. ease-in-out with coincident control points). An editor should keep an iterative fallback or test the solver against the LUT/Newton reference across a dense grid of handle positions.
- The pattern that keeps evaluation cheap in editors is dirty tracking at the *track* level (GSAP's lazy start-value reads, Rive's `didChange`) plus "re-sample only the affected key span when one key moves" — evaluation at time t only needs the two surrounding keys, so an edit invalidates one span, not the whole track. No examined web runtime does span-level invalidation explicitly; they recompute per tick because it is cheap.
- GPU evaluation (uniform buffers / transform feedback in WebGL2, compute in WebGPU) only makes sense when per-element animated values are consumed directly by shaders (particles, instanced layers, path morphs with thousands of vertices). For a layer-based motion-graphics timeline with hundreds of properties, uploading the evaluated values as a UBO per frame is the practical approach; pre-baked LUT textures sampled in the shader are the engine-proven approach when the GPU must evaluate curves itself. WebGPU is optional and not part of the WebGL2 baseline.

### Gaps
- No published benchmark of JS bezier evaluation throughput (curves per ms) from any of these runtimes; bezier-easing explicitly declines to publish numbers.
- No documented web example of evaluating keyframe curves on the GPU (uniform/transform-feedback/WebGPU compute) for a motion-graphics timeline; the only GPU-curve material found is from native game engines.
- I could not open Figma's WebGPU post itself to see which workloads use compute shaders.
- Theatre.js's interpolation file (`interpolationTripleAtPosition.ts`) exists in the repo listing but I did not fetch it, so its bezier solver choice is unconfirmed.

## Key question 3 — Scrubbing: instant timeline scrubbing, frame caching, draft quality, RAM preview in a browser, cancelling stale frames, coalescing pointer events

### Takeaway
Instant scrubbing is built from three layers: (1) coalesce input to one evaluation per animation frame and always render the *latest* requested time (never a queue); (2) keep the per-frame render cheap enough (draft scale/fps, redraw-only-on-change, prefetch around the playhead) that an uncached frame still lands within one refresh; (3) cache rendered frames for playback (After Effects' RAM cache model), with the cache sized against a measured GPU/RAM budget because browsers do not expose one.

### Cited Findings
- **Pointer event coalescing**: browsers "merge multiple updates into one event to reduce event-handling work, at some cost in precision"; `getCoalescedEvents()` returns the `PointerEvent`s that "were coalesced (merged) into a single `pointermove` or `pointerrawupdate` event". — [MDN getCoalescedEvents (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/pointerevent/getcoalescedevents/index.md)
- **Rive scrub path**: `scrub(names, value)` sets `animation.scrubTo = value` and calls `drawFrame()` immediately; in `Animation.advance`, if `scrubTo !== null` the elapsed argument is ignored and the runtime does `instance.time = 0; instance.advance(scrubTo); scrubTo = null` (a reset-then-advance seek, not "set time and advance 0"); `drawFrame()` renders synchronously from `document.timeline.currentTime` when no frame request is pending, otherwise it schedules one. — [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts); [Animation.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/animation/Animation.ts)
- **lottie-web seek**: `goToAndStop(value, isFrame)` sets the raw frame directly when `isFrame` is true, else `value * frameModifier` (time→frame), then `gotoFrame()` renders. Skia's lottie-web perf harness drives playback by calling `goToAndStop` inside a rAF loop and notes the player sometimes drew blank when asked for the very last frame, worked around by subtracting a small value (snippet). — [AnimationItem.js](https://raw.githubusercontent.com/airbnb/lottie-web/master/player/js/animation/AnimationItem.js); [Skia lottie-web-perf harness](https://skia.googlesource.com/skia/+/chrome/m92/tools/lottie-web-perf/lottie-web-perf.html)
- **Motion Canvas seek cost**: because scenes are generator-based, `seek(frame)` must replay: if `frame <= this.frame` (or the scene cache does not cover the target) it rewinds to `currentScene.firstFrame`, calls `currentScene.reset()`, then steps `while (this.frame < frame && !this.finished) this.finished = await this.next()`. The Renderer "plays through the animation as fast as it can, occasionally pausing to keep the UI responsive" (it yields with `setTimeout(resolve, 0)`); preview and render have separately configurable scale and frame rate (snippet of docs). — [PlaybackManager.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/PlaybackManager.ts); [Renderer.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/Renderer.ts); [Motion Canvas rendering docs](https://motioncanvas.io/docs/rendering)
- **After Effects RAM/disk cache model**: "After Effects renders individual frames and temporarily stores them as cache in RAM. When memory is insufficient, fewer frames can be stored, and when RAM is exhausted, After Effects stops caching new frames, forcing it to overwrite previously cached frames when scrubbing"; disk cache is a second tier whose speed "depends on the raw read and write speeds of the drive". AE 25.2's "Enable Preview from Disk Cache" "stores every rendered frame from a composition in disk cache before streaming it into RAM for Preview playback. During playback, frames are read from RAM whenever possible. However, if memory cannot hold the entire composition, frames are continuously streamed from disk to memory" — before 25.2 the playable length was capped by RAM. AE 22.6 added a low-memory warning banner and "can exceed the RAM allotted in Preferences to cache a few frames" and may shrink the preview range (snippets; pages not fetchable). — [School of Motion: cached preview](https://schoolofmotion.com/blog/cached-preview); [Puget Systems on AE 25.2 disk cache](https://www.pugetsystems.com/blog/2025/02/24/upcoming-boost-to-after-effects-preview-playback-with-ram-and-disk-cache/); [Adobe: low-memory mechanism](https://helpx.adobe.com/au/after-effects/desktop/troubleshooting/fixed-and-known-issues/after-effects-low-memory-warning-mechanism.html)
- **Browser video-editor practice (Cap, open source)**: timeline lag on >10-minute videos came from rendering every segment and frame; the fix virtualized the timeline (`visibleTimeRange`, `isSegmentVisible`), throttled frame rendering to "~30fps" with "requestAnimationFrame batching", added "parallel frame prefetching and buffering" with bounded in-flight decodes and a frame-skip cap of 3, and raised the decoder `FRAME_CACHE_SIZE` from 100 to 500 frames "to reduce expensive seeking operations during scrubbing". No measured numbers in the PR. — [Cap PR #1417](https://github.com/CapSoftware/Cap/pull/1417)
- A WebCodecs scrubbing write-up keeps decoded frames in an LRU of 360 frames on desktop / 60 on mobile, evicts eagerly, yields the event loop when the decode queue passes a threshold, and decodes I-frames first "to fill the timeline within a few hundred ms" then back-fills by stride (snippet; page not fetchable). A GeekyAnts post on thumbnail scrubbing lists "dual caching, quality-tiered JPEG extraction ... and seek coalescing" as the production ingredients (snippet). — [cuberoot WebCodecs notes](https://cuberoot.me/dev/algorithms/webcodecs); [GeekyAnts scrubbing post](https://geekyants.com/blog/building-production-grade-video-thumbnail-scrubbing-in-the-browser-hls-frame-extraction-caching-and-performance-trade-offs)
- MasterSelects (browser editor) uses "a 3-tier scrubbing cache" with WebGPU for compositing/scrubbing/export (snippet; secondary source, tiers not described). — [SourcePulse: MasterSelects](https://www.sourcepulse.org/projects/26284920)
- **GPU memory budgets are undocumented**: a 2015 Khronos WebGL list test found Chrome "allocated 15gigs of ram before context loss happened, and no out of memory error was ever received" on a 3 GB GPU, Firefox "just keeps allocating textures forever", Android returned `OUT_OF_MEMORY` at ~2.5 GB and iOS at ~1 GB (snippets; old, single-device). — [Khronos public_webgl thread](https://www.khronos.org/webgl/public-mailing-list/public_webgl/1505/msg00018.php)
- **Readback cost**: `readPixels` is "finish + round-trip"; use fences and `clientWaitSync` polling; WebGL-2's approach "is analogous to the approach in OpenGL". — [MDN WebGL best practices (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/webgl_api/webgl_best_practices/index.md)
- **Pixi/Phaser-style fps gating** gives a built-in "latest wins": Pixi's `maxFPS` gate simply returns without updating when `delta < _minElapsedMS`, so intermediate requests collapse into the next allowed frame. — [PixiJS Ticker.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/src/ticker/Ticker.ts)

### Inferences
- "Latest wins" beats debouncing for scrubbing: store the requested time in a single slot (or a `SharedArrayBuffer` cell, see Q4), evaluate+render once per rAF, and drop everything older. Rive's `scrubTo` slot (`needsScrub`) is exactly this. A debounce adds latency; a queue adds lag that grows with drag speed. Cancellation of stale frames is then implicit (a frame that was never started cannot be stale); for multi-frame work (RAM preview fill, export) use an `AbortSignal` as Motion Canvas's renderer does.
- Pointer events already arrive once per frame on most browsers; `getCoalescedEvents()` is only needed if you want the intermediate positions (e.g. to pre-warm a cache for the direction of travel), not for the displayed frame.
- Draft-quality scrub = render at reduced resolution / skip expensive effects (motion blur, heavy blurs) while the pointer is down, then re-render the final frame on `pointerup`. Motion Canvas's separate preview/render scale is the simplest published form; Cap's ~30 fps throttle during scrub is another. Progressive refinement is then: draft now → full frame when idle → neighbouring frames into the cache while idle (Cap's prefetch).
- RAM-preview-in-a-browser maps to a ring of GPU textures (or an `ImageBitmap` array) keyed by frame index with AE's overwrite-oldest policy. Budget arithmetic (my calculation): a 1920×1080 RGBA8 frame is ~8.3 MB, so 100 frames ≈ 0.83 GB and 1000 frames ≈ 8.3 GB; at 1080p a few hundred frames is the realistic in-GPU cache, which is why AE added disk→RAM streaming in 25.2. Because browsers do not report a budget (Khronos thread), probe: allocate, check `gl.getError() === OUT_OF_MEMORY` and listen for `webglcontextlost`, and keep a hard cap configurable (Cap's 500-frame cache is a reasonable upper reference for 1080p-ish video; the cuberoot 360/60 desktop/mobile split is another).
- Motion Canvas shows the cost of stateful (generator) scenes: backward seeks replay from the scene start. A pure function-of-time core (the reader's) makes random-access scrubbing O(1) per frame; keep it that way (see Q6).

### Gaps
- No primary source gives measured scrub latency (pointer-down to pixels) for any web animation editor.
- No source documents a GPU-texture frame cache with explicit memory budgets in a browser motion-graphics tool; AE numbers are for native RAM. The Khronos memory data are from 2015.
- Adobe's own RAM-preview and AE 25.2 pages were not fetchable; quotes are from Puget/School of Motion secondary coverage.

## Key question 4 — Threading: OffscreenCanvas + workers, SharedArrayBuffer for timeline state, message latency, keeping the UI thread free; Electron specifics (GPU process, vsync, background throttling)

### Takeaway
Render in a dedicated worker with its own `requestAnimationFrame` on an `OffscreenCanvas` (never relay ticks from the main thread), share the hot timeline state (playhead, play/pause, dirty flags) through a cross-origin-isolated `SharedArrayBuffer` with `Atomics`, and throttle the worker to the compositor so it cannot build a multi-frame backlog. In Electron, disable `backgroundThrottling` for the editor window (or use `setBackgroundThrottling(false)`) and understand that offscreen rendering is a different, capped (≤240 fps) pipeline.

### Cited Findings
- **OffscreenCanvas**: "either on a worker or the main thread" you can call `transferControlToOffscreen()`; "Rendering operations can also be run inside a worker context"; "It's also possible to use `requestAnimationFrame()` in workers" (example calls it inside a worker); the alternative "Synchronous display of frames" path is `transferToImageBitmap()` → `bitmaprenderer` context `transferFromImageBitmap()`. — [MDN OffscreenCanvas (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/offscreencanvas/index.md)
- **Why workers need their own rAF** (WHATWG design wiki): without it a worker "can only approximate frame timing with setTimeout or setInterval", which "is not driven by the display"; relaying a main-thread rAF via `postMessage` "may add undue latency to the signal, especially when the browsing context's event loop is busy"; a GPU-accelerated worker loop can outrun the GPU and "cause the accumulation of a multi-frame rendering backlog, resulting in high latency and eventually OOM crashes", so the worker must be throttled (snippets; wiki not fetchable). — [WHATWG wiki: OffscreenCanvas.requestAnimationFrame](https://wiki.whatwg.org/wiki/OffscreenCanvas.requestAnimationFrame)
- A 2017 developer (juj, Emscripten) reported that the main-thread-relay model had frame rates "fluctuating quite badly" and proposed a presentation worker that "runs a requestAnimationFrame loop that signals frame barriers to 'mainWorker' via a semaphore implemented using SharedArrayBuffer", so frames "can be continuously pushed to the display without delay even when the main thread is busy" (snippets; design proposal, no measurements). — [public-webapps-github 2017](https://lists.w3.org/Archives/Public/public-webapps-github/2017Nov/0902.html)
- **SharedArrayBuffer**: "To use shared memory your document must be in a secure context and cross-origin isolated" (check `crossOriginIsolated`; once isolated "`postMessage()` no longer throws for `SharedArrayBuffer` objects"); shared memory was "effectively disabled at the start of 2018" (Spectre) and re-enabled via the 2020 isolation approach; "To synchronize, atomic operations are needed"; `Atomics` is always available. — [MDN SharedArrayBuffer (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/javascript/reference/global_objects/sharedarraybuffer/index.md)
- Cross-origin isolation also raises `performance.now()` resolution from 100 µs to 5 µs. — [MDN performance.now (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/performance/now/index.md)
- **Chromium pipeline facts relevant to threading**: BeginMainFrame is only issued when there is main-thread damage; commit "blocks the main thread during the copy"; frames that miss the activation deadline are dropped; swap can block "until the next vblank". — [Chromium "Life of a frame" (GitHub mirror)](https://github.com/chromium/chromium/blob/main/docs/life_of_a_frame.md)
- **Electron background throttling**: `webPreferences.backgroundThrottling` — "Whether to throttle animations and timers when the page becomes background. This also affects the Page Visibility API. Defaults to `true`"; if one webContents in a window disables it, "frames will be drawn and swapped for the whole window". Runtime control: `contents.setBackgroundThrottling(allowed)` "Controls whether or not this WebContents will throttle animations and timers when the page becomes backgrounded", `contents.getBackgroundThrottling()`. — [Electron web-preferences.md](https://github.com/electron/electron/blob/main/docs/api/structures/web-preferences.md); [Electron web-contents.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/web-contents.md)
- **Electron offscreen rendering**: three modes — "GPU shared texture" (`useSharedTexture: true`, "no CPU-GPU memory copies overhead", needs a native module), "GPU accelerated, CPU shared memory bitmap" (default, "slower than software output" but supports WebGL), and "Software output device" (`app.disableHardwareAcceleration()`, fastest frame generation); "when nothing changes on a webpage, no frames are generated"; `setFrameRate(fps)` — "When `webPreferences.offscreen.useSharedTexture` is `false` only values between 1 and 240 are accepted"; `paint` event delivers only the dirty region; `invalidate()`, `startPainting()/stopPainting()/isPainting()`, `getFrameRate()`. — [Electron offscreen-rendering.md](https://github.com/electron/electron/blob/main/docs/tutorial/offscreen-rendering.md); [Electron web-contents.md](https://raw.githubusercontent.com/electron/electron/main/docs/api/web-contents.md)
- **Electron command-line switches** documented: `--disable-renderer-backgrounding` "Prevents Chromium from lowering the priority of invisible pages' renderer processes"; `--force_high_performance_gpu` / `--force_low_power_gpu` for multi-GPU machines; Chromium flags go through `--enable-features=` or standalone switches. `--disable-gpu-vsync` and `--disable-frame-rate-limit` are **not** documented on Electron's page, and `cc/base/switches.cc` on Chromium main does not contain `disable-frame-rate-limit` (it does contain `enable/disable-main-frame-before-activation`, "Enables sending the next BeginMainFrame before the previous commit activates"). — [Electron command-line-switches.md](https://github.com/electron/electron/blob/main/docs/api/command-line-switches.md); [Chromium cc/base/switches.cc](https://raw.githubusercontent.com/chromium/chromium/main/cc/base/switches.cc)
- MDN: rAF "calls are paused in most browsers when running in background tabs or hidden iframes". — [MDN requestAnimationFrame (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/window/requestanimationframe/index.md)
- **Rive's shared offscreen context**: browsers cap the number of live WebGL contexts (oldest dropped); Rive recommends `useOffscreenRenderer: true` so many instances share one offscreen WebGL context (snippet). In `rive.ts`, `useOffscreenRenderer` is passed to `runtime.makeRenderer(canvas, useOffscreenRenderer)`. — [Rive canvas vs webgl docs](https://rive.app/docs/runtimes/web/canvas-vs-webgl); [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts)
- **dotlottie-web** treats OffscreenCanvas and Web Workers as optional features that "Enable background processing for better performance". — [dotlottie-web README](https://github.com/LottieFiles/dotlottie-web/blob/HEAD/packages/web/README.md)

### Inferences
- Architecture that follows from the sources: UI thread owns the DOM timeline and pointer input; it writes `{requestedTimeNumerator, requestedTimeDenominator, playing, generation}` into a `SharedArrayBuffer` with `Atomics.store` (+ `Atomics.notify` if the worker waits); the render worker runs its own `requestAnimationFrame` loop on the transferred `OffscreenCanvas`, reads the latest state with `Atomics.load` at the top of each frame (latest-wins scrubbing for free), evaluates at exact rational time, renders, and never queues more than one frame. This removes `postMessage` latency from the scrub path and keeps the UI thread free for the timeline. Note `Atomics.wait` is not allowed on the main thread (general knowledge; MDN SAB page did not cover it), so the UI thread must only `notify`.
- Worker rAF cadence is still the compositor's; Chromium's deadline model means a worker frame that takes longer than one vsync is simply shown a vsync later, and a worker that renders faster than the compositor consumes frames risks the WHATWG backlog scenario — so use the worker rAF as the pacing source and do not render outside it.
- Shipping the app requires COOP/COEP headers (browser) — Electron can set them on its `file://`/custom-scheme responses — otherwise fall back to `postMessage` with transferable `ArrayBuffer`s; design the state struct so both transports carry the same bytes.
- For Electron: an editor whose preview window is behind another window will see `requestAnimationFrame` paused unless `backgroundThrottling: false` (per-window), and exports driven by rAF will stall; drive export with the Motion Canvas model (loop as fast as possible with explicit yields) rather than rAF. Electron's offscreen rendering path is for headless capture, not for the interactive preview; its 240 fps cap and dirty-rect `paint` events are documented, but its GPU→CPU copy makes it slower than on-screen rendering unless `useSharedTexture` is used.

### Gaps
- No measured `postMessage` or SAB signalling latencies between main thread and worker on current Chromium were found (all design-level sources are 2015–2017).
- Chromium's background-tab timer throttling specifics (1 Hz, budget throttling, intensive wake-up throttling) could not be fetched (developer.chrome.com / chromestatus blocked); only MDN's "rAF paused" statement is cited.
- Browser compatibility for WebGL2 contexts on worker `OffscreenCanvas` (the MDN compat table is a template placeholder in the source) was not confirmed from a fetched source.
- `--disable-gpu-vsync` / `--disable-frame-rate-limit` behaviour in Electron is undocumented in the pages I could reach; treat as unsupported.

## Key question 5 — Rendering smoothness: motion blur via sub-frame sampling, frame blending, sub-pixel positioning and anti-aliasing, premultiplied alpha, texture filtering under interpolated transforms

### Takeaway
Motion blur in motion-graphics tools is defined by shutter angle/phase and a sample count and is produced by evaluating the scene at sub-frame times and accumulating (AE: 180°, 16 samples, adaptive limit 128; Blender EEVEE: accumulation steps) — this is only correct if evaluation is a pure function of time. For the WebGL2 presentation path, the spec-level details that keep interpolated motion clean are: premultiplied alpha by default, `alpha:false` carries a platform-dependent compositing cost, integer-device-pixel canvas sizing to avoid moiré, and mipmapped/linear filtering (the WebGL default min filter expects mipmaps).

### Cited Findings
- **After Effects motion blur parameters** (Composition Settings → Advanced): Shutter Angle 180, Shutter Phase 0, Samples Per Frame 16, Adaptive Sample Limit 128 (listed for CS3; not re-verified for current versions). "Samples Per Frame sets how many intermediate samples are used to fake continuous blur for 3D layers, Shape Layers, and some effects"; "Adaptive Sample Limit covers everything else"; Shutter Phase "decides how much the blur leads or lags" the frame — set it to "minus one-half the Shutter Angle, which is -90° for a 180° shutter" to centre the blur (older AE defaulted to 0, so blur "always lagged the action"); practitioner advice: max out samples "unless rendering gets really slow", otherwise "you might notice echoes on fast-moving objects" (snippets; pages not fetchable). — [Creative Cow thread (2009)](https://creativecow.net/?p=97118); [ProVideo Coalition: Motion Blur and more](https://www.provideocoalition.com/cmg_hidden_gems_chapter_8_motion_blur_and_more/)
- **Accumulation motion blur** (Blender EEVEE): "EEVEE splits the render into multiple time steps and accumulates the result which is known as Accumulation Motion Blur"; each step "corresponds to a full scene re-evaluation and can add a lot of overhead", and a screen-space post-process blur fills gaps between steps (snippet). Unity Recorder maps a 0–360° shutter angle to a fraction of the inter-frame interval and "makes the shutter remain closed during the rest of the interval" (snippet). Bevy's post-process blur uses `samples` per direction (`3 * 2 + 1 = 7` taps) and notes "WebGL2 uniform structs need 16-byte alignment" (snippet). — [Blender EEVEE motion blur](https://docs.blender.org/manual/en/4.2/render/eevee/render_settings/motion_blur.html); [Unity Recorder accumulation](https://docs.unity3d.com/Packages/com.unity.recorder@4.0/manual/RecorderAccumulationProperties.html); [Bevy motion_blur source](https://doc.qu1x.dev/bevy_trackball/src/bevy_core_pipeline/motion_blur/mod.rs.html)
- **Sub-frame evaluation for smoothness in Lottie players**: `setSubframe(true)` (default) renders "on every requestAnimationFrame with intermediate values" rather than snapping to AE frames; `false` snaps via `~~currentRawFrame`. — [lottie-web README](https://raw.githubusercontent.com/airbnb/lottie-web/master/README.md); [AnimationItem.js](https://raw.githubusercontent.com/airbnb/lottie-web/master/player/js/animation/AnimationItem.js)
- **Gaffer's "final touch"**: render the blend of previous and current simulation states with `alpha = accumulator / dt` to remove the stutter caused by leftover accumulator time. — [Fix Your Timestep](https://raw.githubusercontent.com/gafferongames/gafferongames/master/content/post/fix_your_timestep.md)
- **WebGL context attributes (spec)**: `premultipliedAlpha` default true — "If the value is true the page compositor will assume the drawing buffer contains colors with premultiplied alpha"; "This flag is ignored if the alpha flag is false"; with it true "any pixels sent to the page compositor shall have color values less-than-or-equal-to their alpha value"; `toDataURL` must de-multiply ("the color channels are divided by the alpha channel"), which "is lossy". `preserveDrawingBuffer` default false: "after compositing the contents of the drawing buffer shall be cleared to their default values". `antialias` default true ("If the value is false or the implementation does not support antialiasing, no antialiasing is performed"). `desynchronized`: "the user agent may optimize the rendering of the canvas to reduce the latency, as measured from input events" but "it might introduce visible tearing artifacts". `powerPreference` is "only a hint". — [WebGL 1.0 spec (KhronosGroup GitHub mirror)](https://raw.githubusercontent.com/KhronosGroup/WebGL/main/specs/latest/1.0/index.html)
- **MDN WebGL best practices**: `alpha:false` "causes the browser to composite the WebGL-rendered canvas as though it were opaque" but "On some platforms, this capability unfortunately comes at a significant performance cost" — prefer writing alpha = 1.0; non-integer `devicePixelRatio` "will cause moire artifacts", so "pre-snap" the canvas to whole device pixels using `ResizeObserver` with `'device-pixel-content-box'`; "When in doubt, call `generateMipmaps()` after texture uploads", "Mipmaps are cheap on memory (only 30% overhead)", and without mipmaps set `TEXTURE_MIN_FILTER` to `LINEAR` because the default is "NEAREST_MIPMAP_LINEAR, for mipmapping!"; in WebGL 2 "just use `texStorage` with `levels=1`" for non-mipmapped textures. — [MDN WebGL best practices (GitHub mirror)](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/webgl_api/webgl_best_practices/index.md)
- **Rive's web AA path**: `@rive-app/webgl2` currently "draws through a multisample anti-aliasing (MSAA) path", with a faster pixel-local-storage path behind a draft extension/flag (snippet). — [Rive canvas vs webgl docs](https://rive.app/docs/runtimes/web/canvas-vs-webgl)
- **Android frame pacing** shows that smoothness also depends on presenting frames on consistent vsync multiples, not only on what is drawn. — [Android Frame Pacing](https://developer.android.com/games/sdk/frame-pacing)

### Inferences
- With a pure function-of-time core, motion blur is: for frame f with shutter angle θ and phase φ, evaluate at `t_i = (f + φ/360 + (θ/360)·(i/(N−1)))/fps` for i in 0..N−1 and accumulate with weight 1/N into a float render target (`EXT_color_buffer_float` in WebGL2) — the AE defaults (θ=180°, φ=−90°, N=16) are a sensible preset, with a lower N for draft/scrub and the full N for export. Because every sub-sample is itself an exact-time evaluation, play/seek/export produce identical blur, which is impossible with velocity-buffer blur derived from frame deltas. Velocity-buffer post-process blur (Bevy style) is the cheap real-time fallback.
- "Slow motion stair-stepping" has two causes: (1) snapping evaluation to integer composition frames (lottie `setSubframe(false)`) — fix by evaluating at the exact rational sub-frame time your core already supports; (2) snapping positions to device pixels — fix by keeping transforms in float and relying on MSAA/analytic AA for shapes and `LINEAR`/mipmapped filtering for textures, and by only pixel-snapping the *canvas* (DPR pre-snap), never the content. Frame blending (averaging adjacent frames) is the video-footage fallback when true sub-frame evaluation is unavailable; for native keyframed layers it is unnecessary.
- Keep every intermediate framebuffer premultiplied (the default and what the compositor expects); un-premultiplied textures uploaded with `UNPACK_PREMULTIPLY_ALPHA_WEBGL` avoid dark fringes under bilinear filtering during interpolated transforms. Avoid `preserveDrawingBuffer:true` for the preview (it defeats the compositor's clear/swap optimisations); for export read back via fence + `readPixels` from your own FBO instead.

### Gaps
- No fetched primary source on sub-pixel positioning/anti-aliasing strategies in a vector motion-graphics renderer (Figma/Rive engineering posts were blocked; searches were exhausted before this topic).
- Adobe's own motion-blur documentation was unreachable; the 180/16/128 defaults come from secondary 2009 forum material and may differ in current AE.
- No source on frame blending implementations in a web editor.

## Key question 6 — Determinism: making play = seek = export hold; springs, physics and noise; how tools test it

### Takeaway
The stateless timing model (Web Animations, GSAP's `render(totalTime)`, Remotion's frame→image rule) is the only model under which play, seek and parallel export agree; springs are made deterministic with closed-form damped-harmonic-oscillator solutions (Motion, wobble) plus a tolerance-based settle rule, randomness with seeded helpers, and the tooling tests it by rendering frames out of order / in parallel and comparing.

### Cited Findings
- **Web Animations**: the timing model's "output is based solely on the input time and is independent of previous inputs, the model can be described as stateless", except under "dynamic changes to its timing properties" and stateful playback controls (pause); seeking is "set the current time" (recomputes start time from timeline time, seek time and playback rate, or sets hold time when paused). — [Web Animations Level 1 source](https://raw.githubusercontent.com/w3c/csswg-drafts/main/web-animations-1/Overview.bs)
- **GSAP** renders a tween purely from `totalTime`: `tTime` clamped, `time = tTime % cycleDuration`, yoyo flip, `ratio = ease(time/dur)`; `prevTime` is used for event direction (`onStart`, `onComplete` vs `onReverseComplete`) and for the reverse-ease segment math, not for the value itself; `resetTo` ends with `render(0)`; "immediateRender" is implemented by priming `_tTime = -_tinyNum` so the first render runs. — [GSAP source (second half)](https://raw.githubusercontent.com/greensock/GSAP/master/src/gsap-core.js)
- **Remotion** (the clearest published determinism contract): "Remotion renders in several tabs at once ... These tabs don't share state, and animations that run independent of useCurrentFrame() will break. Frames don't render in order and frames can be skipped"; "Frame 30 might be rendered before frame 10, or frame 50 might be rendered twice"; CSS transitions/`@keyframes` and `setTimeout` are "wrong"; a component must "always display the same image when called multiple times", "not rely on frames being rendered sequentially", and "not animate when the video is paused"; use `Math.random()` replacements — Remotion's seeded `random(seed)` helper; the fallback `--concurrency=1` "will fix flickering / choppyness in many cases, but it is way slower and the correct timing of the animations is still not guaranteed". — [Remotion: Flickering](https://www.remotion.dev/docs/flickering); [Remotion CSS animations troubleshooting](https://www.remotion.dev/docs/troubleshooting/css-animations); [react-doctor rule on seeded randomness](https://www.react.doctor/docs/rules/react-doctor/remotion-deterministic-randomness)
- **Motion Canvas** achieves play = export by running the *same* generator-based playback for both: the `Renderer` "plays through the animation as fast as it can", stepping `playback.progress()` and exporting each frame; seeking backward replays from the scene start. `renderFrame(settings, time)` does `reloadScenes`, `reset`, `seek(frame)`, then renders — i.e. a still is produced by deterministic replay. — [Renderer.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/Renderer.ts); [PlaybackManager.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/PlaybackManager.ts)
- **Rive scrub = reset then advance**: `instance.time = 0; instance.advance(scrubTo)` for linear animations; state machines are advanced incrementally (`advanceAndApply(elapsedTime)`) and are therefore history-dependent. — [Animation.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/animation/Animation.ts); [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts)
- **Closed-form springs (Motion / Framer Motion)**: `dampingRatio = damping / (2 * Math.sqrt(stiffness * mass))`; underdamped `target - env * (A*sin + delta*cos)`, critically damped `target - exp(-ω t) * (delta + (v + ω delta) t)`, overdamped "the sum of a slow and a fast decaying exponential, so no term can overflow"; `done` when `|velocity| <= restSpeed && |target - current| <= restDelta` with defaults `restSpeed {granular: 0.01, default: 2}`, `restDelta {granular: 0.005, default: 0.5}` (granular when `|delta| < 5`); duration-based springs are done when `t >= duration`; `maxDuration: 10.0` s; `findSpring` maps `bounce` → damping ratio and Newton-iterates 12 times for the frequency; `visualDuration` uses `root = 2π / (visualDuration * 1.2)`; `stiffness/damping/mass` override `duration/bounce`; velocity is the analytic derivative (`resolveVelocity`). Caveat: `next(t)` mutates and returns a shared `state` object and `retarget()` changes coefficients, so it is pure only for a fixed configuration. — [Motion spring.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/spring.ts)
- **wobble** (React-Native-era spring lib) chose a closed-form solution over RK4 because it is "Easier to generate keyframes and build continuous/interruptible gestures and animations", with defaults stiffness 100, damping 10, mass 1, `restVelocityThreshold` 0.001, `restDisplacementThreshold` 0.001, `overshootClamping` false. — [wobble README](https://raw.githubusercontent.com/skevy/wobble/master/README.md)
- Figma's spring settle rule: springs "theoretically approach but never reach their final value", so Figma defines the end with "a much tighter tolerance of 0.1%" (snippet). Framer Motion's documented defaults are stiffness 100, damping 10, mass 1 (secondary; snippet). — [Figma forum: spring duration](https://forum.figma.com/archive-21/how-does-spring-animation-duration-work-33227); [Maxime Heckel: physics behind spring animations](https://blog.maximeheckel.com/posts/the-physics-behind-spring-animations/)
- **Gaffer on determinism**: semi-fixed stepping is "not *exactly the same*" across runs because of floating point; exact reproducibility "requires a fully fixed dt". — [Fix Your Timestep](https://raw.githubusercontent.com/gafferongames/gafferongames/master/content/post/fix_your_timestep.md)
- Lottie players expose the **opposite** choice: subframe interpolation makes preview depend on the display's rAF timing (smooth but not frame-exact), while `setSubframe(false)` snaps to AE frames (frame-exact). — [lottie-web README](https://raw.githubusercontent.com/airbnb/lottie-web/master/README.md)

### Inferences
- The reader's "evaluate at exact rational time, pure function of time" core already satisfies the Web Animations/Remotion contract. The remaining risks are at the edges: (1) *stateful features* (state machines, physics, particle systems, "wiggle"-style noise, cumulative counters) — give each a closed form (springs: Motion/wobble equations) or a deterministic *replay-from-anchor* path (Motion Canvas/Rive-scrub style) with cached checkpoints so seek cost is bounded; (2) *randomness* — seed from `(layerId, propertyId, frameIndex)` and use a pure hash, never `Math.random()`; (3) *time-dependent events* (onStart/onComplete) — GSAP's `prevTime` shows these are the one legitimately stateful part; keep them out of the value path; (4) *floating-point reductions* — evaluate curves from the rational time converted once to a double, with the same code path (and ideally the same build/WASM) for preview and export.
- Spring "end of animation" must be defined by a fixed tolerance (Motion's restSpeed/restDelta, wobble's 0.001, Figma's 0.1%), computed once from the parameters, so that the keyframe after a spring starts at the same time in play, seek and export.
- Test like Remotion and Motion Canvas: render a composition (a) sequentially, (b) in random frame order, (c) in N parallel workers, (d) after scrubbing backwards and forwards, and assert byte-identical (or ε-identical for GPU) frames; keep a golden-frame set for regressions; and include "pause does not change the image" as a test case.

### Gaps
- No fetched source describes how Rive, Theatre.js or Jitter/Fable test determinism (golden images, CI frame diffs); only Remotion's and Motion Canvas's approaches are documented in sources I could reach.
- Motion's `findSpring` lives in a file I could not open; the mapping details above are from `spring.ts` references only.
- No source on deterministic noise (seeded Perlin/simplex) in web animation runtimes specifically; After Effects' seeded `wiggle`/`seedRandom` docs were unreachable.

## Key question 7 — Libraries worth knowing (what each actually does, from source)

### Takeaway
The libraries split into *tickers* (GSAP, Anime.js, PixiJS, Phaser, Three.js Timer) that are worth copying for time handling; *stateless evaluators* (bezier-easing, GSAP tween render, Motion's generators, Web Animations) that are worth copying for play = seek; and *renderer/players* (lottie-web, dotlottie-web, Rive, Motion Canvas, Remotion, Theatre.js) that show the preview-vs-export trade-offs. WebGPU-based animation tooling (Figma's renderer) exists but is optional relative to a WebGL2 baseline.

### Cited Findings
- **bezier-easing**: v2 = 11-sample Float32 LUT + Newton (4 iters, min slope 0.001) + binary subdivision (1e-7, ≤10 iters); v3 = closed-form algebraic cubic solve ("exact and faster"), with v3.2.0 (Oct 2026) fixing near-double-root and tiny-x cases; ESM with CJS fallback; TypeScript types. — [v2.1.0 source](https://raw.githubusercontent.com/gre/bezier-easing/v2.1.0/src/index.js); [releases](https://github.com/gre/bezier-easing/releases)
- **GSAP (v3.15 source)**: ticker at up to 240 fps internal gap, `lagSmoothing(500, 33)` defaults, `deltaRatio()`, `fps()`, `sleep()/wake()` with `autoSleep` 120; tween render is a pure function of `totalTime` with lazy start-value capture. — [gsap-core.js](https://raw.githubusercontent.com/greensock/GSAP/master/src/gsap-core.js)
- **Theatre.js core**: seconds-based sequence position, clamped to length; `subUnitsPerUnit` grid (30 in exported JSON) for snapping and fps formatting; `play({iterationCount, range, rate, direction}, ticker)`; the studio offers a multi-track bezier curve editor (snippet). — [Sequence.ts](https://raw.githubusercontent.com/theatre-js/theatre/main/packages/core/src/sequences/Sequence.ts); [Theatre.js sequences docs](https://www.theatrejs.com/docs/0.5/manual/sequences)
- **lottie-web**: float-frame clock (`fr/1000` per ms), `setSubframe`, `goToAndStop(value, isFrame)`, `setSpeed`, `setDirection` (1 / −1), loop handled by `nextValue % totalFrames`. — [AnimationItem.js](https://raw.githubusercontent.com/airbnb/lottie-web/master/player/js/animation/AnimationItem.js); [README](https://raw.githubusercontent.com/airbnb/lottie-web/master/README.md)
- **@lottiefiles/dotlottie-web**: ~500 KB compressed WASM engine fetched from CDN on first construction; Canvas 2D required, OffscreenCanvas/Workers optional; `useFrameInterpolation` toggles sub-frame rendering (snippet). — [dotlottie-web README](https://github.com/LottieFiles/dotlottie-web/blob/HEAD/packages/web/README.md)
- **@rive-app/canvas vs @rive-app/webgl2**: Rive recommends `@rive-app/webgl2` ("the same renderer as the Rive Editor"); canvas uses the browser 2D renderer with "advantages (particularly for performance)" but not every editor feature; WebGL2 currently uses MSAA with a pixel-local-storage fast path behind a flag; `useOffscreenRenderer: true` shares one WebGL context across instances (snippets). Runtime loop: rAF elapsed-seconds advance, redraw-on-change, scrub via `scrubTo`. — [Rive canvas vs webgl docs](https://rive.app/docs/runtimes/web/canvas-vs-webgl); [rive.ts](https://raw.githubusercontent.com/rive-app/rive-wasm/master/js/src/rive.ts)
- **Motion (Framer Motion / Motion One lineage)**: closed-form spring generator, `maxDuration` 10 s, duration pre-sampling at 50 ms steps to a 20 s cap, 5 ms finite-difference velocity for non-spring generators. — [spring.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/spring.ts); [calc-duration.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/utils/calc-duration.ts); [velocity.ts](https://raw.githubusercontent.com/motiondivision/motion/main/packages/motion-dom/src/animation/generators/utils/velocity.ts)
- **wobble**: closed-form spring reference implementation with documented defaults. — [wobble README](https://raw.githubusercontent.com/skevy/wobble/master/README.md)
- **Anime.js v4**: `engine` with `maxFps` 240, `precision` 4, `tickThreshold` 200, `pauseOnDocumentHidden`, `useDefaultMainLoop` (external `engine.update()`), `timeUnit` ms/s, per-animation `fps` throttling with ≤4 ms early-frame tolerance aligned to the frame grid; `setImmediate` in Node. — [engine.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/engine/engine.js); [clock.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/core/clock.js); [consts.js](https://raw.githubusercontent.com/juliangarnier/anime/master/src/core/consts.js)
- **PixiJS Ticker / Phaser TimeStep / Three.js Timer**: see Q1 for the exact clamps (100 ms cap; 10-sample smoothing + 120-frame panic cooldown + 5 fps floor; visibility reset). — [Pixi Ticker.ts](https://raw.githubusercontent.com/pixijs/pixijs/dev/src/ticker/Ticker.ts); [Phaser TimeStep.js](https://raw.githubusercontent.com/phaserjs/phaser/master/src/core/TimeStep.js); [Three Timer.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/core/Timer.js)
- **Motion Canvas**: integer-frame playback (fps 30 default), as-fast-as-possible renderer with explicit yields, image-sequence exporter, `renderFrame(settings, time)`. — [Renderer.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/Renderer.ts); [PlaybackManager.ts](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/packages/core/src/app/PlaybackManager.ts)
- **Remotion**: frame-number-driven React rendering across parallel tabs; seeded `random()`; `delayRender()` for async assets. — [Remotion: Flickering](https://www.remotion.dev/docs/flickering)
- **Figma (WebGPU, optional)**: C++→WebAssembly engine; WebGL→WebGPU migration for compute shaders and explicit draw-call state, maintaining a WebGL fallback (snippets). — [Figma WebGPU post](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/); [Figma WebAssembly post](https://www.figma.com/blog/webassembly-cut-figmas-load-time-by-3x/)
- **Jitter / Fable**: no engineering posts found; Jitter job listings mention "TypeScript, canvas2D/WebGL, React"; a former Fable engineer's profile describes a "WebGL rendering pipeline" and animation engine with interpolations, motion paths, morphing (secondary, self-reported). — [Jitter job post](https://jitter.notion.site/Software-Engineer-dbe2b307ddde454bbe6540030913599b); [Malt profile](https://en.malt.fr/profile/corentinflach)

### Inferences
- For the reader's stack: borrow GSAP's lag-smoothing/re-origin logic and Anime.js's frame-grid tolerance for the *preview clock*; keep the Web-Animations/GSAP/Remotion "value = f(time)" contract for the *evaluator*; use Motion's closed-form spring (with wobble as a cross-check) for springs; and treat Rive's `webgl2` package as the reference for what a vector renderer looks like on WebGL2 today (MSAA path, shared offscreen context).
- `d3-ease`, `popmotion`, GSAP `CustomEase` and Rive's editor internals were not examined in this session (search budget exhausted) — see Gaps.
