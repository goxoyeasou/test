# Interpolation mathematics and curve models for smooth keyframing (motion-graphics tools and standards)

Research date: 2026-10-09. Scope: how shipping tools (After Effects, Blender, Maya, Cavalry, Rive, Lottie/bodymovin) and web standards (CSS Easing, CSS Color 4) represent keyframe curves; the maths behind cubic-bezier easing and its solvers; tangent-continuity models; spatial path/arc-length reparametrisation; rotation; colour; hold/extrapolation; easing presets. For those, facts were obtained either from search-engine extracts of the official page (cited with the official URL) or from the primary *source files* on GitHub (spec `.bs` sources, product source code), which were fully readable. Where only source code was readable, the citation is to the code file.

## Key question 1 — How do After Effects, Blender, Maya, Cavalry, Rive and Lottie represent a keyframe curve, and how do they convert between value-graph and speed-graph views?

### Takeaway
All six use some flavour of piecewise cubic between keyframes, but they parametrise it differently: AE stores per-key *speed + influence* (a speed-graph parametrisation that maps 1:1 to a value-graph bezier handle), Blender/Cavalry/Rive-"Cubic Value" store 2-D bezier handles in (time, value) with the time coordinate clamped inside the segment, Maya stores Hermite tangents as angle (+ optional weight), Lottie/CSS store normalised 0..1 bezier handles per segment, and Rive's default "Cubic" is a normalised ease (no overshoot) applied to the value delta. Hold/step is universal; AE additionally separates *spatial* bezier paths (with roving keyframes) from the temporal curve.

### Cited Findings

**After Effects (temporal model: speed + influence; spatial model: bezier motion path)**
- AE distinguishes temporal interpolation (how values change over time; edited in the Graph Editor value graph) from spatial interpolation (the shape of the path in space; edited on the motion path in the Composition panel). Opacity has only a temporal component; Position also has spatial components. — [Adobe: Keyframe interpolation in After Effects](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- Interpolation types: **Linear** ("change begins instantly at the first keyframe and continues to the next keyframe at a constant speed"); **Auto Bezier** (default *spatial* method; "creates a smooth rate of change through a keyframe", handles reposition automatically when the value changes; dragging a handle converts it to Continuous Bezier); **Continuous Bezier** (smooth through the key, but you place handles; adjusting one side also changes the other); **Bezier** (the two handles "operate independently", allowing sharp corners); **Hold** ("available only as a temporal method", value holds until the next keyframe then changes immediately). — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- "Interpolation methods can vary the rate at which a property changes between keyframes, [but] cannot change the actual duration between keyframes." Preference "Default Spatial Interpolation to Linear" switches the spatial default away from Auto Bezier. Ctrl/Cmd-click toggles Linear ↔ Auto Bezier. — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- Artefact: "Auto Bezier can cause unwanted back-and-forth 'boomerang' motion between two keyframes with equal values"; the documented fix is to set the earlier key to Hold or both keys to Linear. — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- Speed graph editing: dragging a direction handle up/down changes speed ("the incoming handle increases the speed... when you drag it up"); dragging left/right changes **influence**, which "determines how quickly the speed graph reaches the value you set at the keyframe". Handles require Bezier or Continuous Bezier interpolation. — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html)
- Keyframe Velocity dialog (Animation > Keyframe Velocity, Ctrl/Cmd+Shift+K): numeric incoming/outgoing speed plus influence; "Influence is the amount of pull toward the previous keyframe (incoming) or the next keyframe (outgoing)"; the "Continuous (Lock Outgoing and Incoming)" option keeps in/out velocities equal. — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html); [Adobe shortcuts](https://helpx.adobe.com/after-effects/using/keyboard-shortcuts-reference.html)
- **Easy Ease** preset: "each keyframe has a speed of 0 with an influence of 33.33% on either side." — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html)
- Scripting model: `KeyframeEase(speed, influence)`; `influence` is a float in `[0.1..100.0]`; `speed` units "depend on the type of keyframe, and are displayed in the Keyframe Velocity dialog box". Applied via `setTemporalEaseAtKey(keyIndex, inEase[], outEase[])`. — [AE Scripting Guide: KeyframeEase](https://github.com/docsforadobe/after-effects-scripting-guide/blob/master/docs/other/keyframeease.md)
- Ease arrays are per dimension for non-spatial multi-dimensional properties: "If the property value type is `PropertyValueType.TwoD`, the array contains 2 objects... `ThreeD`... 3 objects. For all other value types, the array contains 1 object" (so `TwoD_SPATIAL`/`ThreeD_SPATIAL` get a single ease — one speed curve for the whole path). `KeyframeInterpolationType` is `LINEAR | BEZIER | HOLD`, set separately for in and out. `setTemporalContinuousAtKey` only affects a key whose in and out types are both BEZIER; `setTemporalAutoBezierAtKey` only applies when the key is also continuous. Spatial tangents: `setSpatialTangentsAtKey(keyIndex, inTangent[2|3], outTangent)`; `setSpatialContinuousAtKey`, `setSpatialAutoBezierAtKey` (again only when continuous). — [AE Scripting Guide: Property](https://github.com/docsforadobe/after-effects-scripting-guide/blob/master/docs/property/property.md)
- Roving: "The first and last keyframe in a property cannot rove; if you try to set roving for one of these, the operation is ignored"; `keyRoving` throws for non-spatial property types. — [AE Scripting Guide: Property](https://github.com/docsforadobe/after-effects-scripting-guide/blob/master/docs/property/property.md)
- Roving keyframes "are not linked to a specific time; their speed and timing are determined by adjacent keyframes"; they apply only to spatial properties (Position, Anchor Point, effect control points); "Rove Across Time" makes "the intermediate keyframes adjust their positions on the timeline to smooth the speed curve between the beginning and ending keyframes"; "Lock To Time" reverses it. — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html)

**Lottie / bodymovin (AE's export model)**
- Keyframe fields: `t` = "Frame number" (required); `o` = "Easing tangent leaving the current keyframe"; `i` = "Easing tangent going into the next keyframe"; `h` = hold (int-boolean, default 0). — [lottie-spec base-keyframe.json](https://github.com/lottie/lottie-spec/blob/main/schema/properties/base-keyframe.json)
- Easing handle: `x` "0 means start time of the keyframe, 1 means time of the next keyframe", min 0 / max 1; `y` "0 means start value of the keyframe, 1 means value at the next keyframe", **no min/max** (overshoot allowed). Both may be a number or an array (one per dimension). — [lottie-spec easing-handle.json](https://github.com/lottie/lottie-spec/blob/main/schema/properties/easing-handle.json)
- The easing curve is a cubic bezier from [0,0] to [1,1] with `o` as the first control point and `i` as the second; "Unlike `x` values, `y` values are not clamped to [0..1]". A property "MUST NOT have more than two keyframes with the same `t`"; with two at the same `t` the implementation renders one of the values (an explicit discontinuity mechanism). If the last keyframe is before the end, "the last keyframe value will be held until the end"; the last keyframe needs no `i`/`o`. With `h = 1` "the property will keep the same value until the next keyframe" and `i`/`o` may be omitted. — [lottie-spec properties](https://lottie.github.io/lottie-spec/latest/specs/properties/) (read from [source](https://github.com/lottie/lottie-spec/blob/main/docs/specs/properties.md))
- Position keyframes add `ti` (Value In Tangent) and `to` (Value Out Tangent): "Tangent for values (eg: moving position around a curved path)". — [lottie-spec position-keyframe.json](https://github.com/lottie/lottie-spec/blob/main/schema/properties/position-keyframe.json)
- lottie-web evaluation: `fnc = BezierFactory.getBezierEasing(keyData.o.x, keyData.o.y, keyData.i.x, keyData.i.y).get`; per-dimension easings are built when `o.x` is an array; `perc = fnc((frameNum - keyTime) / (nextKeyTime - keyTime))`; non-spatial value = `keyData.s[i] + (endValue[i] - keyData.s[i]) * perc`; hold keys skip easing entirely; `endValue = nextKeyData.s || keyData.e` (legacy `e` end-value field). — [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js)
- lottie-web spatial branch: `bez.buildBezierData(keyData.s, nextKeyData.s || keyData.e, keyData.to, keyData.ti)`; the control polygon is `s`, `s + to`, `nextS + ti`, `nextS` (sampled with the standard cubic basis); eased progress is mapped to arc length: `distanceInLine = bezierData.segmentLength * perc`, then the code walks the sampled points by `partialLength` and linearly interpolates between samples. `to/ti` are set to `null` (linear path) when the handles are collinear with the endpoints. — [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js); [lottie-web bez.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/bez.js)

**Blender (2-D bezier F-curves in time/value with handle types, plus procedural easing modes)**
- Interpolation per segment: Constant, Linear, Bezier (default; "smooth in both value and speed"); handle types apply only to Bezier. Easing modes (Sine, Quad, Cubic, Quart, Quint, Expo, Circ, Back, Bounce, Elastic) are Robert Penner-style and take an Easing Type (Automatic, Ease In, Ease Out, Ease In Out); "Automatic" uses Ease In for transitional types and Ease Out for the dynamic effects (Bounce, Elastic); Back and Elastic expose their own overshoot/amplitude/period settings. — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html)
- Handle types: **Automatic** (computed for smooth curves but "can overshoot and oscillate"); **Auto Clamped** ("clamps them so the curve doesn't overshoot or reverse direction between keys", recommended default: "use Auto Clamped by default, and only switch to Automatic handles in places where this is desired behavior"); **Vector** (automatic linear segments; moving a handle switches it to Free); **Aligned** (manual, locked opposite directions, "always smooth at the control point"); **Free** (independent). — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html)
- Handle Smoothing (per F-curve, for Automatic/Auto Clamped): "Continuous Acceleration" "produces much smoother curves out of the box, but necessarily means that any changes in the key values may affect interpolation over a significant stretch of the curve"; suggested for limited animation with few keys rather than many-key polished animation. — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html)
- Extrapolation: Constant (default) or Linear ("end segments continue as straight lines, based on the slope of the first and last keys"); cycling is done with F-Curve modifiers rather than extrapolation. — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html)
- Source-level evaluation (`fcurve.cc`): `fcurve_eval_keyframes()` dispatches to extrapolate/interpolate; segment lookup via binary search with a 0.0001 threshold; if the time lands on a key, the key value is returned; `BEZT_IPO_CONST`, discrete flag, or zero-duration segments return the previous key's value. For Bezier: control points = start key, its right handle, end key's left handle, end key; `BKE_fcurve_correct_bezpart()` clamps each handle **separately** so "handles cannot exceed the adjacent key-frames time position" (if a handle's x-extent `len1 > len`, it is scaled by `fac = len / len1`, keeping direction); then `findzero()` solves the cubic in x via `solve_cubic()` (closed-form; keeps roots in roughly [0, 1.000001]) and `berekeny()` evaluates y at that t. — [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc)
- Extrapolation in source: constant if the end key is `BEZT_IPO_CONST`, the curve is set to constant extrapolation, or the curve is discrete; for LIN end keys the slope comes from "the next center point instead of our own handle"; for Bezier end keys the slope comes from the end key's own handle. — [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc)

**Maya (Hermite tangents by angle, optional weight)**
- Tangent types in the Graph Editor Tangents menu: **Spline**; **Clamped** (spline shape "unless two adjacent key values are very close", in which case the segment is interpolated as linear — documented as the fix for "joint slippage" in walk cycles); **Linear**; **Flat** (horizontal); **Stepped** (out tangent flat; value changes at the key); **Plateau** (like spline but "flattens segments between equal-valued keys" and "ensures that the minimum and maximum values along a curve fall on keyframes"; first/last keys always flattened); **Auto** ("clamp curve values between frames to a maximum or minimum point based on the adjacent keyframe values"; first and last keys get flat tangents; interior keys do not overshoot neighbours). — [Maya: Graph Editor Tangents menu (2025)](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm)
- Newer Auto variants: "Auto Ease: Uses a cubic blend weighting, heavily influenced by neighboring keys"; "Auto Mix: A linear blend of the two slopes"; "Auto Span (Legacy)" is the older behaviour formerly just called Auto. "The default type for tangents is Auto." (Older docs list Clamped as the preference default — version-specific.) — [Maya: Graph Editor Tangents menu (2025)](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm); [Maya 2022 Tangents menu](https://help.autodesk.com/cloudhelp/2022/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm)
- Weighted tangents: "Tangents are non-weighted by default in Maya, which means they are locked and you can only change their angle, not their length"; switching keys to Weighted lets you drag length; "The higher the weight of a tangent, the more influence it has on the shape of the curve segment compared with the tangent at the other end"; "Free Tangent Length" (formerly "Free Tangent Weight") unlocks both angle and weight, "Lock Tangent Length" allows angle only. `keyTangent` exposes `-weightedTangents` and in/out tangent types `spline|linear|clamped|plateau|auto|...`. — [Maya: Change tangent weight](https://help.autodesk.com/cloudhelp/2022/ENU/Maya-Animation/files/GUID-884E25DE-2632-42A5-89B3-74B9E94544F4.htm); [keyTangent command](https://help.autodesk.com/cloudhelp/2024/ENU/Maya-Tech-Docs/Commands/keyTangent.html)

**Rive**
- Interpolation types: **Linear** (default; "constant rate of change"); **Cubic** (two draggable handles; default "eases in and out"; "Adjust a Cubic curve from the Interpolation Panel; the Graph Editor shows the curve, but you set it from the panel"; it "only moves between the keyed values"); **Hold** ("holds the current value until the next key is reached, where the next value is set instantly"); **Elastic** ("overshoots the value and oscillates before settling... - Runtime "Cubic Value": `transformValue(valueFrom, valueTo, factor)` computes `t = m_solver.getT(factor)` then `((m_A*t + m_B)*t + m_C)*t + m_D` with `y1 = valueFrom`, `y2 = handle y1`, `y3 = handle y2`, `y4 = valueTo`; `m_A = y4 + 3*(y2 - y3) - y1`, `m_B = 3*(y3 - 2*y2 + y1)`, `m_C = 3*(y2 - y1)`. **CSS (for comparison)**
- `cubic-bezier(x1, y1, x2, y2)`: "Both x values must be in the range [0, 1] or the definition is invalid"; y values are unrestricted. — [CSS Easing Level 2 ED](https://drafts.csswg.org/css-easing-2/) (read from [source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs))

### Inferences
- **Value graph ↔ speed graph in AE is a change of coordinates on the same cubic.** Influence is the handle's horizontal extent as a fraction of the segment duration; speed is the slope at the key. In normalised segment coordinates (x = fraction of Δt, y = fraction of Δv) the outgoing handle is therefore at `(I_out, I_out · s_out · Δt / Δv)` and the incoming handle at `(1 − I_in, 1 − I_in · s_in · Δt / Δv)`. This follows from the Adobe definitions (influence = "pull toward" the neighbour; handle up/down = speed) and the scripting ranges (influence 0.1–100 %), and it explains why AE must store a per-dimension ease for non-spatial 2-D/3-D properties (each dimension has its own Δv) but a single ease for spatial properties (one scalar speed along the path). The bodymovin exporter is the authoritative implementation of this conversion but its source could not be fetched (see Gaps).
- **Easy Ease = smoothstep.** Speed 0 and influence 33.33 % on both sides gives normalised handles (1/3, 0) and (2/3, 1); a cubic bezier with those handles is x(t) = t and y(t) = 3t² − 2t³. This also shows the Hermite↔bezier identity (handle = tangent/3; see Q3) that underlies AE's influence percentage.
- The speed graph is the derivative of the value graph; for spatial properties AE plots scalar speed (|dp/dt|) because the temporal ease drives arc-length fraction along the spatial path (the Lottie/lottie-web model, where `distanceInLine = segmentLength · perc`, is a direct re-implementation of AE's behaviour).
- Blender, Cavalry and Rive "Cubic Value" are the same mathematical object as the AE value graph: a 2-D cubic bezier in (time, value) whose handle x is confined to the segment, evaluated by solving x(t) = time. Rive's default "Cubic" and CSS `cubic-bezier` are the *normalised* form (handles in unit square, applied to the value delta); Lottie's `i/o` are the normalised form with unclamped y so AE value-graph overshoot survives export.
- Maya's "non-weighted" tangent (angle only) is a Hermite tangent with fixed handle length; "weighted" adds the bezier handle length as a free parameter. Weighted-tangent curves are therefore exactly Blender/AE-style free bezier handles; non-weighted ones are a subset.

- The bodymovin AE→Lottie keyframe exporter (`bm_keyframeHelper.jsx`) could not be fetched (repo not accessible via the GitHub API from this session and raw paths 404'd), so the exact speed/influence→(o,i) formula including its averaging over dimensions and its zero-delta guard is given above as an inference only.

- No official Cavalry documentation of a speed graph or of pre/post-keyframe extrapolation was found; Cavalry's "Magic Easing" is named in the docs but its curve definition was not found.

## Key question 2 — What is the maths of cubic-bezier easing (CSS timing function) and how is it solved for a given time? What are its limits?

### Takeaway
A CSS-style timing function is a 2-D cubic bezier P0=(0,0), P1=(x1,y1), P2=(x2,y2), P3=(1,1) with x1,x2 ∈ [0,1] (so x(t) is monotone and invertible) and y unbounded; evaluating it means solving the cubic x(t) = x for t, then returning y(t). Shipping solvers either use a sampled table + Newton–Raphson with a bisection fallback (bezier-easing ≤ v2.1, Rive, lottie-web's BezierFactory) or a closed-form Cardano/trigonometric root (bezier-easing current master, Blender's `solve_cubic`); limits are a single segment per keyframe pair and no overshoot unless y is allowed outside [0,1].

### Cited Findings
- Spec definition: `cubic-bezier( [ <number [0,1]>, <number> ]#{2} )`; output algorithm: with p0=(0,0), p1=(x1,y1), p2=(x2,y2), p3=(1,1), for input progress in [0,1] "return the y value of the cubic Bézier curve... at that x value" (the polynomial is delegated to [FUND-COMP-GRAPHICS]). Outside [0,1] the curve is extended along the tangent at the nearest endpoint: for input < 0, t1 = p0 and t2 = p1 if p1.x > 0, else p2 if p2.x > 0, else return 0; for input > 1, t2 = p3 and t1 = p2 if p2.x < 1, else p1 if p1.x < 1, else return 1; then return the y on the line through t1,t2. Keywords: `ease` = cubic-bezier(0.25, 0.1, 0.25, 1); `ease-in` = (0.42, 0, 1, 1); `ease-out` = (0, 0, 0.58, 1); `ease-in-out` = (0.42, 0, 0.58, 1). — [CSS Easing Level 2 ED source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)
- `linear()` (multi-point piecewise-linear easing): `linear( [ <number> && <percentage>{0,2} ]# )`; `linear` = `linear(0, 1)`; missing input values are canonicalised (first → 0, last → 1, non-monotone inputs raised to the preceding max, runs of missing inputs spaced evenly); output is found by selecting the bracketing points A,B (first two / last two for out-of-range inputs) and linearly interpolating **or extrapolating** along the line through them; a "before flag" makes multi-valued points return the first match. — [CSS Easing Level 2 ED source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)
- `steps(n, position)`: position defaults to `end`; `jump-none` requires n ≥ 2; interval outputs: jump-start first interval 1/n; jump-end first interval 0; jump-none rises by 1/(n−1); jump-both uses 1/(n+1); `step-start` = steps(1, start), `step-end` = steps(1, end); if the before flag is set the output is 0; "at the boundary between intervals, the associated value is the higher value". The document is an Editor's Draft (work status "exploring"). — [CSS Easing Level 2 ED source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)
- **bezier-easing v2.1.0 (Newton + subdivision):** constants `NEWTON_ITERATIONS = 4`, `NEWTON_MIN_SLOPE = 0.001`, `SUBDIVISION_PRECISION = 0.0000001`, `SUBDIVISION_MAX_ITERATIONS = 10`, `kSplineTableSize = 11`, `kSampleStepSize = 0.1` ("established by empiricism with tests (tradeoff: performance VS precision)"). Polynomial helpers A/B/C, `calcBezier(t, a1, a2)` for x(t) or y(t), `getSlope` for the derivative. At construction x(t) is sampled at 11 evenly spaced t. `getTForX(x)`: find the table segment containing x, linearly interpolate an initial guess, compute the slope there; if slope ≥ NEWTON_MIN_SLOPE run up to 4 Newton steps `t -= (x(t) − target)/slope`; if slope == 0 return the guess; otherwise bisect the segment until |error| ≤ 1e-7 or 10 iterations. Constructor throws "bezier x values must be in [0, 1] range"; if `mX1 === mY1 && mX2 === mY2` a linear function is returned; the ease returns exactly 0 at x=0 and 1 at x=1. — [gre/bezier-easing v2.1.0 src/index.js](https://github.com/gre/bezier-easing/blob/v2.1.0/src/index.js)
- **bezier-easing current master (closed form):** validates only x ∈ [0,1] (y unchecked); linear shortcut when both control points lie on the diagonal; coefficients `a = (3x1 − 3x2 + 1)/2, b = x2 − 2x1, c = x1` with x(t) = ((2a·t + 3b)·t + 3c)·t; `x2t` finds u = 1/t as the largest real root of a cubic (avoids dividing by `a`), rescales with `j = 1/max(c, sqrt(x))`, reduces to `v³ − 3m·v + 2h = 0`, uses Cardano when the discriminant `D > 1e-12·h²` (one real root) else the trigonometric three-root form taking the largest; result `min(1, k/(v+s))`; the ease returns `LinearEasing(x)` (clamped to [0,1], NaN passthrough) for x outside (0,1). The algebraic solver is credited to Dmitry Baranovskiy. — [gre/bezier-easing master src/index.js](https://github.com/gre/bezier-easing/blob/master/src/index.js)
- **Rive runtime** uses the same Newton/subdivision design: `NewtonIterations = 4`, `NewtonMinSlope = 0.001f`, `SubdivisionPrecision = 0.0000001f`, `SubdivisionMaxIterations = 10`, `SplineTableSize = 11`, `SampleStepSize = 1/(SplineTableSize − 1)`; `build(x1,x2)` fills `m_values[i] = calcBezier(i * SampleStepSize, x1, x2)`; `getT(x)` brackets linearly, guesses by interpolation, then chooses Newton (slope ≥ min), direct return (slope == 0) or bisection. — [rive-runtime cubic_interpolator_solver.cpp](https://github.com/rive-app/rive-runtime/blob/main/src/animation/cubic_interpolator_solver.cpp); [header](https://github.com/rive-app/rive-runtime/blob/main/include/rive/animation/cubic_interpolator_solver.hpp)
- **Blender** solves the same inversion with a closed-form cubic (`findzero()` → `solve_cubic()`, Cardano-style with quadratic/linear/constant fallbacks as coefficients vanish, keeping roots in ~[0, 1.000001]) after clamping handle x-extents into the segment. — [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc)
- **GSAP CustomEase** (multi-segment alternative): accepts SVG path data (`stringToRawPath`) or 4 numbers (cubic control points with implicit (0,0),(1,1)); segments are stored as cubics (6 numbers each, else "Invalid CustomEase"); `_normalize` maps x to 0..1 and y so the end reaches 1 (with `height`/return-to-start exceptions); `precision` defaults to 1 and sets a flattening threshold `1/(precision*200000)`; `_bezierToPoints` is recursive de Casteljau subdivision at t=0.5 until control points are near the chord; evaluation is a direct lookup `lookup[(p * l) | 0]` plus one linear interpolation `point.y + ((p − point.x)/point.cx) * point.cy` (no root solving); x points going backwards are dropped (x filtered to 0..1) but **y is not clamped, so overshoot is allowed**; inputs outside 0..1 are not handled explicitly. — [GSAP CustomEase.js](https://github.com/greensock/GSAP/blob/master/src/CustomEase.js)
- lottie-web caches a `BezierFactory.getBezierEasing(o.x, o.y, i.x, i.y)` function per keyframe and evaluates `perc = fnc(normalised time)`; the same normalised-handle model as CSS, with Lottie's `y` unclamped. — [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js); [lottie-spec easing-handle.json](https://github.com/lottie/lottie-spec/blob/main/schema/properties/easing-handle.json)

### Inferences
- The x ∈ [0,1] constraint is what guarantees x(t) is monotone on [0,1] (its derivative 3(1−t)²x1 + 6(1−t)t(x2−x1) + 3t²(1−x2) stays ≥ 0), which is why every solver can assume a unique root; Blender's `correct_bezpart` and lottie's/CSS's clamps are the same invariant expressed in absolute versus normalised coordinates. Handles with x outside the segment would make the curve multi-valued in time (a "time-travel" S-bend), which is the artefact these clamps prevent.
- For a deterministic rational-time evaluator, both solver families are deterministic (fixed iteration counts; no time-dependent state), but they differ in precision (bisection stops at 1e-7; Newton is typically far tighter; Cardano depends on cbrt/trig library accuracy). Picking one solver and using it for play, seek and export is what keeps the three in agreement; a sampled lookup like GSAP's trades exactness for speed and is only deterministic if the sample count is fixed.
- Limits of the CSS model: one cubic per keyframe pair (no inflection beyond what a single cubic allows, no bounce/elastic shapes), a flat start/end tangent only when the handle lies on the x-axis / y=1 line, and no overshoot unless y is allowed outside [0,1] (CSS and Lottie allow it; Rive's default "Cubic" does not, Rive's "Cubic Value" does). Multi-segment needs are met by CSS `linear()` (piecewise-linear) or GSAP-style path eases.

### Gaps
- lottie-web's `BezierFactory`/`BezierEaser` file itself was not fetched; its internal constants are assumed to match the original bezier-easing algorithm it is derived from but were not verified here.
- CSS Easing Level 1 (the REC-track document) was not fetched separately; findings are from the Level 2 Editor's Draft, which carries forward the Level 1 definitions plus `linear()`.

## Key question 3 — Which tangent-continuity models prevent velocity discontinuities and overshoot (C1/C2, Catmull-Rom, cardinal, Kochanek–Bartels, monotone Hermite, Blender auto-clamped) and how do they behave with uneven key spacing?

### Takeaway
Velocity continuity (C1) comes from making the in and out tangent slopes equal at every key (AE Continuous/Auto Bezier, Blender Aligned/Auto, Maya non-broken tangents); the *automatic* choice of that slope is where the models differ: Catmull-Rom/cardinal/KB pick a weighted average of neighbouring chords (smooth but can overshoot), monotone schemes (Fritsch–Carlson, Steffen, Blender Auto Clamped, Maya Auto/Plateau, Cavalry Auto-Bézier/Plateau) flatten at extrema and bound the slope so values never leave the keyed range, and C2 schemes (Blender "Continuous Acceleration") solve a global tridiagonal system at the cost of locality. With uneven spacing the naive uniform formulas misbehave; the Δ-weighted non-uniform tangent (Bessel/three-point) or centripetal parametrisation should be used.

### Cited Findings
- **Hermite ↔ bezier equivalence:** cubic Hermite interpolation "can be expressed in terms of cubic Bézier curves with respect to the four values p0, p0 + m0/3, p1 − m1/3, p1" (d3's `point()` does `dx = (x1 − x0)/3` and `bezierCurveTo(x0 + dx, y0 + dx*t0, x1 − dx, y1 − dx*t1, x1, y1)`). — [d3-shape monotone.js](https://github.com/d3/d3-shape/blob/main/src/curve/monotone.js)
- **Non-uniform Catmull-Rom tangent** (Δ_i = t_{i+1} − t_i, v_i = (x_{i+1} − x_i)/Δ_i): ẋ_i = (Δ_i² (x_i − x_{i−1}) + Δ_{i−1}² (x_{i+1} − x_i)) / (Δ_i Δ_{i−1} (Δ_i + Δ_{i−1})), equivalently the "standard three-point difference formula" ẋ_i = (Δ_i v_{i−1} + Δ_{i−1} v_i)/(Δ_{i−1} + Δ_i) (also called piecewise cubic Bessel interpolation); incoming and outgoing tangents "are supposed to be equal" (C1). — [splines docs: Non-Uniform Catmull–Rom](https://splines.readthedocs.io/en/latest/euclidean/catmull-rom-non-uniform.html) (read from the [notebook source](https://github.com/AudioSceneDescriptionFormat/splines/blob/master/doc/euclidean/catmull-rom-non-uniform.ipynb))
- **Parametrisation for spatial Catmull-Rom:** t_{i+1} = t_i + |x_{i+1} − x_i|^α; α=0 uniform ("typically works very well if the (Euclidean) distances between consecutive vertices are all similar", otherwise "in extreme cases there might be even cusps or self-intersections within a spline segment"); α=0.5 centripetal ("guarantees no cusps and no self-intersections" and is "the only parameterization in this family" with that guarantee, per Yuksel et al. 2011; for path animation the motion "will always be towards the next key-frame position"); α=1 chordal ("makes the speed along the spline nearly constant" but the curve can be "awkwardly far from long chords"). — [splines docs: Properties of Catmull–Rom Splines](https://splines.readthedocs.io/en/latest/euclidean/catmull-rom-properties.html) (read from [notebook source](https://github.com/AudioSceneDescriptionFormat/splines/blob/master/doc/euclidean/catmull-rom-properties.ipynb))
- **Kochanek–Bartels (TCB), uniform spacing:** tension scales both tangents by (1 − T); continuity splits them: incoming ½[(1 − C)d₋ + (1 + C)d₊], outgoing ½[(1 + C)d₋ + (1 − C)d₊] (equal when C = 0, "the requirement for a spline to be C1 continuous"); bias weights the chords ½[(1 + B)d₋ + (1 − B)d₊]; combined incoming tangent D⁻ = ½(1 − T)[(1 − C)(1 + B)d₋ + (1 + C)(1 − B)d₊]. T=C=B=0 is Catmull-Rom; C=B=0 is a cardinal spline. Parameter effects: "If t>0, the length of the tangent vector is reduced to zero and tightens the curve, if t<0... produced more slack"; "If b<0, the weight of the destination chord is greater, and if b>0, the weight of the source chord is greater"; C = −1 behaves like piecewise linear, C = 1 gives "inverse corners". — [splines docs: Uniform Kochanek–Bartels](https://splines.readthedocs.io/en/0.1.0/euclidean/kochanek-bartels-uniform.html); [IMSL CsTCB](https://help.imsl.com/java/2022.1/apidocs/com/imsl/math/CsTCB.html)
- **Kochanek–Bartels, non-uniform spacing:** ẋ_i^(−) = (c_i (t_{i+1} − t_i) v_{i−1} + d_i (t_i − t_{i−1}) v_i)/(t_{i+1} − t_{i−1}), ẋ_i^(+) = (a_i (t_{i+1} − t_i) v_{i−1} + b_i (t_i − t_{i−1}) v_i)/(t_{i+1} − t_{i−1}) with a_i = (1−T)(1+C)(1+B), b_i = (1−T)(1−C)(1−B), c_i = (1−T)(1−C)(1+B), d_i = (1−T)(1+C)(1−B); with T=C=B=0 this reduces to the non-uniform Catmull-Rom tangent. The notebook notes that Kochanek and Bartels' own 1984 adjustment for uneven spacing "only rescales the uniform tangents by inbetween counts and leaves their direction unchanged" and says its plots "illustrate the shortcomings of the tangent vectors suggested by Kochanek and Bartels". — [splines docs: Non-Uniform Kochanek–Bartels](https://splines.readthedocs.io/en/latest/euclidean/kochanek-bartels-non-uniform.html) (read from [notebook source](https://github.com/AudioSceneDescriptionFormat/splines/blob/master/doc/euclidean/kochanek-bartels-non-uniform.ipynb))
- **Fritsch–Carlson set-up:** with secants Δ_k, initial tangents m_1 = Δ_1, m_k = ½(Δ_{k−1} + Δ_k), m_K = Δ_{K−1}; define α_k = m_k/Δ_k and β_k = m_{k+1}/Δ_k for each interval; if either α or β is negative "the input data points are not strictly monotone" and the point is a local extremum. — [arXiv 2204.06848 appendix (via search extract)](https://arxiv.org/pdf/2204.06848); SLATEC `DPCHIM` cites Fritsch & Carlson 1980 as its reference ([DPCHIM listing](https://www.eecs.yorku.ca/~roumani/fortran/slatecAPI/dpchim.f.html))
- **Steffen monotone tangent (shipping implementation, d3):** "Calculate the slopes of the tangents (Hermite-type interpolation) based on the following paper: Steffen, M. 1990. A Simple Method for Monotonic Interpolation in One Dimension"; code: `p = (s0 * h1 + s1 * h0) / (h0 + h1); return (sign(s0) + sign(s1)) * Math.min(Math.abs(s0), Math.abs(s1), 0.5 * Math.abs(p)) || 0;` (zero when the secants change sign); one-sided end slope `(3 * (y1 − y0) / h − t) / 2`. — [d3-shape monotone.js](https://github.com/d3/d3-shape/blob/main/src/curve/monotone.js)
- **Blender automatic handles (`calchandleNurb_intern`):** missing neighbours are replaced by a mirrored phantom point (`pt[0] = 2.0f * p2[0] − p3[0]`); direction vectors `dvec_a = p2 − p1`, `dvec_b = p3 − p2`; **for F-curves only the X (time) component is used for lengths** (`len_a = dvec_a[0]`); the tangent is `tvec = dvec_b/len_b + dvec_a/len_a` (a chord-length-normalised average); the handle length is scaled by the constant `2.5614f`, and outside the smoothing path neighbour lengths are limited with `len_a = min(len_a, 5.0f * len_b)` (and vice-versa); with Handle Smoothing on, `len = 6.0f / 2.5614f` so that the horizontal handle size is forced to 1/3 of the key interval. **HD_AUTO_ANIM (Auto Clamped):** when the neighbouring Y values are on the same side of the key the handle is flattened (`/* keep horizontal if extrema */`, `bezt->vec[0][1] = bezt->vec[1][1]`); otherwise the handle Y is capped at the neighbour's value (`/* handles should not be beyond y coord of two others */`), and a `leftviolate/rightviolate` flag triggers realignment of the opposite handle. — [Blender curve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/curve.cc)
- **Blender "Continuous Acceleration" (C2) handles (`bezier_handle_calc_smooth_fcurve`):** "The exact solution is found by solving a tridiagonal matrix equation formed" from second-derivative continuity, under the assumption "that the handle horizontal size is always 1/3 of the" key interval; with `l[i] = dx[i+1]/dx[i]`, the interior equations are `a[i] = l[i]*l[i]; b[i] = 2.0f*(l[i] + 1); c[i] = 1.0f/l[i+1]`; boundary condition "fixed handles or zero curvature" (`bezier_eq_noaccel_right/left`), or locked unknowns; "full cycle merges first and last points into continuous loop" (one fewer unknown); clamp ranges are computed only where Auto Clamped handles are present; `tridiagonal_solve_with_limits` calls `BLI_tridiagonal_solve_cyclic` then locks handles that overshoot their limits ("heuristically only lock handles that go in the right direction if there are such ones", "to definitely avoid infinite loops limit this to 2 times"); `bezier_clamp` "prevents its own point going the wrong way, and adjacent handles overshooting"; output: left handle `−h[i]/l[i]`, right handle `h[i]`. `BKE_nurb_handle_smooth_fcurve` only smooths "continuous sub-sequences of free auto handles"; any non-auto key terminates a run; "ignore cyclic extrapolation if end points are locked". — [Blender curve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/curve.cc)
- Blender manual confirmation of the artefacts: Automatic handles "can overshoot and oscillate"; Auto Clamped prevents overshoot/direction reversal and "avoids S-shapes"; Continuous Acceleration is smoother but non-local. — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html)
- Maya's Auto tangent: interior keys "do not overshoot their neighbors", first/last flat; Plateau guarantees min/max fall on keyframes (falling-ball example: spline goes through the floor, plateau does not); Clamped linearises segments between nearly equal keys (anti-slippage). — [Maya Tangents menu](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm)
- Cavalry: Auto-Bézier "flattens them at peaks and troughs", Plateau "is stricter", Spline "can overshoot keyed values". — [Cavalry Docs: Graph Editor](https://cavalry.studio/docs/user-interface/menus/window-menu/scene-window/graph-editor/)
- AE: Auto Bezier/Continuous Bezier keep one tangent through the key; "Bezier" breaks it (independent handles, for sharp corners); the "boomerang" artefact appears between equal-valued Auto Bezier keys. — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)

### Inferences
- **Continuity classes map to artefacts.** C0 (linear, broken tangents) → velocity jump = visible "speed bump"/kink at the key. C1 (equal in/out slope, any handle *lengths*) → continuous velocity but possibly discontinuous acceleration; because the time axis is the x-axis, slope equality alone (not handle-length equality) is what guarantees velocity continuity in AE/Blender/Maya-style editors, which is why AE's "Continuous" only locks in/out *speed* and lets influence differ. C2 → continuous acceleration (Blender Continuous Acceleration / natural spline), at the cost that every key influences the whole run of auto keys.
- **Overshoot vs smoothness is the real trade-off.** Chord-averaging tangents (Catmull-Rom/cardinal/KB with C=0, Blender Automatic, Cavalry Spline, Maya Spline) overshoot whenever a key is a local extremum because the averaged slope is non-zero there. Every tool's "safe default" (Blender Auto Clamped, Maya Auto/Plateau, Cavalry Auto-Bézier/Plateau, AE's advice to use Hold between equal keys) is a monotone-style fix: zero slope at extrema plus a bound on the slope relative to the neighbouring chords. Fritsch–Carlson's α²+β² ≤ 9 region and Steffen's min(|s0|,|s1|,½|p|) are the formal versions; Blender's "handle y may not pass the neighbour's y" with a 1/3-interval handle is a slightly different sufficient bound in bezier space.
- **Uneven spacing.** Uniform formulas (m = ½(p_{i+1} − p_{i−1})) implicitly assume Δt equal; with a short interval next to a long one they produce a tangent far too steep for the short side (overshoot/oscillation) or too shallow for the long side. The Δ-weighted "three-point"/Bessel tangent — which Blender's F-curve code approximates by normalising chords by their *time* length and capping `len_a ≤ 5·len_b` — is the correct temporal fix, because for a temporal curve the parametrisation *is* time and cannot be re-chosen. Centripetal/chordal α only applies to *spatial* paths where the parameter is free (Q4). The splines documentation's criticism of KB's original non-uniform adjustment is a direct warning not to port 1984 TCB code unchanged into a non-uniform keyframe system.
- Fritsch–Carlson's final step (when α²+β² > 9, scale both tangents of the interval by τ = 3/√(α²+β²)) is the standard 1980 algorithm; it is widely implemented (SLATEC PCHIM, SciPy PCHIP) but could not be verified against a fetched primary source in this session, so treat the stated form as from the literature rather than a cited page.

### Gaps
- Primary texts of Fritsch & Carlson (1980), Fritsch & Butland (1984, weighted harmonic-mean variant), Steffen (1990) and Kochanek & Bartels (1984) were not fetchable; the Wikipedia/SciPy/SLATEC pages describing them were blocked. The τ-rescale step and the Fritsch–Butland weights are therefore not cited to a fetched source.
- Blender's `2.5614` handle-length constant has no explanatory comment in the visible code; its derivation is unknown.
- Maya's documented tangent types do not include a TCB/Kochanek–Bartels type (TCB is a 3ds Max controller); no 3ds Max documentation was fetched, so the TCB UI parameter ranges in a shipping tool are not cited.

## Key question 4 — Spatial paths: arc-length parametrisation, decoupling path shape from timing (AE roving keyframes), numerical arc-length tables

### Takeaway
Tools that offer motion paths (AE, Lottie, Cavalry) keep the path as a cubic bezier through the keyframe positions with spatial tangents, and drive motion along it by mapping the *temporal* ease to an arc-length fraction: progress p ∈ [0,1] from the value/speed curve → distance = p · L → t via an inverted cumulative-length table. lottie-web does this with 150 samples per segment and linear interpolation; AE's roving keyframes go one step further by freeing the *times* of intermediate spatial keys so a single speed curve spans several path segments.

### Cited Findings
- Arc length of a parametric curve: length = ∫₀ᶻ √(fx′(t)² + fy′(t)²) dt; "for cubic and higher curves... there is no 'closed form' solution" (Abel–Ruffini), so numerical methods are used: Legendre–Gauss quadrature remapped to [0,z] as (z/2)·Σ C_i · f((z/2)·t_i + z/2) (n=2: C₁=C₂=1, t = ∓1/√3, which the author calls "a bit low, really"). — [Pomax, A Primer on Bézier Curves: Arc length](https://pomax.github.io/bezierinfo/#arclength) (read from [source](https://github.com/Pomax/BezierInfo-2/blob/master/docs/chapters/arclength/content.en-GB.md))
- Tracing at fixed distance intervals: evenly spaced t values do not give evenly spaced points ("we can't just pick t values at some fixed interval"); the distance-vs-t function "can have more inflection points" than the curve; the practical method is a lookup table: sample the distance at many t, then for a required distance find "the closest t value that matches" and optionally interpolate between the two nearest samples ("with enough samples... we don't even need to bother"); David Eberly's method for moving at a specified speed is cited as the alternative to a LUT. — [Pomax: Tracing a curve at fixed distance intervals](https://pomax.github.io/bezierinfo/#tracing) (read from [source](https://github.com/Pomax/BezierInfo-2/blob/master/docs/chapters/tracing/content.en-GB.md))
- lottie-web `buildBezierData(pt1, pt2, pt3, pt4)`: control points are `pt1`, `pt1 + pt3`, `pt2 + pt4`, `pt2` (so `to`/`ti` are offsets relative to the start and end keyframe positions respectively); each sample is `ptCoord = (1−perc)³·pt1 + 3(1−perc)²·perc·(pt1+pt3) + 3(1−perc)·perc²·(pt2+pt4) + perc³·pt2`; `partialLength` is the Euclidean distance to the previous sample; `segmentLength` is the running sum; the sample count is `getDefaultCurveSegments()` and drops to 2 when both handles are collinear with the chord (`pointOnLine2D`, tolerance ±0.001). `getDistancePerc(perc, bezierData)` converts an arc-length fraction into t by locating the bracketing cumulative lengths (`lengths[initPos] <= lengthPos && lengths[initPos+1] > lengthPos`) and linearly interpolating `percents`. Results are cached per control-point string. — [lottie-web bez.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/bez.js)
- `defaultCurveSegments = 150` (settable via `setDefaultCurveSegments`); `subframeEnabled = true` by default. — [lottie-web common.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/common.js)
- lottie-web position evaluation: `distanceInLine = bezierData.segmentLength * perc` where `perc` is the *temporal* ease output; the walk over `points[j].partialLength` resumes from `_lastPoint/_lastAddedLength` when time moves forward; outside the segment the first/last sampled point is used; "Position with to/ti handles uses the single spatial bezier path with one easing over arc length, not separate x and y easings". — [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js)
- AE: spatial interpolation (Auto Bezier default, Continuous Bezier, Bezier, Linear) shapes the motion path; temporal interpolation and the speed graph control the rate along it; roving keyframes let "a handle have influence over more than one keyframe" and re-time intermediate keys "to smooth the speed curve between the beginning and ending keyframes"; roving is limited to spatial properties and excludes the first/last key. — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html); [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html); [AE Scripting Guide: Property](https://github.com/docsforadobe/after-effects-scripting-guide/blob/master/docs/property/property.md)
- Centripetal parametrisation of a spatial Catmull-Rom path guarantees no cusps or self-intersections within a segment (Yuksel et al. 2011), chordal gives near-constant speed, uniform can cusp. — [splines docs: Properties of Catmull–Rom Splines](https://splines.readthedocs.io/en/latest/euclidean/catmull-rom-properties.html)
- GSAP CustomEase flattens eases by recursive de Casteljau subdivision to a point list and evaluates by direct index into a lookup table (`lookup[(p * l) | 0]`) with one linear interpolation — the same LUT idea applied to a timing curve rather than a path. — [GSAP CustomEase.js](https://github.com/greensock/GSAP/blob/master/src/CustomEase.js)

### Inferences
- The AE/Lottie design is a clean separation of concerns: path shape = spatial bezier (positions + `to/ti` tangents, edited in the viewport), timing = scalar progress curve (value/speed graph or normalised `o/i`), joined by arc-length reparametrisation. Keeping these independent is exactly what lets a user retime without reshaping and reshape without retiming; the only coupling is the arc-length table, which must be rebuilt when the path changes (lottie-web caches it keyed on the control points).
- For a deterministic rational-time core, the LUT approach is preferable to adaptive methods: with a fixed sample count (lottie-web: 150) and a fixed inverse-interpolation rule, position(t) is a pure function of (t, path), so seek/play/export agree. lottie-web's forward-resume optimisation (`_lastPoint`) is only a search shortcut; its result is identical to a from-scratch search, but any implementation that *accumulates* distance frame-to-frame would not be seek-safe. Gauss–Legendre quadrature gives better total-length accuracy per sample than polyline summation but still needs an inverse (bisection/Newton on the cumulative length) to map distance → t.
- Roving keyframes can be understood as: positions of intermediate keys are fixed on the path, their times are unknowns, and the solver picks the times so the speed profile across the whole multi-segment path is continuous (constant speed when the end keys are linear). Because the first and last keys anchor total duration, each roving key removes one timing constraint and adds one smoothness constraint; this is why AE forbids roving on the ends. (Adobe does not publish the equations — see Gaps.)
- With the arc-length model, *spatial* tangent continuity (AE Auto/Continuous Bezier) governs direction smoothness and *temporal* continuity governs speed smoothness; a corner (AE "Bezier" broken spatial handles) produces a direction discontinuity even when speed is continuous, and vice-versa.

### Gaps
- Adobe does not document the roving-keyframe solver; no equations or constraints beyond "smooth the speed curve" were found.
- Cavalry's motion-path documentation (spatial handle behaviour, whether speed along the path is arc-length-based) could not be fetched.
- Eberly's "Moving Along a Curve with Specified Speed" (cited by Pomax) was not fetched.

## Key question 5 — Rotation: slerp vs squad vs Euler keyframes; how 2-D tools treat rotation beyond 360°; whether 2-D rotation has any smoothness issue

### Takeaway
3-D orientation needs quaternion slerp/squad (or carefully ordered Euler with a filter) to avoid gimbal lock and shortest-path flips; 2-D tools (AE, Lottie, Rive, Cavalry) store rotation as an unbounded scalar angle in degrees and interpolate it like any other scalar, so multi-revolution spins are trivial and no gimbal-type problem exists — the only pitfalls are wrap-around if angles are normalised, and the general scalar-curve artefacts (overshoot, velocity bumps) already covered.

### Cited Findings
- Slerp: introduced by Shoemake (1985, "Animating rotation with quaternion curves"); moves between unit quaternions at constant angular velocity along the shortest arc; exponential form Slerp(q₁, q₂; u) = q₁(q₁⁻¹q₂)^u; trigonometric form with weights sin((1−u)θ)/sinθ and sin(uθ)/sinθ where cosθ = q₁·q₂. — [ACM SIGGRAPH history: Shoemake 1985](https://history.siggraph.org/?p=107413); [splines docs: Slerp](https://splines.readthedocs.io/en/latest/rotation/slerp.html)
- Squad: Squad(p, a, b, q; α) = Slerp(Slerp(p, q; α), Slerp(a, b; α); 2α(1−α)); Shoemake's inner control quaternions a_n = b_n = q_n exp(−(ln(q_n⁻¹q_{n+1}) + ln(q_n⁻¹q_{n−1}))/4) (global-frame form a_i = exp(−(ln(q_{i+1}q_i⁻¹) + ln(q_{i−1}q_i⁻¹))/4)·q_i), which "matches the Euclidean quadrangle point formula for uniform Catmull–Rom splines"; Shoemake's paper "uses uniform parameter intervals and doesn't talk about the non-uniform case at all"; the docs derive non-uniform quadrangle points q̄_i^(±) weighted by Δ_i/(Δ_{i−1}+Δ_i) and report that with uneven times "the behavior of the Squad curve becomes more and more erratic" (control quaternions can "wrap around" the hypersphere, earlier than for a quaternion Catmull-Rom); "Allegedly, the proof of continuity of tangents by Shoemake (1987) is flawed" (new proofs: Kim et al. 1996, Dam et al. 1998). — [splines docs: Squad](https://splines.readthedocs.io/en/latest/rotation/squad.html) (read from [notebook source](https://github.com/AudioSceneDescriptionFormat/splines/blob/master/doc/rotation/squad.ipynb)); [rowan interpolate docs](https://rowan.readthedocs.io/en/latest/package-interpolate.html)
- Blender: Euler modes suffer "gimbal lock", which "can cause discontinuous interpolations when animating"; Quaternion mode "doesn't suffer from gimbal lock or any interpolation undesired effect" but "the animation will take the shortest path between them", so orientations more than 180° apart cannot be interpolated directly — "you must set up many intermediate keyframes, 180° from each other at most" — and "the animation curves in this mode are not intuitive". Older manuals require all keyframes of an object to use the same rotation mode. — [Blender Manual: Rotation Modes](https://docs.blender.org/manual/en/latest/advanced/appendices/rotations.html); [Blender 2.93 manual](https://docs.blender.org/manual/en/2.93/advanced/appendices/rotations.html)
- Lottie transform: `r` = "Rotation in degrees, clockwise" (no bound in the schema; the spec playground slider is −360..360 but "these ranges are slider limits, not documented constraints"); `sk` skew in degrees, `sa` skew axis in degrees. — [lottie-spec helpers/transform.json](https://github.com/lottie/lottie-spec/blob/main/schema/helpers/transform.json); [lottie-spec helpers](https://lottie.github.io/lottie-spec/latest/specs/helpers/)
- lottie-web has a separate branch (`this.sh`) that converts keyframe values to quaternions and uses `slerp` for 3-D orientation properties; ordinary rotation goes through the scalar keyframe path. — [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js)
- AE: a Rotation property with `loopOut()` keeps spinning to the end of the timeline; `time*40` on Rotation rotates at 40°/s; `loopOut("offset")` "repeats the segment but offsets each cycle by that value difference, multiplied by the loop count" (continuous spin rather than reset); `loopOut("continue")` extrapolates with the velocity at the last keyframe. — [Adobe: Expression language reference](https://helpx.adobe.com/ca/after-effects/using/expression-language-reference.html); [Adobe: Expression examples](https://helpx.adobe.com/in/after-effects/using/expression-examples.html)

### Inferences
- In a 2-D engine, rotation is a scalar in degrees and should stay unbounded (AE and Lottie both treat it so): 0 → 720 is two full turns, exactly what the keyframe curve says. Normalising to [0,360) at keyframe time would destroy multi-turn intent and create shortest-path ambiguity (the same 180° problem Blender documents for quaternions). There is no gimbal lock for a single-axis rotation; the only smoothness issues are the ordinary scalar ones (overshoot from auto-tangents, velocity bumps at linear keys), so the same curve model used for opacity/scale applies.
- If the app later adds 3-D layers (AE-style X/Y/Z rotation or Orientation), the choice is Euler-per-axis curves (editable, loopable, but can gimbal-lock and must be kept in a consistent order) versus quaternion slerp/squad (no gimbal lock, shortest-path only, uneditable curves, erratic squad under uneven spacing). AE's own split — editable X/Y/Z Rotation plus a separately interpolated Orientation — mirrors this; lottie-web's `sh`/slerp branch handles the latter.
- Slerp's shortest-path rule needs the sign flip: negate one quaternion when q₁·q₂ < 0 (double cover) and fall back to normalised lerp when θ is tiny to avoid sin θ → 0 — standard practice (not cited from a fetched page; see Gaps).

## Key question 6 — Colour interpolation: which spaces give perceptually smooth colour keyframes and avoid grey mid-points; CSS Color 4 rules

### Takeaway
CSS Color 4 makes Oklab the default interpolation space precisely because gamma-encoded sRGB "produces poorer results (overly dark or greyish mixes)"; interpolation must premultiply alpha, and polar spaces (Oklch/LCH/HSL/HWB) need an explicit hue-arc rule (default "shorter"). Legacy sRGB colours keep sRGB interpolation only for web compatibility.

### Cited Findings
- Default space: "If the host syntax does not define what color space interpolation should take place in, it defaults to Oklab." Legacy sRGB colours (hex, named, `rgb()`, `hsl()`, `hwb()`) must interpolate "in gamma-encoded sRGB space" for web compatibility; authors opt into better results via `color(srgb ...)` or by naming an interpolation space. — [CSS Color 4 source: Color Interpolation](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs) (published at [drafts.csswg.org/css-color-4](https://drafts.csswg.org/css-color-4/#interpolation))
- Why not sRGB: sRGB is "neither linear-light nor perceptually uniform" and "produces poorer results (overly dark or greyish mixes)"; an example shows that interpolating *without* premultiplication makes the centre of a red→transparent→blue gradient noticeably greyish because transparent is treated as transparent black. — [CSS Color 4 source](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Premultiplied alpha: when colours are not fully opaque, for rectangular spaces "all component values are multiplied by the alpha value"; for polar spaces "the hue angle is not premultiplied, but the other two axes are premultiplied"; after interpolation, if the interpolated alpha is zero or none the premultiplied values are kept, otherwise "each component which had been premultiplied is divided by the interpolated alpha value". — [CSS Color 4 source](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Missing components: a component missing in one colour "is treated as having the other color's component value"; if both are missing "the interpolated color will also be missing that component"; converting colours for interpolation "will turn any powerless components into missing components" (e.g. hue of an achromatic colour), and a missing alpha is carried forward before premultiplication. — [CSS Color 4 source](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Hue interpolation (default "shorter"): **shorter** — "Angles are adjusted so that |θ₂ − θ₁| ∈ [−180, 180]": `if (θ₂ − θ₁ > 180) θ₁ += 360; else if (θ₂ − θ₁ < −180) θ₂ += 360;` **longer** — `if (0 < θ₂ − θ₁ < 180) θ₁ += 360; else if (−180 < θ₂ − θ₁ ≤ 0) θ₂ += 360;` **increasing** — `if (θ₂ < θ₁) θ₂ += 360;` **decreasing** — `if (θ₁ < θ₂) θ₁ += 360;`. Hue is normalised to [0,360); a hue is powerless when chroma ≤ the space's ε. — [CSS Color 4 source: Hue Interpolation](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Why Oklab: it "was produced by numerical optimization of a large dataset of visually similar colors" and has "improved hue linearity, hue uniformity, and chroma uniformity compared to CIE LCH"; CIE LCH shows "noticeable purpling" in the blue hue slice while in OkLCh "the visual hue remains constant". — [CSS Color 4 source: Oklab and OkLCh](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Oklab conversion (CSS sample code): XYZ(D65) → LMS via a 3×3 matrix whose first row is `[0.8190224379967030, 0.3619062600528904, −0.1288737815209879]`; then `Math.cbrt` on each LMS component (sign-matched cube root, safe for negatives); then LMS′ → Oklab via a matrix whose first row is `[0.2104542683093140, 0.7936177747023054, −0.0040720430116193]`; inverse via `OKLabtoLMS` (first row `[1.0, 0.3963377773761749, 0.2158037573099136]`), cube, `LMStoXYZ`. sRGB transfer: `lin_sRGB`: |v| ≤ 0.04045 → v/12.92 else sign·((|v|+0.055)/1.055)^2.4; `gam_sRGB`: |v| > 0.0031308 → sign·(1.055·|v|^(1/2.4) − 0.055) else 12.92·v (negative inputs mirrored). — [CSS Color 4 conversions.js](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/conversions.js)
- Rectangular interpolation spaces include srgb, srgb-linear, display-p3, a98-rgb, prophoto-rgb, rec2020, lab, oklab, xyz(-d50/-d65); polar spaces are hsl, hwb, lch, oklch (as listed in the spec's predefined/polar space sections). — [CSS Color 4 source](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)

### Inferences
- For keyframed colours in a motion tool: interpolate in Oklab by default (rectangular, no hue ambiguity, perceptually even lightness so mid-points are neither dark nor grey); offer Oklch with the four hue arcs for deliberate hue sweeps (shorter is the safe default; longer/increasing/decreasing for rainbow-style keyframes); keep linear-sRGB as an option for physically-motivated light mixing; keep gamma-sRGB only for parity with imported CSS/legacy assets. Always premultiply alpha before interpolation and treat an achromatic key's hue as "missing" so it inherits the other key's hue instead of pulling toward hue 0.
- Colour banding: interpolating in a perceptual space does not by itself prevent banding; banding comes from 8-bit quantisation of the *output*. Interpolating in float Oklab/linear and converting to sRGB at the end (with dithering if needed) avoids both grey mid-points and the extra quantisation steps of interpolating in 8-bit sRGB. (Inference; CSS Color 4 does not discuss banding.)
- Because an easing curve is applied to the interpolation parameter, not the colour, the keyframe-curve model (Q1–Q3) is unchanged for colour; only the per-component blend differs. Hue must be eased as an angle after the arc adjustment, and overshooting eases (y outside [0,1]) will push chroma/lightness out of gamut, so clamping or gamut mapping is needed after interpolation.

- Which colour space AE, Rive, Cavalry or Lottie players use to interpolate colour keyframes was not found in any fetched documentation (lottie-web interpolates the raw numeric components of the `c` property like any multidimensional value, which implies gamma sRGB, but the spec text saying so was not fetched).

## Key question 7 — Hold/step keyframes and extrapolation (constant, linear, cycle, ping-pong, offset); interaction with smoothing

### Takeaway
Every tool has a hold/step mode (AE Hold, Blender Constant, Maya Stepped, Cavalry Step, Rive Hold, Lottie `h:1`, CSS `steps()`), and most offer the same extrapolation family — constant, linear (tangent continuation), cycle, cycle-with-offset, ping-pong/oscillate — either as curve settings (Maya infinity, Blender extrapolation + Cycles modifier) or as expressions (AE `loopOut`). Hold keys deliberately break C1 at the key; auto-tangent solvers should treat a hold or locked key as a boundary (Blender's C2 solver does), and cycling only stays smooth if the end tangents are solved cyclically.

### Cited Findings
- AE Hold: temporal only; the value holds until the next keyframe then changes immediately; used for strobe effects or sudden appearance; also Adobe's remedy for the Auto Bezier boomerang between equal keys. — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- AE extrapolation via expressions: `loopOut("cycle" | "pingpong" | "offset" | "continue", numKeyframes)`: cycle repeats the segment; pingpong alternates forward/backward; offset "repeats the segment but offsets each cycle by that value difference, multiplied by the loop count"; continue "does not repeat the segment" but "keeps animating the property based on the velocity at the first or last keyframe" and takes no keyframe argument; `loopOutDuration()` is the time-based variant. — [Adobe: Expression language reference](https://helpx.adobe.com/ca/after-effects/using/expression-language-reference.html)
- Blender: Constant interpolation holds until the next key; extrapolation is Constant (default) or Linear (slope of first/last keys); in source, discrete curves/constant end keys extrapolate constant, LIN end keys use the neighbouring key for slope, Bezier end keys use their own handle. Cycling is done via F-Curve modifiers. — [Blender Manual: F-Curve Properties](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html); [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc)
- Blender's C2 handle solver: "full cycle merges first and last points into continuous loop"; "ignore cyclic extrapolation if end points are locked"; smoothing runs only over "continuous sub-sequences of free auto handles" (a non-auto/locked key ends the run). — [Blender curve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/curve.cc)
- Maya: Stepped tangent = flat out tangent, value changes at the key (strobe), with an "Enable Stepped Preview" option; Pre/Post Infinity (Curves menu): Constant, Linear, **Cycle** ("repeats the animation curve as a copy infinitely"), **Cycle with Offset** (repeats but "appends the cycled curve's last key's value to the value of the first key's original curve" — for rolling wheels/steady climbs), **Oscillate** ("repeats the animation curve by reversing its values, and therefore shape, with each cycle"); baking a channel with Infinity on produces editable cycle keys. — [Maya Tangents menu](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm); [Maya Graph Editor Curves menu](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-619CAE9C-107D-4504-A769-227DDC847153.htm)
- Cavalry: Step ("L shape", hold); newer versions list Stepped and Stepped Next. — [Cavalry Docs: Graph Editor](https://cavalry.studio/docs/user-interface/menus/window-menu/scene-window/graph-editor/)
- Rive: Hold "simply holds the current value until the next key is reached, where the next value is set instantly". — [Rive Docs: Interpolation](https://rive.app/docs/editor/animate-mode/interpolation-easing)
- Lottie: `h = 1` holds the value until the next keyframe (`i`/`o` optional); last keyframe value is held to the end; two keyframes at the same `t` are permitted (at most two) to encode an instantaneous jump. lottie-web: hold keys bypass easing (`keyData.h === 1 ? keyData.s[i] : ...`). — [lottie-spec properties](https://lottie.github.io/lottie-spec/latest/specs/properties/); [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js)
- CSS: `steps()` semantics and the before-flag (output 0 when the before flag is set); `cubic-bezier()` extrapolates along the end tangents outside [0,1] and `linear()` extrapolates along its end segments (see Q2 for the exact rules). — [CSS Easing Level 2 ED source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)

### Inferences
- A hold key is a deliberate C0 break, so it must (a) suppress the easing solve for that segment (as lottie-web does), (b) act as a boundary for any auto-tangent or C2 smoothing pass (as Blender's solver does), and (c) define which value is shown *at* the key time (AE/Lottie: the key's own value; Blender: on-key time returns the key value). For a rational-time evaluator the "two keys at the same t" Lottie rule is the cleanest way to express a jump while keeping the map time → value a function.
- Cycle/ping-pong/offset are post-processes on time (and, for offset, on value): t′ = t₀ + ((t − t₀) mod T) (cycle), reflected modulo for ping-pong, plus k·(v_end − v_start) for offset, and tangent continuation for "continue"/Blender Linear/CSS. They are seamless only if the curve's end tangents match: cycle requires v and v′ equal at both ends (Blender achieves this by solving the auto handles cyclically; Maya/AE simply repeat and show a bump unless the user authored matching tangents); ping-pong is C0-continuous by construction but reverses velocity at the turn (a kink unless the end tangents are flat); offset needs equal end *slopes* (not values) to be smooth.
- Lottie has no extrapolation primitives (constant hold before/after only), so AE loop expressions must be baked to keyframes on export; the same applies to any interchange format the app emits.

### Gaps
- The Blender Cycles modifier's exact mode names/options (Repeat, Repeat with Offset, Repeat Mirrored, Before/After counts) could not be fetched; only its existence is cited.
- Cavalry pre/post extrapolation behaviour: no documentation found.
- Whether AE "continue" extrapolation uses the raw handle slope or the speed-graph value was not stated beyond "velocity at the first or last keyframe".

## Key question 8 — How tools expose a small set of easing presets, and the parameters behind them

### Takeaway
Presets are either fixed cubic-bezier handle sets (CSS keywords; Material 3 tokens; AE Easy Ease = speed 0 / influence 33.33 %; Rive F6–F10 shortcuts), Penner-style procedural functions with one or two parameters (Blender's easing modes with Back overshoot and Elastic amplitude/period; Rive Elastic), or physically parametrised springs (Apple's duration + bounce, which converts to mass/stiffness/damping). Multi-segment "emphasised" curves fall outside a single cubic-bezier and need a path/LUT ease (GSAP CustomEase).

### Cited Findings
- CSS keywords: `ease` (0.25, 0.1, 0.25, 1), `ease-in` (0.42, 0, 1, 1), `ease-out` (0, 0, 0.58, 1), `ease-in-out` (0.42, 0, 0.58, 1), `linear` = linear(0, 1), `step-start`/`step-end`. — [CSS Easing Level 2 ED source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)
- Material 3 motion tokens (material-web, tokens v0.192): emphasized `cubic-bezier(0.2, 0, 0, 1)`; emphasized-accelerate `(0.3, 0, 0.8, 0.15)`; emphasized-decelerate `(0.05, 0.7, 0.1, 1)`; standard `(0.2, 0, 0, 1)`; standard-accelerate `(0.3, 0, 1, 1)`; standard-decelerate `(0, 0, 0, 1)`; legacy `(0.4, 0, 0.2, 1)`; legacy-accelerate `(0.4, 0, 1, 1)`; legacy-decelerate `(0, 0, 0.2, 1)`; linear `(0, 0, 1, 1)`; durations short1–4 = 50/100/150/200 ms, medium1–4 = 250–400 ms, long1–4 = 450–600 ms, extra-long1–4 = 700/800/900/1000 ms. — [material-web _md-sys-motion.scss (v0_192)](https://github.com/material-components/material-web/blob/main/tokens/versions/v0_192/_md-sys-motion.scss)
- After Effects Easy Ease: speed 0, influence 33.33 % both sides (Easy Ease In/Out apply to one side). — [Adobe: Apply and control speed changes](https://helpx.adobe.com/after-effects/using/speed.html)
- Rive: default Cubic curve "eases in and out"; Elastic (Amplitude, Period); shortcuts F6 Hold, F7 Linear, F8 Cubic ease-in-out, F9 Cubic Value, F10 Elastic, with Shift/Ctrl modifiers for ease-in / ease-out variants; file-level Default Interpolation. — [Rive Docs: Interpolation](https://rive.app/docs/editor/animate-mode/interpolation-easing); [Rive shortcuts](https://rive.app/docs/editor/keyboard-shortcuts)
- Rive Elastic runtime: `m_s = amplitude < 1 ? period/4 : period/(2π)·asin(1/amplitude)`; easeOut = A(t)·2^(−10t)·sin((t − s)·2π/period) + 1; easeIn with t′ = t − 1: −A·2^(10t′)·sin((−t′ − s)·2π/period); easeInOut splits at t = 2·factor − 1 with ±0.5 scaling; for amplitude < 1 the amplitude is blended from 1 toward the target while |t| < |s| (`(m_amplitude*l) + (1 − l)`). — [rive-runtime elastic_ease.cpp](https://github.com/rive-app/rive-runtime/blob/main/src/animation/elastic_ease.cpp)
- Blender (Penner, BSD-3): Back: `change·t²·((overshoot+1)·t − overshoot) + begin` (in), out mirrors, in-out uses `overshoot *= 1.525`; Bounce-out uses the 7.5625 / 2.75 piecewise parabolas (offsets 0.75, 0.9375, 0.984375); Elastic: default `period = duration·0.3` (in-out: ·0.45); if `!amplitude || amplitude < |change|` then `s = period/4` with `elastic_blend` and `amplitude = change`, else `s = period/(2π)·asin(change/amplitude)`; ease-in = −f·amplitude·2^(10t)·sin((t·duration − s)·2π/period) + begin (t shifted by −1), ease-out = f·amplitude·2^(−10t)·sin(...) + change + begin; Expo is normalised with `pow_min = 2^−10` and `pow_scale = 1/(1 − 2^−10)` so it hits the endpoints exactly; Sine/Quad/Cubic/Quart/Quint are the standard Penner polynomials; Blender's "Automatic" easing picks ease-out for Back/Bounce/Elastic and ease-in for the others. — [Blender easing.cc](https://github.com/blender/blender/blob/main/source/blender/blenlib/intern/easing.cc); [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc)
- Apple springs: `Spring(duration: TimeInterval = 0.5, bounce: Double = 0.0)`; duration "is approximately equal to the settling duration, but for springs with very large bounce values, will be the duration of the period of oscillation"; bounce: "0 indicates no bounces (a critically damped spring), positive values indicate increasing amounts of bounciness up to a maximum of 1.0 (corresponding to undamped oscillation), and negative values indicate overdamped springs with a minimum value of −1.0". — [Apple: Spring.init(duration:bounce:)](https://developer.apple.com/documentation/swiftui/spring/init(duration:bounce:))
- WWDC23 "Animate with springs": conversion `mass = 1`, `stiffness = (2π ÷ duration)²`, `damping = 1 − 4π × bounce ÷ duration` for bounce ≥ 0, `damping = 4π ÷ (duration + 4π × bounce)` for bounce < 0; bounce range −1.0..1.0; bounce > 0 is a decaying cosine ("exactly the behavior of a cosine wave" at 100 %), bounce = 0 "a straight line going down and away that's getting multiplied by our decay", bounce < 0 "two exponential functions added together"; duration "is a perceptual duration that is chosen to be predictable and not move around, even as the other parameters of a spring change", distinct from the unpredictable settling duration; presets `.smooth` (no bounce), `.snappy` (small bounce), `.bouncy` (higher bounce), tunable via `duration:`/`extraBounce:`; on retargeting "a spring animation uses the velocity it had when it was retargeted as the initial velocity towards its new destination". — [Apple WWDC23 session 10158](https://developer.apple.com/videos/play/wwdc2023/10158/); [Apple: Spring.bouncy](https://developer.apple.com/documentation/swiftui/spring/bouncy)
- GSAP CustomEase: any SVG-path-shaped ease (multi-segment cubic), normalised to 0..1 in x, y may overshoot, evaluated by LUT (see Q2). — [GSAP CustomEase.js](https://github.com/greensock/GSAP/blob/master/src/CustomEase.js)
- Cavalry exposes preset curves in its Graph Attribute widget and a "Magic Easing" option in the keyframe dialog. — [Cavalry Docs: Graph Attribute](https://cavalry.studio/docs/user-interface/menus/window-menu/attribute-editor/widgets/graph-attribute/); [Cavalry Docs: Graph Editor](https://cavalry.studio/docs/user-interface/menus/window-menu/scene-window/graph-editor/)

### Inferences
- A compact preset vocabulary for a new tool: Linear; Ease-in / Ease-out / Ease-in-out as cubic-bezier handle sets (CSS keywords or Material "standard" (0.2,0,0,1) which is sharper and more modern-feeling than CSS `ease-in-out`); "Easy Ease" (1/3, 0)/(2/3, 1) = smoothstep for AE parity; Back/Elastic/Bounce as procedural Penner functions with Blender's/Rive's parameter forms; a spring with Apple's (duration, bounce) parametrisation, which is the most designer-friendly spring API found and converts to the physical model with the WWDC formulas. Everything except springs and Penner dynamics can be stored as bezier handles on the keyframe, which keeps one evaluator; springs and elastic need a separate, velocity-aware evaluator (interruptible, no fixed end time).
- Material 3's "emphasized" curve is documented by Google as a multi-segment path that CSS cannot express; the token file therefore aliases it to (0.2, 0, 0, 1). A tool that wants the true emphasised shape needs multi-segment eases (GSAP-style path or two keyframes).

## Key question 9 (synthesis) — Which model is preferred for which property type, and what each model avoids or causes

### Takeaway
For a deterministic, rational-time WebGL motion-graphics core the evidence from shipping tools converges on: a 2-D cubic bezier in (time, value) with time-clamped handles as the universal scalar/vector curve (AE value graph, Blender, Cavalry, Rive Cubic Value, Lottie), monotone/clamped auto-tangents as the default tangent mode, an explicit continuous/broken flag per key, a separate spatial bezier path driven through arc length for position, unbounded scalar degrees for 2-D rotation, Oklab (or Oklch with hue arcs) for colour, and hold keys plus cycle/offset/ping-pong/continue extrapolation as time-remapping post-processes.

### Cited Findings
- Scalar/vector properties: all surveyed desktop tools evaluate Bezier segments by root-solving x(t)=time after clamping handles into the segment (Blender `correct_bezpart` + `solve_cubic`; Rive `CubicInterpolatorSolver`; lottie-web `BezierFactory`). — [Blender fcurve.cc](https://github.com/blender/blender/blob/main/source/blender/blenkernel/intern/fcurve.cc); [rive-runtime cubic_interpolator_solver.cpp](https://github.com/rive-app/rive-runtime/blob/main/src/animation/cubic_interpolator_solver.cpp); [lottie-web PropertyFactory.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/PropertyFactory.js)
- Default tangent modes that prevent overshoot are the documented recommendation in Blender (Auto Clamped), the default in Maya (Auto), and the "Auto-Bézier"/"Plateau" behaviour in Cavalry. — [Blender Manual](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html); [Maya Tangents menu](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm); [Cavalry Graph Editor](https://cavalry.studio/docs/user-interface/menus/window-menu/scene-window/graph-editor/)
- Position: AE/Lottie decouple path (spatial bezier with `to/ti`) from timing (one scalar ease mapped to arc length with a 150-sample table). — [lottie-web bez.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/bez.js); [lottie-web common.js](https://github.com/airbnb/lottie-web/blob/master/player/js/utils/common.js); [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html)
- Rotation (2-D): degrees, unbounded, clockwise in Lottie; AE loop expressions treat it as a plain scalar. — [lottie-spec transform.json](https://github.com/lottie/lottie-spec/blob/main/schema/helpers/transform.json); [Adobe expression reference](https://helpx.adobe.com/ca/after-effects/using/expression-language-reference.html)
- Colour: Oklab default, premultiplied alpha, hue arcs, "overly dark or greyish mixes" in gamma sRGB. — [CSS Color 4 source](https://github.com/w3c/csswg-drafts/blob/main/css-color-4/Overview.bs)
- Opacity/scale/other scalars: Hold (AE "available only as a temporal method"), Constant (Blender), Stepped (Maya), `h:1` (Lottie), steps() (CSS) for discrete changes. — [Adobe: Keyframe interpolation](https://helpx.adobe.com/after-effects/using/keyframe-interpolation.html); [Blender Manual](https://docs.blender.org/manual/en/latest/editors/graph_editor/fcurves/properties.html); [Maya Tangents menu](https://help.autodesk.com/cloudhelp/2025/ENU/Maya-Animation/files/GUID-43A4FE2C-4863-4EA6-B6AE-6D2B6757F6C7.htm); [CSS Easing 2 source](https://github.com/w3c/csswg-drafts/blob/main/css-easing-2/Overview.bs)

### Inferences
- Artefact matrix (derived from the cited behaviours): **Linear** → velocity discontinuity at every key (speed bumps). **Free/broken bezier** → whatever the user draws; S-bends in time are prevented by handle-x clamping. **Chord-averaging auto tangents (Catmull-Rom/cardinal/KB C=0/Blender Automatic/Cavalry Spline/Maya Spline)** → C1, but overshoot at extrema and "boomerang" between equal keys; worse with uneven spacing if the uniform formula is used. **Monotone/clamped auto (Fritsch–Carlson/Steffen/Blender Auto Clamped/Maya Auto–Plateau/Cavalry Auto-Bézier)** → C1 and no overshoot, at the cost of flat tangents at every extremum (motion "parks" briefly at peaks, which is usually desirable in motion graphics). **C2 global (Blender Continuous Acceleration/natural spline)** → smoothest acceleration, but non-local edits and overshoot unless clamped. **Normalised cubic-bezier ease per segment (CSS/Lottie/Rive Cubic)** → simple, portable, single-segment; no overshoot unless y is unclamped; continuity across keys is not enforced unless the authoring UI mirrors handles. **Penner dynamics/springs** → intentional overshoot/oscillation; need parameters, not handles; springs are interruptible with velocity preservation.
- Recommended mapping by property type (inference from the above): scalars and per-component vectors (opacity, scale, skew, generic numbers, 2-D rotation in unbounded degrees) → (time,value) bezier with monotone auto-tangents by default, continuous/broken flag, optional procedural eases; position → spatial bezier path + scalar timing curve via fixed-sample arc-length LUT, with optional roving (free times) for multi-key paths; colour → same timing curve, blend in Oklab with premultiplied alpha, hue arcs for Oklch; booleans/enums/visibility → hold only; 3-D orientation (if ever) → quaternion slerp between keys (squad only with near-uniform spacing).
- Determinism checklist drawn from the implementations: fixed Newton/bisection iteration counts (bezier-easing v2.1/Rive) or closed-form roots (Blender/bezier-easing master); fixed arc-length sample count (lottie-web 150); no frame-to-frame accumulation; hold keys and same-time double keys evaluated by rule (value at the key time belongs to the key); all of these are pure functions of (rational time, curve data), so play, seek and export agree.
